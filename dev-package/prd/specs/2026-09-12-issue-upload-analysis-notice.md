# Spec: 2026-09-12 bugfix 회차 — 업로드 분석 구간의 고지와 소요

출처 intent: `dev-package/intent/2026-09-12-issue-upload-analysis-notice.md` (승인 2026-09-12 · Ted 확인 문장 "좋아 전부권고안으로" · 판정 기록 `dev-package/reports/issues/2026-09-12-ted-decisions.md` ③·⑧)

## 문제 진술

- 업로드 분석 진행 중 `다음 →`(`UploadModal.tsx` · `data-testid="reg-open"`)가 비활성이고, 비활성 사유를 전달하는 요소가 버튼에 연결돼 있지 않다 — 앵커 대조: 같은 버튼의 `disabled` 식은 `!status?.ready` 등 5항의 논리합이고, 같은 요소에 `title`·`aria-describedby` 속성 0건(`GitHub CognileapAI/colab-v2#24` ㉯).
- 조각 141 · 합계 48 MB(`gk2a_ami_le2_lst_ko_202005010000.nc` · LST) 업로드에서 분석 구간이 길게 이어진다는 보고가 있고, 접수→`ready` 소요를 잰 회차가 0건이다(`#24` ㉮).
- 같은 업로드의 다음 단계인 미리보기 렌더 소요도 실측 0건이다(`#25` ⑴).
- 합격선이 미정이라 두 구간이 수정 대상인지 판정할 입력이 없다.

## 해법 개요

- 사용자 관점 행위는 기존과 동일 — 파일을 올리고 분석이 끝나기를 기다린 뒤 `다음 →` 을 누른다. 새 화면·새 조작을 만들지 않는다.
- 추가되는 것은 비활성 버튼 옆의 정적 한 줄뿐이다 — 「분석이 끝나면 다음으로 갈 수 있어요」 계열 문면 1건. 분석 완료 시 그 줄이 사라지고 버튼이 활성으로 바뀐다.
- 비활성 조건 자체는 무변 — 정책 6 유지(`dev-package/reports/upload-layout-preview/policy-map.md` 정책 6 행). 인용: 원문 축자 「분석이 끝나야 다음 버튼이 켜진다」·「분석 완료 전 다음 비활성; 전송100%와 분석완료 구분」.
- 소요는 코드 변경 0의 측정 회차 1건으로 잰다 — 같은 업로드를 연속 두 단계(워커 분석 · viz 렌더)로 재고 보고서 1건을 배출한다. 합격선은 그 값을 본 Ted 가 지정한다.

## 사용자 스토리

1. 데이터를 올리는 연구자로서 `다음 →` 이 회색인 이유 한 줄을 버튼 옆에서 읽기를 원한다, 화면이 멈춘 것인지 기다리는 것인지 가르기 위해서.
2. 화면 낭독기를 쓰는 연구자로서 비활성 버튼에 초점을 두었을 때 사유 문장이 함께 읽히기를 원한다, 시각 배치만으로는 사유가 전달되지 않기 때문에.
3. 마우스를 쓰는 연구자로서 비활성 버튼 위에 커서를 두면 같은 사유가 뜨기를 원한다, 문장을 찾아 화면을 훑지 않기 위해서.
4. 데이터를 올리는 연구자로서 분석이 끝난 순간 사유 줄이 사라지기를 원한다, 이미 해소된 안내가 남아 혼선을 만들지 않기 위해서.
5. 데이터를 올리는 연구자로서 분석 완료 칩(`분석 중` → `분석 완료`)과 버튼 활성이 같은 시점에 바뀌기를 원한다, 두 표시가 어긋나면 어느 쪽을 믿을지 갈리기 때문에.
6. 조각 141개를 올리는 연구자로서 대기가 정상 범위인지 판정된 근거가 있기를 원한다, 같은 보고를 반복 제출하지 않기 위해서.
7. 판정자(Ted)로서 접수→`ready` 소요의 실측값을 조각 수별로 보기를 원한다, 합격선을 값에 근거해 정하기 위해서.
8. 판정자로서 분석 구간과 렌더 구간의 값이 같은 업로드에서 연속으로 측정되기를 원한다, 두 구간의 몫을 가르기 위해서.
9. 판정자로서 각 값에 측정 환경(로컬 / dev)과 실행 명령이 함께 적히기를 원한다, 다음 회차가 같은 조건으로 재측정할 수 있기 위해서.
10. 개발자로서 워커 고정 지연(5초)·화면 폴링 주기(1초)의 기여분이 값으로 분리되기를 원한다, 수정 대상을 순차 다운로드와 고정 지연 중에서 고르기 위해서.
11. 개발자로서 측정 중 상태 조회 오류 경로(재시도) 발생 여부가 기록되기를 원한다, 사용자가 본 정지 구간이 폴링 실패였을 가능성을 닫기 위해서.
12. 개발자로서 같은 업로드에서 렌더 요청 호출 횟수가 기록되기를 원한다, 재마운트로 인한 반복 렌더 가설을 닫기 위해서.
13. 조사자로서 같은 측정 회차에서 확장보기 겹침(`#29` ⑴) 재현 여부가 기록되기를 원한다, 그 항목의 등급(결함 / 좁은 폭 1열 접힘)을 가르기 위해서.
14. 조사자로서 같은 회차에서 부모 찾기 창 결과 0행(`#30` ㈎) 재현 여부가 기록되기를 원한다, 조회 결함 여부를 가르기 위해서.
15. 다음 회차 담당자로서 미확인 항목 중 이 측정이 닫은 것과 남은 것이 목록으로 구분되기를 원한다, 남은 조사 범위를 재산정하지 않기 위해서.

## 구현 결정

### 갈래 ㉯ — 비활성 사유 고지 (레인 L5 · frontend 단독)

- 모듈 = 업로드 모달 컴포넌트 1개 ＋ 문면 상수 모듈 1개. 새 컴포넌트·새 상태를 만들지 않는다.
- 문면은 문면 상수 모듈에 상수 1건으로 추가한다 — 인라인 문자열을 쓰지 않는다. 근거 = 같은 모듈이 분석 칩 문면 두 건(`ANALYZING_CHIP`·`ANALYZED_CHIP`)을 이미 상수로 소유하고 문면 자리표(`U-14` = 「업로드 장면1 · 분석 상태 칩」)를 함께 등재한다. 신규 상수도 같은 자리표 등재 규약을 따른다.
- 인터페이스 = 버튼과 사유 요소의 연결 2종.
  - 사유 요소 = 행동 줄 안의 정적 텍스트 요소 1개. 고유 `id` 를 가지고, 버튼이 `aria-describedby` 로 그 `id` 를 가리킨다.
  - 버튼 `title` = 같은 문면 상수.
- 표시 조건 = 버튼의 기존 `disabled` 식 중 **분석 미완(`status.ready` 거짓) 갈래일 때만** 표시한다. 실패·접수 오류(`status.failure`·`intakeError`·`statusIssue`) 갈래는 기존 오류 표시가 이미 자리를 가지므로 사유 줄을 중복 노출하지 않는다.
- 해제 조건 = 분석 완료 시 사유 요소가 DOM 에서 제거되고 `aria-describedby`·`title` 이 함께 사라진다. 버튼 활성 시점에 안내가 남지 않는다.
- 비활성 식 자체는 무변 — 항 추가·항 삭제 0.
- 상태 기계 (결정을 산문보다 정확히 담는 부분만):

  ```
  분석 진행(status.ready = false, 오류 없음)  → 버튼 disabled · 사유 요소 표시 · title 설정 · aria-describedby 연결
  분석 완료(status.ready = true, 오류 없음)   → 버튼 enabled  · 사유 요소 없음 · title 없음 · aria-describedby 없음
  오류(failure | statusIssue | intakeError)   → 버튼 disabled · 사유 요소 없음(기존 오류 표시가 담당)
  ```

- 스키마 · 마이그레이션 = 없음.
- API 계약 = 비파괴 · 변경 0건. `contracts/` 접촉 0.
- 파이프라인·워커 코드 접촉 0.
