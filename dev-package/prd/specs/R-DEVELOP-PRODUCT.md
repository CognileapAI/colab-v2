# Spec: R-DEVELOP-PRODUCT · 브랜치 전환과 운영 최초 초기화
출처 intent: `dev-package/intent/2026-09-15-develop-product-deployment.md` (승인 2026-09-15)

상태: 설계 초안. 구현·원격 설정·배포·삭제 미실행. 시험 경계는 2026-09-15 사용자 확인 완료: "네, 이 범위로 진행 (권고)".
계획 진행: 2026-09-15 사용자 "계쏙해"에 따라 실행 계획 작성으로 진행. 설계의 기술 권고를 사용자 개별 판정으로 기록하지 않는다.

## 문제 진술
- main 단일 배포 원천과 이에 고정된 검사·CI를 develop 개발 원천 및 product 운영 원천으로 바꿔야 한다.
- 운영 배포는 현재 수동 실행이다. 사람의 develop → product PR 병합을 배포 시작점으로 연결해야 한다.
- dev 전용 reseed를 그대로 운영에 실행할 수 없다. 첫 배포에만 운영 전체 초기화를 허용하고 이후 중복 실행을 막아야 한다.

## 해법 개요
- 기본 브랜치는 develop, 운영 배포 브랜치는 product로 분리한다. 운영 변경은 동일 저장소 develop의 PR을 사람이 병합하는 경로만 허용한다.
- 기존 배포·정본 적재·로그인·조회 흐름을 재사용한다. 승인된 병합 결과와 정본 입력을 고정하여 배포하고, 최초 회차에만 초기화한다.
- 최초 초기화 중에는 점검 상태를 유지한다. 검증 성공 후 서비스를 공개하며 실패하면 사람이 재개를 결정한다.
- 운영 환경 식별값은 사용자가 제공할 파일로 연결한다. 코드의 환경 이름 prod와 브랜치 이름 product는 별개로 취급하며 일괄 문자열 치환하지 않는다.

## 사용자 스토리
1. 개발자로서 기본 브랜치 develop에서 작업을 통합하고 싶다, 개발 변경과 운영 배포 시점을 분리하기 위해서다.
2. 운영자로서 develop의 변경을 product PR에서 검토하고 싶다, 배포할 변경을 사람이 확인하기 위해서다.
3. 운영자로서 PR을 직접 병합하면 배포되기를 원한다, 별도의 배포 승인 작업을 반복하지 않기 위해서다.
4. 운영자로서 다른 브랜치·외부 저장소 PR과 직접 push가 차단되기를 원한다, 지정된 배포 경로를 유지하기 위해서다.
5. 운영자로서 병합한 버전이 배포되기를 원한다, 이후 develop 변경이 배포 내용에 섞이지 않기 위해서다.
6. 운영자로서 첫 PR에서 삭제 대상과 정본 입력을 확인하고 싶다, 최초 운영 교체의 범위를 알기 위해서다.
7. 운영자로서 dev reseed와 동일한 계정·권한·소속·데이터·로그인 비밀번호를 운영에 재현하고 싶다, 같은 구성을 사용하기 위해서다.
8. 사용자로서 초기화 도중에는 점검 안내를 받고 싶다, 부분 적재 상태를 정상 서비스로 오해하지 않기 위해서다.
9. 운영자로서 첫 초기화 이후에는 일반 배포만 실행되기를 원한다, 운영 데이터가 반복 삭제되지 않기 위해서다.
10. 운영자로서 실행 중단 위치와 결과를 확인하고 싶다, 실패 후 안전하게 재개 여부를 결정하기 위해서다.
11. 운영자로서 환경·입력·자격이 없으면 실행 전에 실패하기를 원한다, 다른 환경에 변경을 가하지 않기 위해서다.
12. 사용자로서 완료 후 로그인과 자료 조회가 동작하기를 원한다, 배포 성공이 실제 사용 가능 상태를 뜻하기 위해서다.

## 구현 결정
- 모듈 · 인터페이스: 기존 CI, 배포 계획 실행기, 배포 원천 검사, reseed 단계 실행기를 연결한다. 운영 서버에서 GitHub PR 코드를 임의 실행하는 별도 우회 경로를 만들지 않는다.
- 브랜치 전환: 현재 원격 상태·열린 PR·보호 규칙·워크트리·배포 참조를 조사한 후 전환 기준 커밋을 기록한다. rename, 기본 브랜치 설정, CI·원천 검사 변경은 한 전환 계획에서 수행한다. 기존 개발 배포 주기는 임의로 바꾸지 않는다.
- product 최초 생성은 기준점 설정이며 최초 배포로 취급하지 않는다. 기준점과 첫 PR 변경이 존재하도록 전환 순서를 구성하고, 첫 운영 배포는 반드시 사람의 PR 병합에서 시작한다.
- develop 통합 흐름의 기점은 새 기본 브랜치로 옮긴다. staging 리허설 역할은 유지한다. product 승격 PR은 merge commit 방식을 제안한다. 장기 브랜치 사이의 공통 이력을 유지하며 develop을 product로 역병합해야 하는 운영을 추가하지 않는다.
- product 보호: PR 필수, 필수 검사, 직접 push·force push·삭제 금지, 자동 병합 금지. 출발 저장소와 출발 브랜치를 함께 검사한다. 사람 병합은 허용된 사람의 권한과 실제 병합 행위자 검증으로 강제한다. 봇 우회 권한을 배포 경로로 사용하지 않는다.
- PR 생성자가 사람 한 명인 경우 자신의 PR에 승인 리뷰를 줄 수 없으므로, 사람의 직접 병합을 별도의 필수 승인 리뷰와 혼동하지 않는다. 리뷰 인원 추가를 사용자 요구로 간주하지 않는다.
- CI 비교 기준은 PR 대상 브랜치를 따른다. develop과 product 모두 필요한 검사를 실행하고, 기존 main 고정 비교 때문에 잘못된 변경 범위를 검사하지 않도록 한다.
- 배포 원천은 dev에 대해 develop, 운영에 대해 product로 구분한다. 실제 배포 대상은 병합 이벤트에서 고정한 커밋과 산출물 식별값이다. 실행 중 최신 HEAD로 다시 선택하지 않는다. 기존 운영 릴리스 태그 요구는 유지하며, 태그와 후보 커밋을 대조한다.
- 자동 배포는 정상 병합 여부·출발 저장소·브랜치·사람 행위자·고정 커밋을 검증한 뒤 실행한다. PR 검증 작업에는 운영 비밀과 파괴 권한을 제공하지 않는다. 구체 실행 호스트와 접근 방식은 제공 설정 및 네트워크 조사 결과로 확정한다.
- 운영 배포는 직렬화하고 실행 중 강제 취소로 초기화가 끊기지 않도록 한다. 여러 PR이 연속 병합되거나 작업이 재시도돼도 오래된 후보가 최신 배포를 덮어쓰지 않는 순서 검사를 둔다.
- 최초 초기화 선언에는 환경 식별, 대상 DB·저장소, 삭제 계획, 정본 파일·자료의 식별값, 계정 구성, 후보 커밋, 최초 실행 식별자를 포함한다. 비밀번호 값과 그 값을 추측할 수 있는 검증용 해시는 공개 선언에 넣지 않는다.
- 후보 고정은 두 단계다. PR 검증 시 head/base SHA와 manifest digest를 결속하고, 사람 병합 후 실제 merge SHA의 부모 관계·승인 입력을 확인해 실행 기록에 결속한다. PR 이전에 아직 생성되지 않은 merge SHA를 요구하거나 manifest가 자신의 hash를 포함하도록 만들지 않는다.
- dev와 동일한 비밀번호는 기존 외부 비밀 전달 경로로 공급한다. 계정 신원·역할·소속과 정본 자료의 재현을 분리 검증하고, 로그인으로 인증을 확인한다. 실행 시점의 dev DB 전체를 그대로 복제하는 기능을 새로 만들지 않는다.
- 기존 dev 전용 reset의 거부 조건은 유지한다. 운영 초기화는 검증된 대상과 첫 PR 선언을 요구하는 별도 진입 조건을 갖추며, 공통 적재·검증 단계만 재사용한다.
- 최초 실행 상태는 초기화로 삭제되지 않는 운영 기록에 영속 보관한다. 미실행 → 실행 중 → 성공 또는 실패를 기록하고, 변경 시작 전에 잠금과 실행 식별자를 저장한다. 성공 상태에서는 다시 초기화하지 않는다. 실행 중·실패 상태에서 일반 배포 재시도는 중단한다. 기록 조회 실패를 미실행으로 해석하지 않는다.
- 삭제 대상은 검토된 정확한 목록과 대조한다. 운영 기록·백업 영역은 삭제 범위에서 제외한다. 실제 구성에 맞는 백업·복구 자료 확보는 삭제 전 조건이며, 실패 시 자동 복구를 뜻하지 않는다.
- 재개는 사람이 승인한 기존 실행 식별자와 기록을 사용한다. 선행 검사를 다시 수행하고, 완료된 단계 및 부분 실행된 단계의 정합성을 확인한 후 재개한다. 재개 명령으로 전체 reset을 자동 반복하지 않는다.
- 최초 실행 실패 후 기존 dev 경로의 앱 자동 재기동을 운영에 그대로 적용하지 않는다. 점검 상태는 애플리케이션 프로세스 생존 여부와 별도로 유지하고 모든 필수 검증이 성공한 뒤 해제한다.
- 스키마 · 마이그레이션: 신규 제품 스키마나 Alembic revision은 계획하지 않는다. 기존 플랫폼·AI 체인 분리를 유지하며 초기화 후 승인된 후보의 체인 끝점을 검증한다.
- API 계약: 비파괴. 제품 API·이벤트 변경 없음. 기존 계정 인증과 연구실 경계가 적용된 조회를 재사용한다.

## 시험 결정
- 외부 행위 기준 검증의 중심은 사람의 허용된 PR 병합 → 고정된 버전 배포 → 최초 초기화 → 로그인·자료 조회다. 아래 실패 경로도 같은 실행 경계에서 확인한다.
- 재사용 seam: 기존 배포 명령과 원천 검사, reseed 실행 명령과 원격 도구 대역, 로그인·자료 조회 및 기존 브라우저 사용자 여정. 내부 함수 호출 횟수만으로 성공을 판단하지 않는다.
- 신설 seam: GitHub 병합 이벤트를 기존 배포 명령에 연결하는 진입점. 외부 이벤트와 실행 기록을 입력해 허용·거부·재시도 결과를 검사한다.
- 신규 운영 점검 명령도 독립 시험 경계로 검증한다. 기존 운영에는 점검 전용 진입점이 없으며 웹/API/미리보기 공개 경로 차단과 비공개 적재·검증 접근이 함께 성립해야 한다.
- 정상 경로: 같은 저장소 develop PR의 사람 병합으로 정확히 지정된 후보가 운영에 반영되고 최초 검증 후에만 점검이 해제된다.
- 거부 경로: 다른 브랜치, 같은 이름의 외부 저장소 브랜치, 직접 push, 봇 병합, 미병합 이벤트, 대상 커밋 불일치, 운영 설정 부재에서 변경 작업 0건을 확인한다.
- 중복·경합 경로: 성공한 첫 실행의 이벤트 재전달, 배포 작업 재시도, 동시 실행, 기록 부재·조회 실패에서 잘못된 초기화가 발생하지 않는다. 일반 후속 배포의 reset 실행은 0건이다.
- 중단 경로: 변경 시작 전·삭제 중·적재 중·검증 중 실패를 주입한다. 실행 상태가 보존되고 운영은 점검 상태이며, 일반 재시도로 reset되지 않는다. 사람의 재개로 완료한 뒤에도 동일 자료가 중복되지 않는다.
- 정본 검증: 입력 manifest와 실제 생성 계획의 자료·연결 수를 대조한다. 현재 도구의 28개 자료·18개 연결 기대치는 입력 변경 시 승인된 계획과 함께 갱신하며 고정 숫자만으로 성공을 선언하지 않는다.
- 사용자 여정: 같은 계정·비밀번호 로그인, 역할·소속 및 연구실 경계, 자료 목록·상세·미리보기와 새로고침 지속성을 확인한다. 비밀번호와 인증 토큰은 증거에서 제외한다.
- 미리보기는 완료·실패의 최종 상태까지 기다린다. 컨테이너 표시 또는 실패 문구가 아직 없다는 이유만으로 성공으로 세지 않는다.
- 선행 증거: 잔여 결함의 실패 재현 및 수정 후 dev에서 10단계를 한 프로세스로 완주한다. 이 증거를 최초 운영 실행의 진입 조건으로 삼는다.
- 해당 서비스 단독 게이트 이름: 도구 변경에는 기존 `dev-reseed-selftest`를 적용한다. 배포 원천은 기존 dev·prod ship-gate 셸 시험을 확장한다. 신규 병합 진입점·최초 실행 기록 시험의 등록 이름은 실행 계획에서 정한다. 제품 서비스 코드 수정 시 해당 서비스 게이트를 추가한다.
- green-by-skip 방지: 필수 시나리오 목록과 실행·성공·판정 실패·준비 실패·면제 수를 보고한다. 대상 0건·입력 부재는 성공이 아니다. 게이트 종료 0/1/78을 보존하며 대역 시험과 실제 dev·운영 실행 근거를 구분한다.
- 시험 경계는 2026-09-15 사용자 확인 완료다. 이 문서는 검사 설계이며 위 시험을 실행했다는 보고가 아니다.

## 정책 대조 (작성 시점 제약)
- CLAUDE.md §2 도메인 / §3 불변 규칙: 도메인 소유 테이블, 플랫폼·AI 체인 분리, 연구실 경계를 유지한다. 계정은 신원·접근, 자료는 카탈로그·수집의 기존 흐름을 사용한다. 문서에 절대경로·비밀 값을 기록하지 않는다.
- CLAUDE.md §5: 승인 intent 범위만 수행한다. 기존 dev 거부 조건의 우회나 게이트 비활성화로 운영 실행을 성립시키지 않는다.
- CLAUDE.md §10 및 브랜치 정본: main 단일 원천과 develop 신설 제외 규칙은 승인 intent에 따라 개정 대상이다. 기존 규칙을 적용한 채 새 구조가 이미 허용된 것으로 보고하지 않는다.
- 배포 규칙의 dev 한정 초기화 예외: 사용자에게 승인된 최초 운영 교체의 대상·범위·첫 PR 증거를 조건으로 새 정책을 명시한다. dev 상시 승인 범위를 운영으로 확대하지 않는다.
- 계약 동결 해제 필요: 아니오 — 제품 계약 변경 없음.

### 디자인 제약 확인 (`frontend/` 를 건드리면 필수 · 화면마다 한 표)
- 해당 없음 — 제품 화면 변경은 계획하지 않는다. 운영 점검은 배포 계층에서 유지하며, 새로운 제품 화면이 필요해지면 해당 디자인 제약을 먼저 추가한다.

## 범위 밖
- 최초 회차 이후 운영 reseed, 일반 배포 재시도로 전체 초기화 반복.
- 추가 배포 승인, 봇 자동 병합, develop 이외 브랜치의 product 직접 반영.
- dev와 다른 운영 비밀번호 발급 정책 및 임의 제품 기능·계약·화면 변경.
- 실패 시 자동 데이터 복구 및 자동 서비스 공개.
- 운영 설정 파일 없이 대상 환경 추측, 이 spec 작성 중 브랜치·GitHub 설정·운영 데이터 변경.
