# Stage 2 미리보기 보존 — BF-12 · TL-2

출처: `R-STAGE1-STAGE2-CLOSEOUT.md` Task 6, 대장 `BF-12`·`TL-2`, 사용자 2026-09-10 승인 경계.

## 현재 사실

- BF-12의 로깅 설정·실패 시험은 이미 main에 있고 로컬에서 INFO stdout, 멱등, 비밀 미출력을 증명한다.
- 판정처는 staging이 아니라 dev(AWS)다. dev compose에는 현재 이벤트 스풀 선언·공유 볼륨이 없어 viz 배경 루프가 서지 않는다.
- dev의 source와 preview sink는 S3다. 기존 `ReclaimJob`은 로컬 디렉터리만 읽으므로 스풀만 연결하면 주체 0의 준비 실패를 낸다. 이것을 첫 바퀴 계수로 세지 않는다.
- TL-2는 BF-12 dev 첫 바퀴 실측이 선 뒤에만 착수한다.

## BF-12 dev 관측기

- pipeline-worker와 viz-render가 하나의 쓰기 가능한 이벤트 스풀 볼륨을 공유한다. 이 배선은 자동 무효화와 회수 루프를 함께 켠다.
- S3 모드의 회수는 관측 전용이다. `COLAB_VIZ_TILE_RECLAIM_APPLY` 값과 무관하게 S3 DeleteObjects를 호출하지 않는다.
- 목록 범위는 정확히 `uploads/`와 `previews/`뿐이다. 빈 접두사·버킷 루트 목록은 거부한다.
- 주체의 타일 키는 객체 ETag가 아니라 본체·격자 바이트 전체를 최대 1 MiB 청크로 읽어 계산한 SHA-256으로 재계산한다. ETag는 HeadObject와 조건부 GetObject가 같은 버전인지 고정하는 데만 쓴다.
- 관측기는 파일을 작업 디렉터리에 materialize하지 않는다. 전체·단일 객체 크기가 작업 디렉터리 상한보다 커도 streaming하며, 메모리는 청크와 다이제스트·목록 메타데이터로 제한한다. 렌더 중인 공용 source cache는 읽거나 지우지 않는다.
- 목록·HeadObject·조건부 GetObject의 크기 또는 버전이 갈리거나 수신이 부족·초과하면 즉시 준비 red다. 열린 응답 스트림은 성공·실패 모두 닫는다.
- 목록·다운로드·크기 검증 중 하나라도 실패하면 고아 0으로 접지 않고 `ready=false` 요약을 남긴다.
- 성공 요약은 주체, 타일 벌, 닿음, 못 닿음, 삭제 0을 한 줄로 남긴다. object key 외 자격증명·URL·헤더·본문은 로그에 싣지 않는다.

## TL-2 순서와 경계

- BF-12를 닫는 증거는 동일 dev 배포 SHA에서 장기 서비스 4개 healthy와 init·migration 일회성 작업 성공을 확인한 뒤 얻은 첫 주기 로그다. 기본 주기 3600초를 임의로 짧게 바꾸어 완료를 주장하지 않는다.
- 로그에서 삭제 0, 비밀 0, 유효 계수를 확인한 뒤에만 TL-2 RED 시험을 작성한다.
- TL-2는 원장 부재와 사이드카 부재를 별도 관측 등급으로 가르고 둘 다 자동 삭제하지 않는다. 기존 19벌과 재굽기로 닿지 않는 16벌을 실제 dev 자료로 대조한다.
- dev 배포와 실제 캐시 삭제는 각각 실행 직전 사용자 승인을 받는다. 이 라운드에서 실제 삭제는 수행하지 않는다.

## 완료 판정

- 로컬: S3 관측기와 dev 배선의 실패 시험 RED → GREEN, viz/pipeline 단독 게이트와 경계 게이트 green.
- BF-12: 승인된 dev 배포 후 첫 주기 요약 1줄, 유효 계수, 삭제 0, 비밀 0.
- TL-2: BF-12 완료 뒤 분류 시험·구현·실데이터 관측이 모두 서며 삭제 0. BF-12가 열려 있으면 TL-2도 열어 둔다.
