# Spec: 운영자용 Slack 상태 알림과 사용자 활동 일일 보고
출처 intent: `dev-package/intent/2026-09-12-operator-slack-notifications.md` (승인 2026-09-12)
상태: intent 승인·시험 경계 확인 완료(2026-09-12) · 실행 계획 작성 완료 · 구현/실제 연결/전송 미실행

## 문제 진술
- 기존 배포 실행기는 배포·검증 성공만 Slack으로 보내며 실패 경로는 전송하지 않는다. 상태 감지는 별도 webhook 구조이고, 채널 분리·전달 상태·중복 정책이 통합되어 있지 않다.
- 사용자 활동·다운로드·권한 변경·접근 요청 원장이 서로 다르고 일부 변경 사건이 기록되지 않는다. 기존 홈 활동 조회는 삭제된 대상을 제외하므로 감사 보고의 원천으로 그대로 사용할 수 없다.
- 운영자는 시스템 이상을 제때 알고, 매일 실제 이용 연구실 전체의 활동과 감사 상세를 확인해야 한다. 수집 실패와 무활동, 사건 성공과 알림 실패를 구분해야 한다.

## 해법 개요
- 개발 상태 전용 채널과 사용자 활동 전용 채널에 서로 다른 Slack incoming webhook을 연결한다. 사용자 활동 채널 한 곳에 일일 요약과 감사 상세를 함께 보낸다. 채널 이름·ID·비밀값은 연결 입력이며 문서에 가짜 값을 채우지 않는다.
- 배포 결과·CoLAB 점검 결과·관련 AWS 상태를 사건으로 저장한 뒤 Slack 전달 작업으로 분리한다. 알림 재시도가 배포·사용자 작업을 다시 실행하지 않는다.
- 매일 한국 시간 08:00에 전날 실제 사용 환경의 활동을 집계한다. 연구실별·사용자별 일반 활동 요약 다음에 삭제·권한 변경·접근 승인·거절의 상세를 보낸다.
- 기존 도메인별 원장을 재사용하고, 없는 변경 기록만 원래 행위를 소유하는 도메인에 보강한다. 운영 보고의 조립층은 도메인의 읽기 Port를 통해 합친다.
- 이번 산출물은 사양이다. 구현·시험·배포·실제 Slack 연결 결과로 표시하지 않는다.

## 사용자 스토리
1. 운영자로서 배포 환경·버전과 성공 여부를 알고 싶다, 어느 환경이 바뀌었는지 판단하기 위해서다.
2. 운영자로서 배포 실행 실패와 배포 후 검증 실패를 구분하고 싶다, 대응해야 할 지점이 다르기 때문이다.
3. 운영자로서 서비스·백업 이상과 복구를 받고 싶다, 정상화 여부를 추측하지 않기 위해서다.
4. 운영자로서 같은 장애의 반복 관측을 새 장애와 구분하고 싶다, 반복 메시지 때문에 새 문제를 놓치지 않기 위해서다.
5. 운영자로서 AWS에서 발생한 관련 상태 변화도 받고 싶다, CoLAB 앱이 실행되지 못하는 상황도 파악하기 위해서다.
6. 개발자·운영자로서 개발 상태와 사용자 활동을 다른 채널에서 받고 싶다, 대응 알림과 일일 업무 확인을 구분하기 위해서다.
7. 운영자로서 매일 08:00에 전날 보고를 받고 싶다, 같은 시간 범위로 이용 현황을 비교하기 위해서다.
8. 운영자로서 모든 실제 연구실의 활동을 보고 싶다, 특정 연구실만 보고 전체라고 오인하지 않기 위해서다.
9. 운영자로서 시험 활동을 제외하고 싶다, 시험 자동화가 실제 이용 현황을 부풀리지 않기 위해서다.
10. 운영자로서 일반 활동을 사용자별로 요약해 보고 싶다, 활동이 많아도 읽을 수 있기 위해서다.
11. 운영자로서 삭제·권한 변경·접근 승인·거절의 행위자·시각·대상·변경 내용을 건별로 보고 싶다, 중요한 조치를 추적하기 위해서다.
12. 운영자로서 삭제된 대상도 감사 내역에서 확인하고 싶다, 현재 화면에 없다는 이유로 기록이 사라지지 않기 위해서다.
13. 운영자로서 활동이 없던 날과 집계 실패를 구분하고 싶다, ‘활동 없음’을 잘못 믿지 않기 위해서다.
14. 운영자로서 실패한 보고가 늦게라도 도착하기를 원한다, 일시적인 장애로 하루 기록을 잃지 않기 위해서다.
15. 운영자로서 중요한 장애의 전송 여부가 불명확하면 중복 가능성을 표시한 재전송을 원한다, 누락보다 중복을 감수하기로 했기 때문이다.
16. 운영자로서 보고가 여러 메시지로 나뉘어도 날짜·순서·누락 여부를 알고 싶다, 일부 메시지를 전체 보고로 오인하지 않기 위해서다.
17. 운영자로서 집계 기능이 일반 사용자의 연구실 접근 권한을 바꾸지 않기를 원한다, 운영 보고 때문에 제품 경계가 넓어지면 안 되기 때문이다.
18. 운영자로서 다운로드 기록의 실제 의미를 알고 싶다, 티켓 발급만으로 파일 수신 완료를 단정하지 않기 위해서다.

## 구현 결정

### 모듈 · 인터페이스와 배치
- 사건 생성, 원장 읽기, 보고 조립, 전송을 분리한다. 앱 요청 안에서 Slack을 호출하거나 일일 스케줄을 앱 워커의 background task에 넣지 않는다.
- 개발 사건은 기존 배포 실행기와 상태 감지기가 생성한다. 실행 결과를 영속 기록한 후 전송 대기열로 넘긴다. 배포 ID·환경·검증 결과를 유지하며 기존 배포 잠금은 보존한다.
- 사용자 보고는 독립된 운영 CLI/job이 실행한다. D1은 연구실 목록과 표시 이름, D2는 접근·권한 사실, D3은 데이터 변경·삭제 감사, D5는 업로드 접수 사실, D6은 프로젝트 생성·삭제 감사, D8은 기존 활동·다운로드를 제공한다. 조립층만 여러 Port를 함께 호출한다.
- AWS 수집·Slack 전송은 CoLAB 앱/DB가 중단돼도 실행할 수 있는 EventBridge → SQS → Lambda 경로로 구성한다. 개발/사용자 보고 큐는 분리하고, 영속 사건·전송 상태는 DynamoDB에 둔다. HTTP sender·사건 정규화·보고 렌더링은 AWS 런타임과 분리한 순수 인터페이스로 시험한다. 신규 AWS 자원은 이 사양의 구현 대상이며 현재 설치된 것으로 간주하지 않는다.
- 로컬 발생 사건은 영속 볼륨의 전송 대기 기록에 먼저 보존하고 원격 저장 접수 후 발행 완료로 기록한다. AWS 이벤트는 큐 소비자가 영속 저장한 뒤 메시지를 확인 처리한다. 큐는 운송 수단이며 유일한 원장이 아니다.
- SQS/Lambda에는 중복 전달을 전제로 한 처리를 적용한다. 수신 큐의 ARN으로 허용되는 논리 채널을 결정한다. 메시지 안의 임의 채널·webhook 값으로 목적지를 바꾸지 않는다.

### 개발 상태 사건과 중요도
| 사건 | 발생 기준 | 중요도·처리 |
|---|---|---|
| 배포 성공 | 대상 환경의 배포와 선언된 검증 모두 성공 | 정보, 배포 ID·환경별 최종 결과 1건 |
| 배포 실행 실패 | 관리 실행기의 배포 단계 실패 | 중요, 실패 단계·환경·버전·배포 ID |
| 배포 후 검증 실패 | 배포는 실행됐지만 검증 실패 | 중요, 배포 실행 실패와 별도 문면 |
| 서비스 이상/복구 | 환경별 기존 health 점검의 이상 전이/회복 | 이상은 중요, 복구는 회복 통지 |
| 백업 이상/복구 | 기존 백업 신선도 oracle의 이상 전이/회복 | 이상은 중요, 복구는 회복 통지 |
| 정기 배포 검증 이상/복구 | 실행 중인 버전의 정기 검증 이상 전이/회복 | 배포 작업 실패와 별도 사건 |
| AWS 관련 장애/종료 | 사용 계정·서비스·리전·자원과 관련된 AWS Health issue 및 closed 갱신 | issue는 중요, closed는 AWS 사건 종료로 표시 |
| AWS 예정 변경 | 관련 자원의 scheduledChange | 주의, 예정 시각과 영향 대상 표시 |
| AWS 자원 상태 경보 | 등록 자원의 CloudWatch ALARM/OK/INSUFFICIENT_DATA 전이 | ALARM은 중요, OK는 해당 경보 회복, 데이터 없음은 관측 불가 |
| 수집·보고·전송의 지속 실패 | 전송/집계 재시도 실패 또는 정기 실행 heartbeat 누락 | 개발 채널에 운영 알림 자체의 이상으로 표시 |

- 자체 probe는 기존 5분 주기·연속 2회 실패 임계를 승계하고 회복은 활성 이상 뒤 첫 성공이다. 배포 명령 실패는 이 임계를 기다리지 않는다. 같은 활성 이상에는 추가 정상 관측/실패 관측 메시지를 보내지 않는다. 재발에는 새 incident ID를 부여한다.
- AWS Health 사건 종료는 CoLAB의 실제 복구를 증명하지 않는다. 자체 서비스 복구와 이름·사건 ID를 분리한다. 기존 장애를 못 본 첫 OK를 ‘복구’라고 만들지 않는다.
- AWS 범위는 연결 manifest에 계정·사용 리전·전역 이벤트 리전·관련 서비스·자원과 환경 매핑을 명시한다. Health issue/scheduledChange와 관련 상태 갱신을 수집하고 무관한 전 계정·전 서비스 소식을 보내지 않는다. 미지정 자원은 임의 환경으로 분류하지 않으며 수집 범위 미확정으로 readiness 실패를 낸다.
- CloudWatch는 현재 등록된 CoLAB EC2의 instance/system status check와 등록된 상태 경보의 전이를 연결한다. 기존 앱·백업·정기 검증 probe는 heartbeat를 내고, 15분 이상 관측이 없으면 관측 중단 경보를 낸다. 새로운 지출·보안·사용자 행동 탐지 기능은 추가하지 않는다.
- AWS Health는 EventBridge 수집을 사용하며 유료 지원 플랜을 전제로 Health API polling을 추가하지 않는다. 사용 리전과 전역 사건을 받는 us-east-1 규칙의 누락을 검사한다.

### 사건 식별·전송 상태·재시도
- 정규 사건에는 schema version, event ID, source, environment, occurred_at(UTC), severity, incident/release ID, 안전한 표시 필드가 있다. 수신 시각과 발생 시각을 분리한다. 비밀·원시 stdout/stderr·요청 본문은 넣지 않는다.
- 중복 키는 배포의 경우 배포 ID+환경+결과 종류, probe는 환경+대상+incident ID+전이, AWS는 원본 사건 ARN/ID+상태 갱신 식별자다. Health 페이지·관련 자원 목록 분할과 중복 리전 전달을 수용하고 동일 갱신을 중복 통지하지 않는다.
- 상태는 pending, sending, sent, retry_wait, uncertain, held로 구분한다. 사건 처리 성공과 Slack 접수 성공을 별도로 기록한다. sending에는 만료되는 소유권을 두며 경쟁 실행은 조건부 갱신으로 막는다.
- Slack HTTP 200과 성공 응답을 확인한 경우에만 sent다. sent 상태의 동일 메시지는 재전송하지 않는다. Slack 접수는 사람의 읽음으로 표시하지 않는다.
- 429는 Retry-After 이상 기다린다. 일시 네트워크 오류·5xx는 1분, 5분, 15분, 이후 60분 간격으로 재시도한다. due 작업을 재개하는 스케줄러는 1분마다 돌며 중복 스케줄에도 상태 조건을 확인한다.
- 잘못된 채널·인증·payload 등 영구 오류는 held로 남기고 지속 실패를 기록한다. 설정이 복구되면 해당 건만 다시 예약한다. 실패한 사건을 폐기하거나 실패를 sent로 바꾸지 않는다.
- 중요한 장애 알림에서 원격 접수 여부가 불명확하거나 sending 중 실행이 중단되면 같은 사건 ID로 재전송하며 ‘이전 전송 결과 불명확 · 중복 가능’을 붙인다. 일반 배포 성공·일일 보고의 uncertain은 자동으로 중복 재전송하지 않고 확인 가능한 상태와 명시 재시도 명령을 제공한다. 명확한 실패는 중요도와 무관하게 재시도한다.
- 일반 uncertain/held가 생기면 원문을 재전송하는 대신 개발 채널에 해당 사건 ID와 확인 필요 상태를 한 번 알린다. 운영자는 ID로 Slack 접수 확인 결과를 기록하거나 ‘중복 가능’ 문구를 붙인 명시 재시도를 요청할 수 있다. 60분 이상 해소되지 않은 건은 미해결 전달 상태 목록에 남기고 상태 점검을 실패로 판정한다. 확인 필요 알림 자체가 전송 불능이면 같은 실패 원장에 남긴다.
- 새 전송 경로 활성화 시 기존 배포 Slack 직접 전송은 해당 배포에 대해 대체한다. 한 배포를 구·신 sender가 동시에 전송하지 않는다. 기존 개발 작업 완료용 Stop Slack은 이번 제품 운영 알림과 별개로 유지한다.
- 큐의 보존 기간 만료만으로 사건이 사라지지 않게 영속 상태에서 미전송 건을 재발행한다. 소스 사건·미전송 상태의 자동 삭제/TTL은 이번에 도입하지 않는다. poison message는 분리하고 진단 가능한 실패 건수로 남긴다.
- 전송기 자체나 Slack 전체가 중단된 동안 같은 Slack 경로로 즉시 알린다고 보장하지 않는다. 실패 상태·CloudWatch 상태를 보존하고 경로 복구 후 지연 알림을 전송한다. 다른 외부 통지 채널을 새로 추가하지 않는다.

### 활동 사건·감사 기록의 의미
| 분류 | 보고 원천·보강 | 일일 표시 |
|---|---|---|
| 업로드·등록 | D5 접수 사실을 접수 원천, D8 데이터셋 등록 활동을 등록 원천으로 사용 | upload ID로 묶어 등록이 있으면 등록 1건, 없으면 접수 상태 1건. 같은 업로드를 두 성공 건으로 합산하지 않음 |
| 데이터 변경 | 메타·본체·격자·계보 변경 중 기존 기록 재사용, 없는 변경 감사 보강 | 실제 성공한 변경의 사용자별 요약 |
| 데이터 삭제 | 기존 승인된 운영 삭제 경로에 감사 기록 추가 | 삭제 대상·행위자·시각·삭제 내용, 제품 삭제 API 신설 없음 |
| 프로젝트 생성·삭제 | 생성/삭제 기존 기록을 대조하고 삭제 전 snapshot 보강 | 생성은 요약, 삭제는 건별 상세. 수정·상태·연결 변경은 이번 대상 아님 |
| 다운로드 | 기존 티켓 발급 기록 | ‘다운로드 요청/티켓 발급’ 건수. 바이트 수신 완료로 표현하지 않음 |
| 접근 요청 | 요청자·요청시각 원장 | 사용자별 요청 건수 |
| 접근 승인·거절 | 결정자·결정시각·결과 원장 | 대상·요청자·결정자·시각·결정 내용, 허용 범위·기한 변화 포함 |
| 권한 변경 | 기존 스위치별 append-only 권한 변경 원장 | 변경자·대상자·시각·권한·켬/끔. 여러 스위치는 각각 보존 |

- 한 행위가 여러 기존 원장에 있으면 원천 우선순위와 stable source ID로 한 번만 집계한다. 사용자·시각·대상 문자열이 같다는 이유만으로 서로 다른 실제 행위를 합치지 않는다.
- D2의 권한·접근 원장과 D8 활동·다운로드 원장을 원천으로 재사용하되 현재 상태를 과거 감사로 해석하지 않는다. D2 접근 결정에는 승인 당시 허용 범위·기한·결정 전후 값의 append-only snapshot을, 권한 변경에는 당시 스위치 전후 값을 같은 업무 트랜잭션으로 보존한다. 이후 grant 기한이 바뀌어도 과거 승인 감사는 바뀌지 않는다.
- D3의 미기록 변경·삭제와 D6의 삭제 전 사실은 각 도메인 소유 append-only 감사로 보강한다. 감사 쓰기는 성공한 업무 변경과 같은 DB 트랜잭션이며 rollback이면 둘 다 남지 않는다. Slack 실패는 업무 트랜잭션과 무관하다.
- D5의 접수는 기존 completeUploadTransfer 이후 확정된 upload ID를 사용하며, multipart 진행·클라이언트 업로드 시작만으로 접수 사건을 만들지 않는다. 다른 날짜에 접수와 등록이 생기면 각 날짜의 실제 전이를 표시하되 ‘업로드 작업 수’와 ‘상태 전이 수’를 섞지 않는다.
- 변경 감사는 event ID, lab ID, actor ID, 대상 ID·종류, 발생시각, 행위 종류, 필요한 변경 전/후 표시값을 보존한다. 삭제 감사는 삭제 전 표시 이름과 대상 ID를 저장하고 대상 삭제의 cascade로 없어지지 않게 한다. 기존 자료에 없던 과거 이름·상태를 지어내지 않는다.
- 현행 이름 조회가 실패해도 감사 행은 버리지 않고 ID와 ‘표시 이름 없음’을 사용한다. 기존 홈 활동 API처럼 사라진 대상을 걸러내지 않는다. 자유 입력·긴 설명은 Slack 문법을 escape하고 mention 실행을 막는다.
- 일반 변경 실패·로그인·화면 열람의 전수 감사 수집은 이번 범위가 아니다. 다운로드의 실제 전송 완료 계측과 프로젝트 수정·상태·연결 변경 보고도 신설하지 않는다.
- 최초 활성화 이전에 없던 감사 이력은 복원했다고 주장하지 않는다. 활성화 시 수집 시작 시점을 고정하며 첫날은 ‘수집 시작 이후’임을 명시한다. 완전한 하루 기준 수집이 시작된 뒤부터 정상 일일 보고로 판정한다.

### 연구실 경계·시험 제외·일일 집계
- 전용 읽기 전용 보고 DB role은 NOBYPASSRLS이며 원장·표시 이름·연구실 목록 조회에 필요한 SELECT만 가진다. 쓰기, 전체 DB 읽기, colab_backup 자격 재사용을 금지한다.
- 지연 commit을 놓치지 않도록 보고 대상 원천은 업무 트랜잭션에서 도메인 소유의 내보내기 대기 항목도 함께 기록한다. 불변 감사와 가변 내보내기 접수 상태는 별도 저장한다. 내보내기 작업자는 commit된 미접수 항목을 시간/ID 상한 없이 읽어 원격 사건 원장에 stable source ID로 저장하고 접수 확인 후에만 완료 처리한다.
- 내보내기 상태 갱신은 보고 읽기 role에 추가하지 않는다. 별도 NOBYPASSRLS 내보내기 role에 도메인별 접수 상태 갱신만 허용하고, 업무/감사 행 UPDATE·DELETE는 허용하지 않는다. 연구실별 scope·도메인 Port 경계는 동일하게 적용한다. 이 접수 상태는 append-only 감사 행을 수정하는 우회 경로가 아니다.
- D1의 연구실 루트 목록에서 대상 전체를 열거하고 각 연구실을 별도 트랜잭션의 SET LOCAL scope로 읽는다. 기존 FORCE RLS 정책을 유지한다. 조립층이 전역 raw SQL로 타 도메인 테이블을 join하지 않는다. 원장에 없는 사용자 권한을 보고 API로 노출하지 않는다.
- 배포 manifest에서 environment와 usage(live/rehearsal)를 분리한다. 현재 실제 사용 dev만 활동 보고 대상이고 staging은 rehearsal이다. 이름만 보고 dev를 시험 환경으로 제외하지 않는다.
- 시험 제외는 서버 관리 manifest의 명시적 시험 연구실·계정 ID와 적용 시작 시각을 사용한다. 사용자가 요청 본문으로 시험 표시를 주어 감사에서 빠질 수 없다. manifest의 빈 제외 목록은 명시적 빈 목록이어야 하며, 누락은 준비 실패다. 새로운 실제 연구실은 별도 등록 없이 전체 목록에서 포함된다.
- 08:00 Asia/Seoul 실행일 D의 보고 범위는 [D-1 00:00, D 00:00) Asia/Seoul이다. DB는 UTC로 비교한다. 제목에는 보고 날짜·환경·시간대를 표시한다.
- 집계는 영속 사건 원장의 원천별 시간창 필터와 결정적인 (발생시각, source ID) cursor로 페이지를 끝까지 읽는다. 원천 내보내기 미접수·실패와 연구실 목록을 함께 대조한다. snapshot/cutoff와 읽은 연구실 수·원천 수·행 수·제외 건수를 보고 실행 manifest에 보존한다. 첫 페이지나 상위 N개를 전체로 간주하지 않는다.
- 조회 일부 실패 시 성공 부분과 실패 연구실/원천 수를 구분한 ‘집계 불완전’ 보고를 낸다. retry는 같은 날짜를 보완하며 ‘정정 보고’와 revision을 붙인다. 누락 원천이 남으면 완료나 활동 없음으로 바꾸지 않는다.
- 모든 대상 원천의 성공적인 조회 결과가 0건일 때만 ‘활동 없음’이다. 대상 연구실이 0개이면 ‘대상 연구실 0개’로 별도 표시하고 준비 상태를 검사한다. 소스 미설정·권한 오류·DB 미접속은 0건과 다르다.
- 마지막 성공 날짜만 추적하지 않고 날짜별 실행 상태를 보존한다. 스케줄 중단 후 누락된 날짜를 오래된 순서로 다시 집계한다. 내보내기 접수 시 occurred_at의 KST 날짜에 대해 원격 원장의 report-dirty 표식을 같은 영속 쓰기로 남긴다. 날짜가 이미 보고됐으면 정정 revision을 생성한다. 원천 대기 목록은 발생시각 cursor 뒤만 읽지 않으므로 예전 시각을 가진 늦은 commit도 발견한다. 감사 변경은 새 원천 사건으로 기록하며 이미 보낸 본문은 덮어쓰지 않는다.
- report ID는 실제 환경+KST 날짜, revision은 집계 manifest 변화, 각 전송 part는 report ID+revision+part 번호로 고정한다. 재전송 때 현재 데이터를 임의로 새로 렌더링하여 동일 ID의 본문이 바뀌지 않게 한다.

### 메시지와 채널 경계
- 개발 메시지는 중요도·환경·사건·발생시각·현재 상태·관련 ID를 먼저 보여준다. 원시 로그 대신 실패 단계와 안전한 요약을 싣는다.
- 활동 보고 첫 부분은 날짜·수집 완전성·연구실/사용자/활동 건수와 요약이다. 이후 중요 감사 내역을 시각순으로 싣는다. 보고·감사 상세는 모두 같은 활동 채널이다.
- text 기반 메시지를 보수적으로 3,000자 이하로 분할하고, 모든 part에 날짜·report ID·revision·part/total을 붙인다. 긴 행 자체도 분할하여 뒤를 버리지 않는다. 한 채널에 초당 1건 이하로 전송하고 429 지시를 우선한다. 첫 버전은 Slack thread 조회·삭제·파일 업로드 권한 없이 작동한다.
- 채널별 전송 lease와 순서를 관리하여 여러 작업이 동시에 같은 part를 전송하지 않게 한다. 활동 보고 마지막 part 전송 전 전체 전송 완료로 표시하지 않는다. 부분 전송은 남은 part만 재개한다.
- 두 채널 webhook은 분리된 비밀 참조를 사용한다. 개발 큐가 활동 채널로, 활동 큐가 개발 채널로 직접 전달되는 설정은 준비 실패로 거절한다. 집계 실패를 개발 채널에 알릴 때 사용자 감사 본문을 복사하지 않는다.

### 스키마 · 마이그레이션 · API 계약
- platform 파일 그래프에서 확인한 현재 head는 `0024_s2_grid_convenience`, 그 부모는 `0023_upv_image_grid`다. 이 사양은 head를 변경하지 않았다. 실행 직전 재확인한 단일 head 뒤에 도메인 소유 감사표·필요한 snapshot 열·보고 role grant를 비파괴적으로 추가한다. revision 번호는 실행 계획 착수 시 충돌 없이 발급한다.
- 새로운 감사표에 append-only 보호, lab RLS, 시간+ID 인덱스, 원천 중복 식별 제약을 둔다. 도메인별 내보내기 대기/접수 표와 읽기/내보내기 role도 별도 권한으로 선언한다. 기존 기록은 UPDATE로 새 사실을 지어내지 않는다. 원본 선언 스키마와 적용 DB를 함께 검증한다. ai 체인은 변경하지 않는다.
- HTTP 제품 API는 비파괴·변경 없음이다. 기존 upload pipeline 이벤트를 운영 알림 메시지로 재해석하거나 frozen 계약 필드를 바꾸지 않는다. 운영 사건 입력은 별도의 버전 있는 내부 계약이다.
- AWS 전송 상태는 platform/ai DB와 독립이며 서비스 간 DB 경계를 넓히지 않는다. 자격증명은 런타임 역할·관리 비밀 참조를 사용하고 EC2에 정적 AWS 키를 넣지 않는다. NAT gateway를 추가하지 않는다.

## 시험 결정
- 사용자 확인 대상 시험 경계: **격리 환경에서 실제 배포 진입점·업무 API/기존 운영 명령으로 사건을 만든 뒤, 운영 job을 실행하여 두 가짜 Slack 수신처에 도착한 문면·건수·순서를 확인한다.** DB 내용만 맞거나 formatter만 맞는 것으로 완료 판정하지 않는다. 실제 Slack 전송은 별도 연결 승인 후 검증한다.
- 재사용 seam: 배포 실행기의 execute/sender 주입, 상태 감지기의 probe/webhook 경계, core-api의 HTTP 통합 시험과 PostgreSQL RLS 시험을 재사용한다. 신규 seam은 운영 job의 clock/source reader/queue transport/HTTP sender 경계이며 제품용 공개 API를 만들지 않는다.
