## 1. 목표와 확정 경계

운영자가 백오피스 화면에서 이메일로 식별되는 서비스 계정을 추가하고, 사용자가 전달받은 초기 비밀번호로 로그인한 뒤 자신의 비밀번호로 변경하여 서비스를 사용한다.

**확정된 것**

1. 운영자 계정 직접 추가가 Stage 3 최우선이다. 이메일 주소는 서비스 계정 식별자이며 메일함 생성 요구가 아니다.
2. 운영자가 초기 비밀번호를 전달하고 사용자가 첫 로그인 때 변경한다(2026-09-11 사용자 답).
3. Google 로그인 보류는 유지한다. 기존 로그인·비밀번호 발급 경로 제거 승인은 없다.
4. 생성은 서비스 운영자만 수행하고 기존 연구실 하나와 `교수 | 연구원` 역할 하나를 지정한다.
5. 기존 이메일은 덮어쓰거나 다른 연구실에 연결하지 않고 중복으로 거절한다.
6. 별도 워크트리에서 BO-1의 로컬 구현과 검증까지 승인됐다. 커밋·배포·push는 승인 범위가 아니다.

**구현 계약**

- 첫 로그인에서는 비밀번호 변경을 마치기 전 일반 화면·데이터 API 사용을 허용하지 않는다. 강제 변경 상태를 서버에서 검사하고 브라우저 새로고침·직접 URL/API 호출로 우회할 수 없게 한다.
- 운영자가 초기 비밀번호를 입력하고 별도 채널로 사용자에게 전달한다. 서버는 평문을 응답하거나 재조회하지 않는다.
- 서비스 운영자는 보호된 DB 등록부로 판정한다. 교수나 연구실 설정 권한을 자동으로 서비스 운영자로 올리지 않는다.
- 초기 비밀번호·새 비밀번호는 로그, 분석 이벤트, 오류 응답, 감사 내역에 기록하지 않는다. 감사 내역에는 행위자·대상·결과만 남긴다.
- 입력 오류·중복 이메일·동시 생성 충돌은 계정과 소속이 부분 저장되지 않도록 처리한다. 기존 계정 암호 또는 소속을 자동 덮어쓰지 않는다.

## 2. 확정된 기술 경계

| 결정 | 확정값 | 구현 경계 |
|---|---|---|
| 생성 권한 | 서비스 운영자만 | 보호된 operator 등록부와 좁은 DB 함수가 재검증. 일반 앱 role의 직접 실행과 actor 위조 거부 |
| 첫 소속 | 기존 연구실 하나·기존 역할 하나 | 새 연구실 생성과 역할 체계 개편 없음 |
| 기존 이메일 | 대소문자·앞뒤 공백을 정규화해 중복 거절 | 기존 행을 변경하지 않고 신규 발급만 전역 중복을 막음 |
| 초기 비밀번호 | 운영자가 입력·전달 | 응답·로그·감사 내역에 평문 없음. 재발급은 범위 밖 |
| 첫 로그인 | 변경 전 일반 API 전부 거절 | DB 전용 토큰 종류와 자격 version을 매 요청 대조하고 변경 성공 뒤 새 토큰 발급 |
| 기존 로그인 | 파일 기반 accountName 로그인 유지 | DB가 소유한 로그인 이름의 실패를 파일 발급기로 넘기지 않음 |

전역 unique 제약을 기존 `d1_account.email`에 추가하지 않는다. 과거 연구실별 중복 행을 보존하면서 관리 함수가 신규 발급만 전역 검사하고, 신규 로그인 자격 표의 정규화 이름 unique 제약으로 동시 요청을 막는다. 기존 수동 CLI와 동시 실행하지 않는 운영 절차를 두며 신규 자격이 존재하는 동안 롤백도 additive 표를 보존한다.

## 3. 현행 구현 근거와 설계 과제

| 확인한 실물 | 근거 | 이번 사양에 미치는 영향 |
|---|---|---|
| 계정 이메일 유일성은 연구실 단위 `UNIQUE(lab_id,email)` | `db/platform/schema.sql`의 `d1_account` | 이메일만으로 로그인할 때 기존 중복 이메일의 연구실 선택/계정 식별 정책 필요 |
| 현재 로그인 입력은 `accountName`, 응답은 token/expiresAt | `contracts/seams/fe-core.yaml`의 `SessionCredentials`, `services/core-api/src/colab_core/app/routes/session.py`, `frontend/src/auth/LoginPage.tsx` | 이메일 식별 요구를 단순 화면 문구 교체로 구현하지 않음. 기존 accountName 로그인과의 호환 정책 확정 |
| 자격 JSON을 기동 시 한 번 메모리에 읽음 | `services/core-api/src/colab_core/kernel/credentials.py`, `services/core-api/src/colab_core/app/main.py`의 `CredentialStore.from_file` | 생성 직후 로그인·첫 로그인 암호 변경은 현행 파일 쓰기만으로 해결되지 않음 |
| 자격 파일은 읽기 전용 마운트, 회전은 재기동 절차 | `infra/staging/compose.i2.yml`, `docs/DEPLOY.md`의 자격 파일 회전 | 웹 발급에 매번 서비스 재기동을 요구하는 방식은 채택하지 않는 방향으로 설계 |
| 계정/역할/권한 SQL과 자격 설정 CLI가 분리 | `services/core-api/ops/provision-account.sql`, `services/core-api/ops/set-password.py` | 계정·소속·로그인 자격의 원자 저장 경계를 새로 정해야 함 |
| 기존 구성원 조회·권한 수정만 존재 | `services/core-api/src/colab_core/app/routes/members.py` | 구성원 권한 수정과 신규 서비스 계정 생성은 다른 기능. 현행 교수/위임 관리자 권한을 생성 권한으로 자동 확대하지 않음 |
| 강제 변경 상태·사용자 비밀번호 변경 API/화면 경로 없음 | 위 인증 계약·서버·frontend 조사 | 변경 전 제한 세션/토큰 또는 변경 전용 인증 경로와 우회 거부를 함께 설계 |

자격 저장은 **DB 기반 인증 자격으로 옮기는 방안**을 우선 제안한다. 별도 저장소를 선택한다면 동적 갱신·계정 DB와의 일관성을 입증해야 한다. 기존 파일 기반 계정의 목록·중복 이메일·사용 중 로그인 이름을 비밀값 출력 없이 조사하고, 전환·호환·되돌림을 별도 수용 항목으로 확정한다. 이 초안은 DB 이전이나 기존 자격 삭제를 승인하지 않는다.

구현 착수 전에 닫을 추가 질문은 이메일 식별의 전역 유일성/다중 연구실 처리, 기존 accountName 로그인 유지 방식, 자격 저장 전환 및 rollback이다. 코드 사실로 새 제품 정책을 자동 결정하지 않는다.

## 4. 사용자 흐름과 수용 기준 제안

| 흐름 | 기대 결과 | 증명 방법 |
|---|---|---|
| 운영자 로그인 → 계정 추가 화면 | 허용된 운영자만 화면과 생성 API 사용 | 일반 사용자·다른 연구실 관리자·미인증 요청의 거부 시험 |
| 이메일·소속·역할 선택 → 생성 | 계정 1개 및 승인된 소속만 저장, 초기 비밀번호 전달 가능 | 저장·재조회·새로고침 및 동시 중복 요청 검증 |
| 잘못된 이메일/없는 연구실/허용 안 된 역할 | 안내 후 저장 없음 | 음성 시험과 저장 전후 건수 대조 |
| 기존 이메일 재입력 | 결정된 중복 정책, 기존 암호·소속 불변 | 기존 계정 로그인 및 소속 재조회 |
| 초기 비밀번호 첫 로그인 | 비밀번호 변경으로 이동, 일반 기능 사용 차단 | 직접 URL/API·새로고침·재로그인 우회 음성 시험 |
| 새 비밀번호 저장 | 변경 의무 해제, 새 비밀번호 로그인 성공·초기 비밀번호 실패 | 로그아웃·재로그인, 실패 재시도 및 동시 변경 검증 |
| 연구실 경계 | 지정 연구실의 허용된 역할로만 조회·쓰기 | cross-tenant 음성 시험, 기존 역할 권한 회귀 |
| 기존 사용자 로그인 | 기존 사용자에게 신규 계정 변경 의무를 소급하지 않음 | 기존 로그인·세션·속도 제한 회귀 |
| 발급/변경 실패 | 중간 상태나 비밀번호 노출 없음 | 트랜잭션 실패·응답/로그 점검 |

위 표는 **BO-1 완료 정의 제안**이다. 현재 대장의 `완료 정의 미작성`을 대체하지 않는다. 구현 수용에는 계약·DB 양 체인 정합·기능 시험·실제 사용자 여정·현재 배포 규칙에 따른 dev 증거가 필요하며, 이번 문서 검증은 제품 검증을 대신하지 않는다.

## 6. Stage 1·2 잔여와 릴리스 경계

[기존 배포 보고서](../../reports/stage12-tl2-deploy/release.md)의 U-2·IS4·I3·I4·TL-2는 **기록상 잔여 실행 5건**이다. 이번 작업에서 운영 실측하지 않았고, 최신 환경에 그대로 남았는지는 각 항목 실행 직전 다시 확인한다.

이 5건은 Stage 3 **계획 작성의 차단 조건이 아니다**. 다만 운영 적용·정기 실행·알림 검증을 건너뛴 채 Stage 1·2 전체 완료로 선언하지 않는다. Stage 3 릴리스 시 선택된 변경과의 의존성, 현재 배포 환경과 main 기준, 보존·복구·감시 증거를 다시 대조한다. 단계 번호만으로 5건을 모두 계정 기능의 기술적 선행으로 추가하지 않는다.

## 7. 편의 기능 — 후일 묶음

메일 초대 자동화, 대량 계정 등록, 계정 템플릿, 소속 추천은 이번 요청에 포함되지 않는다. 구현 일정에 넣지 않는다. 새 연구실 생성·역할 체계 개편·Google 로그인 재개 역시 별도 요구·승인 없이 계정 발급에 끼워 넣지 않는다.
