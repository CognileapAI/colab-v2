# Stage 3 계획 초안 — 운영자 계정 발급 우선

> **For agentic workers:** 2026-09-11 사용자가 BO-1 정책과 로컬 구현을 승인했다. 계약·실패 시험·구현·게이트 순서를 지키며 작업 사본 하나에는 쓰기 주체 하나를 유지한다.

**Goal:** 운영자가 이메일 식별 계정을 발급하고 첫 로그인에서 비밀번호를 변경하는 흐름을 Stage 3 첫 구현 단위로 준비한다.

**Architecture:** 기존 인증·연구실 경계 위에 운영자 발급 및 초기 비밀번호 변경 의무를 연결하는 방향이다. 서비스 운영자 판정·발급 계약·상태 저장 구조는 사양 리뷰로 확정하며, 기존 로그인 경로 제거를 전제하지 않는다.

**Tech Stack:** 현재 저장소의 core-api·frontend·contracts·DB 체인을 대상으로 한다. 구현 단계의 라이브러리·API 추가 결정은 이 문서에서 하지 않는다.

**Spec:** [계정 발급 사양 초안](../specs/stage3-account-onboarding.md)

## Global Constraints

- 첫 구현 우선순위는 BO-1이며 전체 16항목은 범위 지도다.
- 상태 정본은 `dev-package/work-items.yaml`. 이번 문서 작업은 대장 상태·완료 정의를 수정하지 않는다.
- 운영자 초기 비밀번호 전달 → 사용자 첫 로그인 변경은 사용자 확정값이다.
- 생성 권한·소속·기존 계정 처리는 사양의 승인/제안 구분을 따른다.
- 연구실 경계·D10→D4 쓰기 금지·두 DB 마이그레이션 체인·생성물 손수정 금지를 유지한다.
- 계약 동결 → 외부 동작 실패 시험 → 최소 구현 → 관련 게이트 → 실제 사용자 여정 순서를 유지한다.
- 비밀번호를 로그·문서·감사 이벤트에 저장하지 않는다.
- 커밋·배포·push·운영 데이터 변경은 이번 계획 작성 범위에 없다.

## 3. 변경 후보와 책임 경계

현행 경로의 책임을 나눈 표다. 새 파일·함수·계약 명세는 승인 후 실행계획에서 확정한다.

| 책임 | 현행 파일/검증 자산 | 작업 |
|---|---|---|
| 인증·운영자 생성 계약 | `contracts/seams/fe-core.yaml` | 이메일 식별 호환·생성·암호변경·제한 상태 계약; 생성물은 생성기로 갱신 |
| 자격 저장·서버 인증 | `services/core-api/src/colab_core/kernel/credentials.py`, `services/core-api/src/colab_core/app/routes/session.py`, `services/core-api/src/colab_core/app/main.py` | 파일→동적 자격 전환 방안·기존 사용자 유지·변경 전 API 거부 |
| 계정·소속·권한 저장 | `db/platform/schema.sql`, `services/core-api/src/colab_core/app/routes/members.py` | 기존 이메일 연구실내 유일성 대조·계정/역할/자격 원자성·생성 권한 |
| 기존 운영 발급 경로 | `services/core-api/ops/provision-account.sql`, `services/core-api/ops/set-password.py` | 새 경로와 호환/전환 검토; 기존 도구 제거 자동 승인 없음 |
| 첫 로그인 화면 | `frontend/src/auth/LoginPage.tsx` | 초기 로그인 이후 변경 진입, 완료 전 일반 화면 차단 |
| 기존 회귀 자산 | `services/core-api/tests/test_password_login.py`, `services/core-api/tests/test_session_login.py`, `services/core-api/tests/test_lab_members.py`, `services/core-api/tests/test_permission_defaults.py`, `services/core-api/tests/test_login_limiter_buckets.py`, `frontend/test/auth.test.tsx`, `frontend/test/members.test.tsx` | 기존 로그인·권한·소속 회귀 및 새 음성 시험 |

DB 자격 전환을 우선 제안하되 미승인이다. 기존 계정 이메일 중복·accountName 호환·세션 만료·전환 rollback을 A에서 고정하고 B에 포함한다. 운영 비밀값은 조사 출력에 싣지 않는다.

## 4. 첫 구현 묶음의 순서 제안

아래는 승인된 BO-1 로컬 구현 작업 분할이다. dev 배포는 현재 승인 범위가 아니다. 정확한 함수·요청/응답·새 파일명은 현행 코드 조사와 사양 결정으로 정하며, 존재하지 않는 API를 확정 코드처럼 제시하지 않는다.

### Task A. 발급 권한과 계정 상태 계약 확정

**입력:** 사용자 결정, 현행 인증 및 소속/역할 모델, BO-1 선행 PA의 대장·실물.
**산출:** 서비스 운영자 판정, 입력 정규화·중복 정책, 계정 생성 원자성, 첫 로그인 변경 의무, 초기 암호 노출·만료·재발급·세션 처리 계약.

- [x] 현행 서비스 운영자 권한이 존재하는지 확인하고 연구실 관리자 권한과 구분한다.
- [x] 계정/소속 선택과 중복 이메일 처리 정책을 확정한다.
- [x] 신규 계정만 비밀번호 변경 의무를 갖는 상태 전이와 우회 차단 API 범위를 확정한다.
- [x] 기존 accountName 로그인·연구실별 중복 이메일·파일 자격의 전환/rollback과 DB 자격 저장 제안을 확정한다.
- [x] 계약 변경의 동결 해제 필요 여부를 판정하고 해당되는 승인 범위로 계약을 고정한다.
- [x] 아래 Task B·C에 사용할 실제 테스트 코드와 실행 명령을 실행계획에 추가한다.

**수용:** 입력·출력·실패 응답·역할 매트릭스·마이그레이션 필요 여부가 확정되어 후속 작업자가 정책을 새로 선택하지 않는다.

### Task B. 운영자 발급을 끝까지 저장

**입력:** A의 동결 계약과 권한 매트릭스.
**산출:** 허용된 운영자가 계정 1개를 추가하고 발급값을 전달할 수 있는 서버·화면 경로.

- [x] 일반 사용자/다른 연구실 관리자/미인증 생성 거부, 중복/동시 요청, 없는 연구실/허용 안 된 역할, 부분 저장 부재의 실패 시험을 작성하고 RED를 확인한다.
- [x] 기존 도메인 경계를 유지해 생성·소속 부여·초기 자격 저장을 구현한다.
- [x] 운영자 화면에서 입력→생성→결과 재조회와 오류 안내를 연결한다.
- [x] 평문 비밀번호 재조회·로그 노출 부재와 기존 계정 암호·소속 불변을 확인한다.
- [x] `contract-lint`·`contract-breaking`·`generated-up-to-date`·`frontend-typecheck`·`frontend-test`·`service-tests-core-api`를 관련 게이트 후보로 대조하고 확정한 게이트를 실행한다. 실제 계수·준비 실패를 기록한다.

**수용:** spec §4 발급·입력 오류·중복·권한·실패 행 충족. 암호 변경 전 제품 기능 접근은 C까지 허용하지 않는다.

### Task C. 첫 로그인 비밀번호 변경

**입력:** B의 신규 계정, A의 변경 의무 상태·세션 계약.
**산출:** 초기 로그인 → 변경 화면 → 새 비밀번호 로그인으로 이어지는 사용자 여정.

- [x] 변경 전 직접 URL/API·새로고침·재로그인 우회 거부와 기존 사용자 회귀의 실패 시험을 작성하고 RED를 확인한다.
- [x] 서버에서 변경 의무를 강제하고 새 비밀번호 저장 성공 뒤 상태를 바꾼다.
- [x] 변경 실패·동시 제출에서 중간 상태가 남지 않도록 확정 정책을 구현한다.
- [x] 초기 암호 로그인 실패·새 암호 로그인 성공 및 연구실 경계 지속성을 확인한다.
- [x] 기존 로그인·속도 제한·세션·역할 회귀 시험을 실행한다.

**수용:** spec §4 첫 로그인·새 비밀번호·연구실 경계·기존 로그인 행 충족.

### Task D. 통합 사용자 여정과 릴리스 수용

**입력:** B·C 같은 변경 트리의 통과 증거와 승인된 최종 완료 정의.
**산출:** 운영자 발급→전달→첫 로그인→변경→재로그인→허용 연구실 기능 사용의 실제 증거.

- [x] 테스트 URL·격리 계정/연구실·대상 SHA·정리 범위를 고정한다.
- [x] agent-browser로 입력·저장·새로고침·로그아웃/로그인·권한 거부를 검증한다. 화면 사진만으로 성공 처리하지 않는다.
- [x] DB 변경 시 `migration-single-head`·`schema-diff`·`migration-drift`·`rls-coverage`·`rls-effect`를 확정 실행 목록에 포함하고 양 체인 선언·실제 upgrade/downgrade를 확인한다.
- [x] 변경에 필요한 전체 검증과 advisor 수용 검토를 완료한다.
- [ ] main 기준·배포 승인 범위·Stage 1·2 잔여와의 실제 의존을 재확인하고 현행 dev 완료 규칙을 적용한다(로컬 완료, dev 배포 미실행).
- [ ] dev 배포 증거까지 충족 시에만 BO-1 상태를 done으로 갱신한다(완료 정의는 확정, 상태 open 유지).

**수용:** 단계 완료와 제품 전체 완료를 구분하고 미실행·준비 실패를 통과로 계산하지 않는다.

## 5. 후속 묶음의 준비 순서

1. 검색: T-1 온톨로지 → K4 서비스/P4 화면의 사양·평가셋 조율 → G1b 최신성 대조. K4→P4는 새 대장 간선으로 추가하지 않는다.
2. 계보 보조: K3 제안 → K5 원장. LV-4는 P2 선행·저장 정책 확정 후 독립 계획 가능.
3. 가공: DP-1 독립 사양 → LV-3 표식. 새 데이터셋을 만드는 기능이며 미리보기와 구분한다.
4. 보존: C1 확인 → C2/C3/C4 → C3·C4 집계, C4 → R2. 기존 코드 재사용이나 파일 이동을 자동 승인하지 않는다.

BO-1 이후 제품 순서는 미확정이다. 완료 정의 없는 보존·가공 항목은 정의와 범위를 먼저 만든다. 편의 기능은 spec §7에 모으고 일정에 넣지 않는다.
