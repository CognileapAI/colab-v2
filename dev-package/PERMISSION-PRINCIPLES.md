# PERMISSION-PRINCIPLES.md — E-01 권한 **원칙** (선행분)

> WU-G3 산출물. **원칙만 담는다.** 어느 화면 어느 버튼이 누구에게 보이는가는 여기 없다 —
> 그건 후행 WU **P8**(E-01 화면별 적용 지점 표)과 **G4**의 몫이다. 정본도 같은 분리를 쓴다
> (`Policy_역할과_권한` §0 — 가. 원칙 / 나. 화면별 적용 지점 표).
>
> 정본 판본: `Policy_역할과_권한` **v1.3** · `DataModel_공통_기반` v1.8 · `Policy_공통_기반` v1.4 · `Policy_승인_처리`.
> 값이 어긋나면 **정본이 이긴다.** 이 문서는 정본을 코드 관점으로 옮겨 적은 것이지 새 정책이 아니다.

---

## 1. 축의 분리

**P-1. 역할과 권한은 서로 다른 축이다.** 역할이 기본을 정하고, 권한은 사람별 스위치다. 둘을 한 값으로 합치지 않는다.
　근거: `Policy_역할과_권한` §1.3-1, §2

**P-2. 역할은 두 층뿐이다 — 교수 / 연구원.** 시니어·주니어 같은 계정 등급을 두지 않는다. 등급 대신 위임 가능한 권한으로 푼다.
　근거: `Policy_역할과_권한` §2

**P-3. 권한 스위치는 정확히 네 개다** — `업로드·편집` · `프로젝트 생성` · `승인 위임` · `연구실 설정`. 다섯 번째를 만들지 않는다. 연구실 일괄 설정·프로젝트별 권한은 v2 범위 밖이다.
　근거: `Policy_역할과_권한` §2, §8 · `DataModel_공통_기반` §3(구성원)

**P-4. 기본값은 스위치 성격을 따른다.** `업로드·편집`·`프로젝트 생성`은 **기본 켜짐**(필요한 사람만 막는다), 위임 성격인 `승인 위임`·`연구실 설정`은 **기본 꺼짐**(맡길 사람만 켠다).
　근거: `Policy_역할과_권한` §1.3-2, §2

**P-5. 교수는 네 스위치가 항상 켜진 것으로 취급한다.** 교수 행은 고정이며 끌 수 없다. 교수 전용은 **Verified 체크 하나뿐**이고, 이것만은 위임되지 않는다.
　근거: `Policy_역할과_권한` §2 표, §3, §6, §8

**P-6. 판정은 언제나 스위치 기준으로 적는다.** "연구원이니까 업로드할 수 있다"처럼 역할로 권한을 단정하는 코드·화면·문서를 만들지 않는다. 항상 "`업로드·편집`이 켜진 사람".
　근거: `Policy_역할과_권한` §2 주의

## 2. 행동 ↔ 조건 (정본 표 전사 — 이 표에 없는 행동은 먼저 정본에 추가한다)

| 행동 | 연구원 | 교수 |
|---|---|---|
| 검색 · 조회 · 계보 보기 · 시각화 보기 | 항상 | 항상 |
| 업로드 · 시각화 편집 · 계보 확정 | `업로드·편집` | 항상 |
| 프로젝트 생성 · 관리 | `프로젝트 생성` | 항상 |
| 접근 요청 승인 / 거절 | `승인 위임` | 항상 |
| Verified 체크 | 불가 | 항상 |
| 연구실 정보 편집 · 구성원 권한 설정 | `연구실 설정` | 항상 |

**P-7. 이 표가 권한 판정의 유일한 원천이다.** 화면이 조건을 임의로 정하지 않는다. 새 행동이 생기면 **정본에 먼저 추가한 뒤** 화면에 반영한다 — 역순 금지.
　근거: `Policy_역할과_권한` §2 표, §7

**P-8. 같은 사람·같은 기능은 모든 화면에서 같은 결과다.** 화면별 편차를 허용하지 않는다.
　근거: `Policy_역할과_권한` §7

## 3. 경계 (연구실 = 테넌트)

**P-9. 연구실이 모든 것의 경계다.** 검색·카탈로그·계보·프로젝트가 전부 자기 연구실 안으로 잘린다. 다른 연구실 데이터는 **어떤 화면에도 나타나지 않는다.** 연구실 간 공유는 v2 범위 밖.
　근거: `DataModel_공통_기반` §2(연구실 경계) · `planning/README.md` §4(연구실 밖 검색 = 백로그)

**P-10. 경계는 권한보다 바깥이다.** 스위치가 다 켜진 교수라도 남의 연구실은 보지 못한다. 권한 판정 이전에 경계가 먼저 잘린다.
　근거: `DataModel_공통_기반` §2 — 경계는 스위치 표(§3)와 별개 축

## 4. 기본 거부와 이중 시행

**P-11. 화면에서 숨긴 것은 서버에서도 같은 기준으로 막는다.** 주소를 직접 치거나 화면 밖 경로로 들어와도 결과가 같아야 한다. 화면 숨김은 UX이지 보안이 아니다.
　근거: `Policy_역할과_권한` §1.3-6, §4(공통 행)

**P-12. 권한이 없어 못 하는 기능은 화면에서 숨긴다.** 비활성 버튼·경고 토스트로 남기지 않는다 — 눌러도 할 일이 없고 요청 경로도 없어, 보여 주면 사용자가 자기 실수를 의심한다.
　근거: `Policy_역할과_권한` §1.3-4, §4

**P-13. 잠긴 데이터는 숨기지 않는다.** 이름·요약까지는 보이고, **그 자리가 `접근 요청` 버튼이 된다.** 같이 숨기면 접근 요청 흐름 자체가 사라진다.
　근거: `Policy_역할과_권한` §1.3-5, §4

**P-14. 두 축은 서로 다른 처리다** — "권한 없음 → 숨김" vs "데이터 잠김 → 노출 + 요청 자리". 한 메커니즘으로 합치지 않는다.
　근거: `Policy_역할과_권한` §4 표

**P-15. 잠긴 데이터가 화면마다 어디까지 보이는가는 이 문서가 정하지 않는다.** 값의 정본은 승인 처리(E-06) 적용 지점 표다. 여기서는 "숨기지 않는다"는 원칙까지만 고정한다.
　근거: `Policy_역할과_권한` §4 말미 · 변경 이력 v1.2 · `Policy_승인_처리` §8

**P-16. 권한 훅은 최소 단위에 건다.** 컨테이너에 걸어 하위 전부를 지우지 않는다. 할 일 함이 선례다 — 함 자체는 전원에게 보이고 그룹마다 조건이 다르다(계보 확인=전원 / Verified 검토=교수 / 받은 접근 요청=교수·`승인 위임`).
　근거: `Policy_역할과_권한` §6.1 · `Policy_승인_처리` §3, §8(S-01)

## 5. 권한 값의 원천과 변경

**P-17. 역할 값은 제품 밖에서 들어오고 제품 안에서 바꿀 수 없다.** v2 1차는 개발자가 계정에 심어 제공한다. 로그인·초대·프로필·역할 지정 화면을 두지 않는다(P1 보류).
　근거: `Policy_역할과_권한` §3 · `planning/README.md` §4

**P-18. 권한 스위치를 고치는 자리는 `연구실 설정 > 구성원 · 권한` **한 곳**이다.** 구성원=행, 권한 4종=열의 격자 표에 칸마다 체크박스.
　근거: `Policy_역할과_권한` §3 · `Policy_공통_기반` §2(GNB `연구실 설정`)

**P-19. 권한은 실시간 저장이 아니다.** `권한 편집 → 체크 → 저장 → 확인 모달` 세 단으로 끊는다. 권한은 켜는 순간 남의 계정에 힘이 생기므로 되돌릴 지점이 필요하다.
　근거: `Policy_역할과_권한` §3

**P-20. 편집 중에는 토스트를 띄우지 않고 바뀐 칸에 표식만 남긴다.** 확인 모달은 변경 내역을 다시 나열하지 않고, 모달의 `취소`는 **편집 모드를 유지한다**(저장만 물린 것).
　근거: `Policy_역할과_권한` §3 표

**P-33. 권한 변경은 이력에 남는다 — append-only, 스위치 하나당 한 줄.** 열 = 언제 / 누가(저장한 사람) / 대상(권한이 바뀐 구성원) / 무엇(스위치 4종 중 하나) / 어떻게(켬·끔). 확인 모달 한 번에 세 칸이 바뀌면 **세 줄**이 남는다. 수정·삭제 경로를 만들지 않는다. **v2 에 조회 화면은 두지 않는다.**
　근거: `PLAN-SoT §9-㉘`. 정본에 항목이 없다(`DataModel_공통_기반`) — 기록은 소급이 불가능하므로 P0 에서 자리를 만든다

## 6. 위임

**P-21. 두 위임(`승인 위임` · `연구실 설정`)은 서로 독립이다.** 한쪽만 켤 수 있고, 한쪽이 다른 쪽을 함의하지 않는다.
　근거: `Policy_역할과_권한` §6

**P-22. `승인 위임`의 범위는 접근 요청뿐이다.** Verified는 위임되지 않는다. `연구실 설정`의 범위는 연구실 정보 + 구성원 권한이다.
　근거: `Policy_역할과_권한` §6, §8 · `Policy_승인_처리` §2 표(처리하는 사람)

**P-23. 사람을 표기할 때 역할과 받은 위임을 함께 적는다.** 둘 다 받은 연구원은 `연구원 · 승인·설정 위임`. 역할만 적으면 같은 연구원인데 왜 이 사람에게만 버튼이 보이는지 설명되지 않는다.
　근거: `Policy_역할과_권한` §6

**P-31. 위임은 재위임되지 않는다.** `연구실 설정` 위임자는 격자 표에서 **`업로드·편집`·`프로젝트 생성` 두 열만** 편집한다. `승인 위임`·`연구실 설정` 두 열은 **교수만** 편집한다(교수 행 고정은 P-5 그대로). 그 두 열은 위임자에게 **값은 보이되 편집 불가**로 표시한다 — 열을 지우면 표 구조가 깨져 무엇을 못 만지는지조차 안 보이므로 여기서는 `P-12`(숨김)를 적용하지 않는다.
　근거: `PLAN-SoT §9-㉙`. 정본은 **교수 행 고정**까지만 닫았다(`Policy_역할과_권한` §3) — 이 원칙은 그 공백을 메운 레포 결정이다

## 7. 접근 상태와 승인 흐름 (원칙 부분만)

**P-24. 데이터셋의 접근 상태는 `열림 / 잠김` 두 값이다.** 잠김이면 **허용자 목록**을 함께 두고, 목록의 각 줄에 만료일을 둔다.
　근거: `DataModel_공통_기반` §4.1

**P-32. 접근 상태 기본값은 `열림` 이고, 연구실 `데이터 공개 범위` 의 값 집합도 `열림 / 잠김` 2값이다.** 데이터셋과 같은 값 집합이라 `P-27` 의 덮어쓰기가 대입 한 번으로 끝난다 — 매핑 테이블을 만들지 않는다. 3값 이상을 두지 않는 이유는 v2 에 그것을 쓸 화면이 없어서다.
　근거: `PLAN-SoT §9-㉗`. 정본은 `[가정] 기본은 열림`(`DataModel_공통_기반` §4.1)까지만 — 가정을 값으로 승격한 것이다

**P-25. 승인의 단위는 데이터 한 건, 유효기간은 6개월이다.** 만료되면 허용 목록에서 빠지고 다시 요청한다. 사람 단위·연구실 단위 일괄 승인은 없다.
　근거: `Policy_승인_처리` §3-6, §7.2 · `DataModel_공통_기반` §4.1, §8

**P-26. 거절에는 사유가 필수이고(1~300자), 사유는 요청자에게 그대로 전달된다.**
　근거: `Policy_승인_처리` §3-7, §6

**P-27. 데이터셋 단위 공개 범위가 연구실 기본값을 이긴다.** 연구실 정보의 `데이터 공개 범위`는 **기본값 한 값**이고, 데이터셋이 따로 정했으면 그쪽이 우선.
　근거: `DataModel_공통_기반` §2(데이터 공개 범위), §4.1

**P-28. Verified는 권한 축이 아니라 품질 보증 표시다.** 접근을 열거나 막지 않는다. 승인은 교수만, 취소도 교수가 직접 시작한다(파급 안내 후 허용).
　근거: `Policy_승인_처리` §2 표, §3-5, §3-9

## 8. 소유자

**P-29. 모든 데이터에 소유자가 반드시 있다.** 빈 값을 허용하지 않는다.
　근거: `Policy_역할과_권한` §1.3-7, §5

**P-30. `소유자`와 `올린 사람`은 별개 기록이다.** 소유자는 승계로 바뀔 수 있고, 올린 사람은 바뀌지 않는다. 승계 화면이 없어 지금은 두 값이 늘 같지만, **자리는 지금 나눠 둔다** — P1에서 승계가 붙을 때 소급하지 않기 위해서다.
　근거: `Policy_역할과_권한` §5

## 9. 시행 위치 — RLS vs 애플리케이션

정본은 **"화면에서 숨기더라도 서버에서 같은 기준으로 막는다"**(P-11)까지만 말한다. 그 아래 층(무엇을 DB RLS로, 무엇을 애플리케이션으로 막는가)은 **기획 정본에 없는 구현 결정**이다. 아래는 이 레포의 규칙에서 오는 것이지 정본에서 오는 것이 아니다.

**P-34. 잠금의 시행은 두 층으로 쪼갠다.** RLS 는 **행을 사라지게** 하는 도구라, 잠김을 통째로 얹으면 `P-13`(잠긴 것도 이름·요약까지 보인다)이 깨지고 **E-06 승인 흐름 자체가 죽는다** — 없는 데이터는 요청할 수 없다.

| 대상 | 시행 | 근거 |
|---|---|---|
| 연구실 경계 (행의 존재 여부) | **RLS** | `CLAUDE.md §3-5` · P-9·P-10 |
| 데이터셋 메타 (이름·요약) | **필터 없음** | P-13 |
| **파일 본체** (다운로드·원본·시각화 소스) | **RLS** — 허용자 목록 + 만료일 기준, 본체 테이블에 별도 정책 | 진짜 지켜야 할 것은 페이로드다. 애플리케이션 버그로 경로가 새도 DB 가 거부한다 → P-11 을 구조로 만든 것 |
| 권한 스위치 4종 판정 | **애플리케이션** | 행 필터가 아니라 동사 판정이다 |

　근거: `PLAN-SoT §9-㉖`. 정본은 "서버에서 같은 기준으로 막는다"(P-11)까지만 말한다 — 그 아래 층은 레포 결정이다

**D3 에 딸리는 게이트 2종** — ① 허용자 아님·만료됨 두 경우 본체 조회가 **DB 층에서 0행**인 음성 테스트 ② 잠긴 데이터셋의 **메타는 반드시 조회되는** 양성 테스트(RLS 를 과하게 걸어 `P-13` 을 깨는 회귀 방지). 둘 다 red fixture 로 fail-closed 증명.

## 10. [Ted 판단 필요] — 정본이 말하지 않는 것
