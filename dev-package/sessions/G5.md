## 2. 대조 상대 — 왜 v1 스키마인가

**v2에는 스키마가 없다.** `db/platform` · `db/ai` 는 README뿐이고 `contracts/schemas/common.json` 하나가 전부다.
그래서 `WORK-UNITS §5` 의 "기존 스키마"는 v2를 가리킬 수 없다.

대조 상대는 **v1(Launch)의 실제 스키마**다.

```
10 CoLAB-Launch/colab-backend-platform/db/schema.sql
10 CoLAB-Launch/colab-backend-platform/migrations/versions/0001~0007
```

**이유.** G5가 지목한 5개 항목 — 파일 1:N · 다중 부모 계보 · 프로젝트 N:N · 계보 상태 4값 · 레코드 시점 3종 — 은
전부 260808→260818에서 **뒤집힌** 것들이다. v1 스키마는 그 낡은 가정이 코드로 굳어 있는 **유일한 구체물**이고,
"무엇을 물려받으면 안 되는가"는 그것과 나란히 놓아야만 기계적으로 말할 수 있다.

> **코드를 가져오지 않는다.** v1은 읽기 전용 참조다 (`PLAN-SoT §6`). 여기서 나오는 것은 *지식*이지 코드가 아니다.

## 3. 범위

### 건드리는 것

| 대상 | 내용 |
|---|---|
| **DataModel v1.8** | 저장 형태 전량을 v2 스키마 설계 기준으로 옮긴다 — 연구실 · 계정 · 데이터셋 · 파일 · 계보 관계 · 프로젝트 · 활동 기록 · 다운로드 이력 |
| **v1 스키마** | 테이블·컬럼·FK·제약·시점 컬럼·테넌시 컬럼을 읽어 v1.8과 대조한다 |
| **도메인 배정** | 각 기록이 D1~D8 중 어디 소유인지 명시 (`DOMAINS.md §6` 기준) |

### 건드리지 않는 것

- **DDL·마이그레이션 작성** — 그건 P0이다. G5는 **표까지**다
- **OpenAPI·JSON-Schema 저작** — D2다. `common.json` 도 손대지 않는다
- **화면 규칙** — Policy v1.4는 화면 틀·이동·색상이라 저장 형태와 겹치지 않는다. 참조만 건다
- **D9·D10 (온톨로지·AI)** — G8·K1 소관이고 마이그레이션 체인이 분리된다

## 7. 함정 — v1에서 같은 자리에 있었던 실패

| 함정 | 무슨 일이 있었나 | G5에서 막는 법 |
|---|---|---|
| **ID 타입 드리프트** | `users.id`를 String(20/30/36)으로 제각각 선언 (`DOMAINS.md §143`) | 기준표에 ID 타입을 **한 곳**으로 적고, 정본은 `common.json`뿐임을 명시 |
| **계보를 노드에 붙임** | 가공 방식이 데이터셋에 붙으면 부모가 여럿일 때 어느 부모의 가공인지 말할 수 없다 | v1.8 §4.2대로 **관계에 부착**임을 판정에 박는다 |
| **계보 상태를 저장** | 저장하면 파일이 바뀌어도 안 따라간다 | **파생 계산**으로 못박는다 (v1.8 §4.1) |
| **파일 1:1 전제** | 포맷·용량이 단수 컬럼이면 조각 96건짜리 데이터셋이 안 들어간다 | 1:N + 합치는 규칙(§4.3)을 기준표에 옮긴다 |
| **스코프 컬럼 누락** | 한 줄 누락으로 타 연구실 노출 | 기준표의 **모든 행**에 테넌시 열을 두고 빈칸을 남기지 않는다 |
| 파일에 계보를 둠 | 계보가 데이터셋 층·파일 층으로 갈라져 판정 불가 | **파일에는 계보 없음**을 명시 (§4.3) |
