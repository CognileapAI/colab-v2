# WU-IS3 — staging 백업 체계

> **상태: 🟧 기구·증명 완료 · 대상 미연결.** 백업 스크립트·스케줄·보존·fail-closed 증명·
> 백업→파괴→복원 왕복 실증까지 전부 끝났으나, **staging 에 백업할 데이터 저장소가 아직 없다**
> (`infra/staging/README.md` — nginx + cloudflared 뿐). 실대상은 **I2 walking skeleton** 과 함께 온다.
> 그때 붙이는 일은 **설정 한 줄**이지 다시 쓰는 일이 아니다(§2). "나중에" 로 남기지 않기 위해
> 붙이는 절차를 §2 에 명령 단위로 적어 뒀다.
>
> 확인 시점 `www.colab-hydro.com/healthz` = **200** (작업 전·후 동일). 살아 있는 staging 컨테이너는
> 건드리지 않았다.

---

## 1. 만든 것

전부 `infra/staging/backup/` 아래다. IS1·IS2 가 세운 "인프라는 레포의 산출" 관행을 그대로 따른다.

| 파일 | 하는 일 |
|---|---|
| `backup.sh` | 1회 백업. 임시파일 → `PIPESTATUS` 확인 → **검사 통과분만** 최종본. 보존 정리 포함 |
| `verify-artifact.sh` | 산출물 검사 C1~C6. **이 WU 의 본체** |
| `verify-restore.sh` | 복원 **결과** 검사 — 테이블 수 · 테이블별 행 수 · 총 행 수 |
| `roundtrip.sh` | 백업→파괴→복원 왕복 실증(일회용 리허설 인스턴스) |
| `selftest.sh` | fixture 10건이 전부 RED 임을 강제. 하나라도 GREEN 이면 셀프테스트가 실패한다 |
| `latest-check.sh` | 최신 산출물 재검사. **산출물이 없는 것도 실패**다 |
| `schedule.crontab` · `install-schedule.sh` | 스케줄 선언 + 병합 설치. 경로를 문서에 박지 않고 실행 시점에 만든다 |
| `config.example.env` | 설정 예시(비밀 없음). 실값은 홈의 `0600` 파일 |
| `seed.sql` · `count-query.sql` · `content-digest.sql` · `expected-counts.tsv` | 리허설 자재 |

### 설계가 PoC 사건의 세 원인을 그대로 뒤집는다

`DEPLOY-CURRENT.md §8` 이 원인을 셋으로 특정해 놨다. 각각에 구조를 하나씩 대응시켰다.

| 사건의 원인 | 여기서의 대응 |
|---|---|
| ① 크론이 **죽은 트리**를 가리켰다 | 대상을 설정으로 명시. 대상이 없으면 **`exit 78`** — 조용한 성공이 없다. 크론 줄은 `install-schedule.sh` 가 레포 실위치에서 생성한다 |
| ② 리다이렉션이 `pg_dump` 보다 **먼저 파일을 만들었다** | 임시파일(`.inflight-*`)에 받고 `PIPESTATUS[0]` 확인. 실패 시 최종 경로에 **아무것도 남기지 않고** trap 으로 임시파일도 지운다 |
| ③ 가드가 **크기·`gzip -t` 만** 봤다 | `verify-artifact.sh` 가 해제 후 바이트 · `CREATE TABLE` 수 · **데이터 행 수** · **신선도**까지 본다 |

### 보관처 · 비밀 취급

- 산출물은 **레포 밖**, 홈 아래 `colab-v2-backups/staging/`. 백업을 레포에 쓰면 git 이 데이터 저장소가 된다.
- 설정 실값은 홈의 `.colab-v2-staging-backup.env`(`0600`) — IS2 의 `.colab-v2-staging.env` 와 같은 관행이다.
  레포 파일 어디에도 비밀·절대경로가 없다.

## 2. 백업 대상 — 지금 걸린 것 / I2 뒤에 붙는 것

| 대상 | 상태 | 근거 |
|---|---|---|
| **platform postgres (D1~D8)** | **미연결.** `COLAB_BACKUP_TARGET=none` 이 기본값이고, 이 상태에서 `backup.sh` 는 성공하지 않는다(exit 78) | staging 에 postgres 자체가 없다 |
| **리허설 postgres** | **연결됨 — 이번에 실제로 백업·복원했다.** 일회용 `d1_*` 컨테이너 | §4 |
| ai postgres (D9·D10) | 미연결. 저장소가 없고 마이그레이션 체인도 분리다(`CLAUDE.md §3-3`) — 대상이 생기면 **두 번째 프로파일**로 붙인다 |
| 오브젝트 스토리지(업로드 원본) | 미연결. staging 에 없다. PoC 에서 백업 13GB 의 사실상 전부가 이것의 미러였다 — 붙일 때 **용량 정책부터** 정한다 |

**붙이는 절차** (I2 직후, 이 순서 그대로):

1. 홈 설정 파일에서 `COLAB_BACKUP_TARGET=postgres`, `COLAB_BACKUP_PG_CONTAINER`·`_DB`·`_USER` 를 채운다.
2. `./backup.sh` 1회 → GREEN 확인.
3. `./install-schedule.sh install` — **여기서 처음 스케줄을 건다.**
   대상 없이 미리 걸면 매일 실패가 쌓이고, **그 알람 피로가 8주 침묵의 메커니즘이었다**(`DEPLOY-CURRENT §9`).
4. `./roundtrip.sh` 를 실데이터 규모에서 한 번 더 — 복원 소요 시간이 그때 처음 실측된다.

스케줄은 두 줄이다. 백업만 걸면 "돌긴 도는데 복원되는지는 모르는" 상태가 되고, 그게 사건의 본질이었다.

| 시각 | 하는 일 |
|---|---|
| 매일 03:30 | `backup.sh` — 검사 통과분만 최종본 |
| 매주 월 04:10 | `latest-check.sh` — 최신 산출물 재검사(신선도 포함). 침묵을 주 1회 강제로 깬다 |

## 3. 증명 — 빈 백업이 성공으로 기록되지 않는다

`./selftest.sh` 한 줄로 재현된다. **fixture 10건 전부 기대대로 RED · 셀프테스트 GREEN**(exit 0).

먼저 **대조군**을 둔다 — 정상본 하나가 GREEN 이어야 한다. 그게 아니면 "검사기가 무조건 red 를 낸다"
는 것이고 증명이 성립하지 않는다. 실행 결과: `대조군 GREEN — 검사기는 정상본을 통과시킨다`.

| # | fixture | 실제 red 출력(요지) |
|---|---|---|
| **F1** | **0바이트 산출물** | `FAIL C1 크기 0B < 1024B` · `FAIL C2 gzip 무결성 — 손상·절단` · `FAIL C3 해제 결과 0바이트` · `FAIL C4 CREATE TABLE 0개 < 20` · `FAIL C5 데이터 행 0건 < 1` → **RED(5건)** |
| **F2** | **빈 gzip 20바이트** — 2026-07 사건의 실물 형태 | `FAIL C1 크기 20B < 1024B (빈 gzip 은 20B 다)` · **`PASS C2 gzip 무결성`** · `FAIL C3 해제 결과 0바이트 — 이것이 8주 사건의 실물이다` · `FAIL C4` · `FAIL C5` → **RED(4건)**. **C2 가 PASS 인 것이 요점이다** — PoC 가 본 두 항목 중 하나는 여기서도 통과한다. 크기·무결성만 보는 가드는 이 파일을 8주 통과시켰다 |
| **F3** | 크기는 있으나 테이블·행이 없다 | `PASS C2` · `PASS C3 해제 후 5428B` · `FAIL C4 CREATE TABLE 0개 < 20` · `FAIL C5 데이터 행 0건` → **RED(3건)** |
| **F4** | **테이블 20개 · 데이터 행 0** (구조는 왔는데 내용이 없다) | `PASS C4 CREATE TABLE 20개 (>= 20)` · `FAIL C5 데이터 행 0건 < 1 — 테이블만 있고 내용이 없다` → **RED(2건)** |
| **F5** | 절단·손상 gzip | `FAIL C2 gzip 무결성 — 손상·절단` → **RED** |
| **F6a** | **덤프가 non-zero 로 죽었다** (존재하지 않는 대상) | `pg_dump 실패 (exit 1). 임시파일 폐기 · 최종본 생성 안 함.` → **RED(exit 1)** |
| **F6b** | 위 실패 **직후 최종 경로 상태** | `새 파일 0개 · inflight 잔해 0개` — 실패가 산출물을 남기지 않는다 |
| **F6c** | **이전 성공본이 그대로 남아 있다** (8일 전 파일) | `PASS C1~C5 전부` · `FAIL C6 신선도 11520분 > 1500 — 오래된 잔존 파일이다` → **RED**. 내용이 멀쩡해도 **오늘의 백업이 아니다** |
| **F7** | 대상 미연결(`TARGET=none`) | `이 상태를 성공으로 기록하지 않는다 — exit 78` → **RED(exit 78)** |
| **F8** | **복원이 exit 0 인데 DB 가 비었다** — 실제 postgres 로 재현(스키마만 적재, psql 은 정상 종료) | `PASS 테이블 20 개` · `FAIL 행 수 d1_lab = 0 (기대 2)` … 8행 전부 · `FAIL 총 행 수 0 — 복원은 끝났는데 DB 가 비었다. 이것이 '성공한 빈 복원' 이다` → **RED(10건)** |

셀프테스트 자신도 fail-closed 다 — **fixture 가 하나라도 GREEN 이면 exit 1**, docker 가 없어 F8 을
못 돌리면 그것도 **SKIP 이 아니라 실패**로 센다(`green-by-skip` 금지, `CLAUDE.md §4`).

마지막 줄: `셀프테스트 GREEN — fixture 10 건 전부 기대대로 RED`.

## 4. 왕복 실증 — 백업 → 파괴 → 복원

`./roundtrip.sh`. **대상은 일회용 리허설 인스턴스이지 살아 있는 staging 이 아니다.**
staging 에는 백업할 데이터가 없으므로, 대신 **경로 전체를 실물로 한 번 통과**시켰다.

절차: `db/platform/schema.sql`(정본) 적용 → `seed.sql` 적재 → `backup.sh` → **원본 컨테이너 삭제**
→ 새 인스턴스 생성 → 복원 → 대조.

| 단계 | 실측 |
|---|---|
| 스키마 | 정본 그대로. 테이블 **20개** |
| 씨앗 | 19행 (아래 표). ULID 도메인·CHECK·FK 를 실제로 통과하는 값만 썼다 |
| 산출물 | `platform-<타임스탬프>.sql.gz` **6,201B** (해제 49,507B) · 검사 `C1~C6 전부 PASS` |
| 파괴 | 원본 컨테이너 `rm -f` — 되돌릴 것이 없는 상태 |
| 복원 | 빈 새 인스턴스에 `psql` 적재 |
| 대조 | **행 수 8행 전부 일치 · 총 19행 · 테이블 20개** |
| 내용 대조 | md5 다이제스트 **`54d8fbdec67dfc004f1fc712c61045b6` → 동일** |

행 수 대조 (전 = 후):

| 테이블 | 백업 전 | 복원 후 |
|---|---|---|
| `d1_lab` | 2 | 2 |
| `d1_lab_profile` | 2 | 2 |
| `d1_account` | 3 | 3 |
| `d2_member_role` | 3 | 3 |
| `d3_dataset` | 3 | 3 |
| `d3_dataset_description` | 3 | 3 |
| `d6_project` | 2 | 2 |
| `alembic_version_platform` | 1 | 1 |
| **합계** | **19** | **19** |

행 수만 보면 "19행이 19행으로 왔다" 는 값이 뒤바뀐 복원도 통과한다. 그래서 **내용 다이제스트**를
따로 뜬다(`content-digest.sql` — id·이름·역할·소유자·업로더·상태를 정렬해 md5). 두 값이 같았다.

**격리 준수** — 리허설 컨테이너는 `d1_pg_src` · `d1_pg_dst` · `d1_pg_selftest` 셋이고
**호스트 포트를 열지 않았으며** PGDATA 를 tmpfs 에 뒀고 종료 시 전부 제거했다. 다른 레인의
`a1_*` · `c1_*` 는 손대지 않았다. 작업 전·후 `healthz` **200 / 200**.

## 6. IS3 를 진짜로 닫으려면 남은 것

`WORK-UNITS.md` IS3 행의 완료 정의는 **「백업 1회 + 복원 1회 성공 + 빈 백업 fixture 로 fail-closed 증명」**이다.
셋 중 **fail-closed 증명은 충족**(§3), **백업·복원 1회는 리허설 대상으로 충족**(§4)이다.
남은 하나가 "그 대상이 staging 이어야 하는가" 이고, 그건 저장소가 없어 지금 성립하지 않는다. 그래서 🟧 다.

닫으려면 순서대로 셋:

1. **I2 로 staging postgres 가 올라온다** (다른 레인 진행 중) — 이것이 유일한 진입조건이다.
2. §2 의 붙이는 절차 4단계 실행 → `backup.sh` GREEN · `install-schedule.sh install`.
3. `selftest.sh` 를 `gates/run.sh` 에 단일 case 로 편입 (`gates/` 편집이 한가해진 뒤).

세 개가 끝나면 IS3 는 ✅ 다. 1번이 열리는 즉시 2·3은 한 세션 안에 끝난다 — 새로 설계할 것이 없다.

## 7. 실대상 연결 — 설정 4줄이 아니라 프로파일 2개였다

`I2.md §6` 이 넘긴 값은 넉 줄이었지만 그대로 붙이면 **`colab_platform` 만 백업된다.**
`colab_ai` 는 별도 데이터베이스이고(`CLAUDE.md §3-3` · `I2 §2`), 한쪽만 덮은 백업이 전체 성공으로
기록되는 것이 이 WU 가 막으려는 실패 그 자체다. 그래서 **대상을 프로파일 목록으로 바꿨다.**

| 바뀐 것 | 무엇 |
|---|---|
| `lib.sh` | `COLAB_BACKUP_PROFILES` + 프로파일별 DB·합격선 조회 함수. 미설정이면 구 단일대상 설정을 프로파일 `platform` 하나로 읽는다(기존 fixture 무수정 통과) |
| `backup.sh` | 프로파일 루프. 산출물 이름 `<프로파일>-<타임스탬프>.sql.gz`. **하나라도 실패하면 전체가 exit 1** — 부분 성공을 성공으로 기록하지 않는다 |
| `latest-check.sh` | 프로파일마다 최신본을 따로 묻는다. 한쪽만 남아 있는 상태를 통과시키지 않는다 |
| `run-scheduled.sh` (신규) | 크론 실행 껍데기. 실패를 표식 파일로 남긴다(§10) |
| `restore-rehearsal.sh` (신규) | **실 staging 백업**을 일회용 인스턴스에 복원해 대조. 살아 있는 DB 는 읽기만 한다 |
| `selftest.sh` | fixture **F9 추가** — 두 체인 중 한쪽만 백업된 상태가 RED 임을 강제 |

합격선이 프로파일마다 다르다. platform 은 테이블 20, ai 는 **4**(`d9_method_term`·`d9_place_alias`·
`d9_topic_synonym` + `alembic_version_ai`). 하나의 전역 합격선 20 을 그대로 쓰면 ai 백업이
**영원히 red** 이거나, 20 을 4 로 낮춰 **platform 의 절단을 놓치거나** 둘 중 하나가 된다.

실값은 홈의 `.colab-v2-staging-backup.env`(`0600`)에만 있다. 레포·문서에 비밀도 절대경로도 없다.

## 8. 실백업 — 살아 있는 staging 대상, 두 체인 각각

`./backup.sh` 1회. 컨테이너 경유(`docker exec … pg_dump`)라 **호스트 포트를 열지 않는다.**

| 프로파일 | 데이터베이스 | 산출물 | 압축 | 해제 후 | `CREATE TABLE` | 데이터 행 | 검사 |
|---|---|---|---|---|---|---|---|
| platform | `colab_platform` | `platform-20260823T044538.sql.gz` | **5,635 B** | 47,347 B | **20** | **1** (COPY 블록 20) | C1~C6 **전부 PASS** |
| ai | `colab_ai` | `ai-20260823T044546.sql.gz` | **2,427 B** | 6,766 B | **4** | **23** (COPY 블록 4) | C1~C6 **전부 PASS** |

각 산출물 옆에 `.sha256` 을 같이 남긴다. 종료코드 **0** · 마지막 줄 `백업 GREEN — 프로파일 2 개 전부 성공`.

**정직하게 적어 둘 것 하나.** platform 의 "데이터 행 1건" 은 `alembic_version_platform` 의 한 줄이다.
staging platform 에 아직 업무 데이터가 없다(`I2 §6-2`). 즉 지금의 C5(행 ≥ 1)는 **마이그레이션 표 덕에
통과하고 있고**, platform 에 실데이터가 들어오는 WU 에서 `COLAB_BACKUP_MIN_ROWS_platform` 을
그 규모로 올려야 이 검사가 다시 날을 갖는다. 지금 임의의 큰 수를 박으면 매일 red 다.

호스트 시계가 작업 중 약 8초 뒤로 스텝했다(WSL2 특성). 파일 mtime 과 이름의 타임스탬프가
초 단위로 어긋난 이유이고, 신선도 상한이 1500분이라 판정에는 영향이 없다.

## 9. 복원 리허설 — 실백업을 일회용 인스턴스에 되살렸다

`./restore-rehearsal.sh`. **살아 있는 staging DB 위로는 복원하지 않는다.** 일회용 인스턴스
`is3_pg_platform` · `is3_pg_ai` 를 만들고(호스트 포트 없음 · PGDATA tmpfs) 끝나고 지웠다.
다른 레인의 `b3_*` 와 떠 있던 `oasdiff` 컨테이너는 건드리지 않았다.

기대치는 정적 파일이 아니라 **살아 있는 staging 에서 그 자리에서 읽어** 만든다 —
그래야 "픽스처와 맞았다" 가 아니라 "원본과 맞았다" 가 된다.

| 프로파일 | 복원 소요 | 테이블 (원본 → 복원) | 행 수 대조 | 총 행 | 내용 다이제스트 |
|---|---|---|---|---|---|
| platform | 1초 | **20 → 20** | 20개 테이블 전부 일치 | 1 = 1 | `69beaffdca47cefd40109a03853afe36` **일치** |
| ai | 1초 | **4 → 4** | `d9_method_term` 13 · `d9_place_alias` 4 · `d9_topic_synonym` 5 · `alembic_version_ai` 1 — 전부 일치 | 23 = 23 | `da507d442a19203b3a9a9225e709b066` **일치** |

**K2 시드는 이름으로 못 박아 따로 셌다** — `13+4+5 = 22 행`. 별도 `PASS` 줄이 있다.

행 수만 보면 **값이 뒤바뀐 복원도 통과한다.** 그래서 테이블마다 `COPY … TO STDOUT` 으로 본문을
뽑아 정렬 후 md5 를 떠 원본과 대조했다(원본 쪽은 읽기만). 두 값이 같았다. 결과 `복원 리허설 GREEN`.

복원 소요 시간은 이 규모(총 24행)에서 1초다. **§5-6 의 "실데이터 규모 실측" 은 여전히 미충족**이다 —
지금 staging 에 실데이터가 없기 때문이고, 그건 백업 기구의 결손이 아니라 대상의 상태다.

## 10. 스케줄 설치 — 그리고 실패가 사람 눈에 보이는 경로

`./install-schedule.sh install` 실행. **이제 설치했다.** 예정대로 두 줄이다.

| 시각 | 하는 일 |
|---|---|
| 매일 03:30 | `run-scheduled.sh backup.sh` — 두 프로파일 |
| 매주 월 04:10 | `run-scheduled.sh latest-check.sh` — 최신본 재검사(신선도 포함) |

크론 데몬이 실제로 돌고 있음을 확인했다(`cron.service` active, 8시간 가동). 걸어 놓고 안 도는 상태를
"설치했다" 로 적지 않기 위해서다.

**실패는 세 자리에 남는다** (`run-scheduled.sh` 가 만든다. 성공·실패 양쪽을 실제로 태워 봤다):

| 자리 | 무엇 | 실측 |
|---|---|---|
| `staging-backup.log` | `!!! backup.sh 실패 (exit 1)` | 확인 |
| `BACKUP-FAILED.txt` | 실패 표식. **다음 성공에서만 사라진다** — 지나간 실패가 지워지지 않는다 | 확인 |
| `LAST-SUCCESS.txt` | 마지막 성공 시각. **크론이 아예 안 돈 경우**를 이것으로 잡는다 | 확인 |

여기에 주간 `latest-check.sh` 가 최신 산출물의 **신선도(C6 · 25시간)** 를 다시 묻는다.
백업이 조용히 멈추면 늦어도 그 주 월요일에 RED 다. 이것이 침묵의 상한을 **1주**로 자른다.

**그러나 정직하게 — 셋 다 "가서 봐야 보이는" 자리다.** push 알림(메일·메신저) 채널은 여전히 없다
(`§5-5`). 크론 메일은 이 호스트에 MTA 가 없어 도착하지 않으므로 `MAILTO=""` 로 명시해 두고
표식 파일 쪽에 무게를 실었다. **"실패했는데 아무도 모르는" 창이 0 이 되지는 않았고, 최대 1주로
줄었을 뿐이다.** 알림 채널은 이 레포 밖 결정이라 정본 확인이 필요하다 — 남은 것으로 §12 에 남긴다.

## 11. fail-closed 재확인 — 이번엔 살아 있는 설정 위에서

`./selftest.sh`. **대조군 GREEN · fixture 전부 기대대로 RED · 셀프테스트 GREEN(exit 0).**
F1~F8 은 §3 의 그것 그대로 다시 red 였고, 여기에 이번에 하나가 늘었다.

| # | fixture | 결과 |
|---|---|---|
| F1~F5 | 0바이트 · 빈 gzip 20B · 내용 없음 · 스키마만 · 절단 | 전부 **RED** |
| F6a·b·c | 덤프 사망 / 잔해 0 / 옛 성공본 신선도 | 전부 **RED**(b 는 "새 파일 0개·inflight 0개") |
| F7 | 대상 미연결 | **RED (exit 78)** |
| F8 | 복원 exit 0 인데 DB 가 비었다 | **RED** |
| **F9 (신규)** | **두 체인 중 한쪽만 백업됐다** — 실 staging pg 에 붙여 platform 은 뜨고 ai 는 없는 DB 를 가리킨다 | **RED (exit 1)**. 부분 성공은 성공이 아니다 |

F9 는 이번 세션에서 새로 생긴 실패 종류를 fixture 로 고정한 것이다. 대상이 둘이 되는 순간
"조용히 한쪽만 덮는 백업" 이 가능해졌고, 그건 8주 사건과 같은 계열이다.

## 12. 남은 것 — 그리고 왜 그것이 IS3 를 막지 않는가

| # | 남은 것 | 왜 지금 못 하나 | IS3 를 막는가 |
|---|---|---|---|
| 1 | **`gates/run.sh` 편입**(§6-3) | 같은 밤 다른 레인이 D3b 로 `gates/` 를 고치고 있다(`run.sh`·`README.md`·신규 도구 2개가 미커밋 상태). 이 세션의 금지 범위다 | **막지 않는다.** IS3 의 완료 오라클(`WORK-UNITS.md`)은 「백업 1회 + 복원 1회 + fail-closed 증명」이고 게이트 편입은 그 문장에 없다. 증명은 `selftest.sh` 로 지금 재현된다 |
| 2 | **push 알림 채널** | 레포 밖 결정(§5-5). 채널을 임의로 정하면 정본 없이 값을 만드는 것이다 | 막지 않는다. 침묵 상한은 1주로 잘렸다(§10) |
| 3 | **오브젝트 스토리지 백업** | staging 에 아직 없다(`I2 §6-4`). 용량 정책부터 | 막지 않는다. 대상이 없다 |
| 4 | **호스트 밖 사본** | 백업이 원본과 같은 WSL2 머신 위에 있다. 오프호스트는 I0(AWS) 이 열려야 성립 | 막지 않는다 |
| 5 | **복원 소요 실측(실규모)** · **platform 행 합격선** | staging platform 이 0행이다 | 막지 않는다. 대상의 상태다 |

**판정: ✅.** 완료 오라클 세 항목이 전부 **실 staging 대상**으로 충족됐다 —
백업 1회(두 체인 각각, §8) · 복원 1회(내용 대조까지, §9) · 빈 백업 fixture fail-closed(11건, §11).
§2 가 예고한 「붙이는 일은 설정 한 줄」은 절반만 맞았다. 실제로는 **두 체인을 두 백업으로 가르는
일**이었고, 그 사실을 fixture 하나(F9)로 못 박아 두는 것까지가 이 세션의 몫이었다.
