## 2. 미선언 입력의 red 가 거짓 원인을 말하던 것

### 2.1 무엇이 문제였나

R4 가 red 를 판정/준비로 가른 뒤, 기준선 red 둘(`schema-diff`·`autometa-loss`)이
「**검사 대상이 규율을 어겼다**」로 찍혔다. 실제 원인은 **적용 DB URL 이 아무 데도 선언되지 않은 것**이다.
대상은 한 건도 보이지 않았고 어긴 것도 없다 — 읽는 사람은 고칠 코드를 찾으러 가고, 고칠 코드는 없다.
R4 의 구분이 없애려던 모호함이 그대로 남아 있던 자리다.

### 2.2 어느 범주인가 — 준비, 그 안에서 원인만 가른다

가르는 축은 하나다: **대상이 판정됐는가.**

| 상태 | 대상이 판정됐나 | 범주 |
|---|---|---|
| 대상이 규율을 어겼다 | 예 | red(판정) |
| 환경을 기다리다 못 떴다 | 아니오 | red(준비·환경대기) |
| **입력이 선언되지 않았다** | **아니오** | **red(준비·입력미선언)** |

**넷째 범주를 만들지 않았다.** 미선언은 판정이 아니므로 준비다. 다만 준비 red 의 원인은 한 종류가
아니어서 — 환경대기는 「무엇을 얼마나 기다렸나」를 답할 수 있고 미선언은 기다린 것이 없다 —
같은 문장으로 찍으면 상한을 늘리러 가게 된다. 그래서 **범주는 그대로 두고 원인만 표식에 적었다.**

### 2.3 고친 모양

- 공용 표식기 `gates/tools/_readiness.sh`
  `::gate-readiness-failure::gate=<게이트>|cause=입력미선언|missing=<선언되지 않은 것>|detail=<사유>`
  `cause=` 없는 옛 표식은 환경대기로 읽힌다(`_pg.sh`). 종료코드는 78 그대로 — **여전히 red 다.**
- 사람이 읽는 줄: 「**검사에 필요한 입력이 선언되지 않았다.** 판정 red 가 아니다. 검사 대상은 한 건도
  보지 못했다 — 「대상이 규율을 어겼다」가 아니라 「아무도 값을 말하지 않았다」다. 선언되지 않은 것: …」
- 실행기 요약(`gates/run.sh`)이 준비 red 안에서 원인별 건수를 적는다.
  입력미선언 줄은 「**상한을 늘려도 달라지지 않는다. 그 값을 선언하고 다시 돌린다**」로 끝난다.
- 적용 자리 — `schema-diff`(체인별 URL 미선언 · 구 단일 변수만 선언), `autometa-loss`(적용 DB URL 미선언 ·
  면제 선언 파일 부재 · `datasets` 항목 부재). 셋 다 「선언이 없다」이지 「대상이 틀렸다」가 아니다.

### 2.4 곁다리로 잡힌 결함 — 표식이 grep 에 안 잡히던 것

표식을 `cut -c1-400` 으로 잘랐는데 **`cut -c` 는 바이트로 센다.** 한글 한 글자 중간에서 잘리면 깨진
바이트가 남고, `grep` 이 그 출력을 **바이너리로 보아 표식을 못 찾는다.** 실제로 실행기 요약이
`schema-diff` 에 대해 「사유 표식 없음」을 찍었다. `readiness_oneline()` 으로 잘라낸 뒤 유효하지 않은
바이트를 버리게 했고, `_pg.sh` 의 같은 자리도 그것을 쓴다.

## 3. 병렬 안전성 미선언 게이트 둘을 선언한다

종전: 실행기가 안전한 쪽(단독)을 고르고 그렇게 했다고 적었다 — 옳은 동작. 이제 **근거를 재고 선언**했다.

| 게이트 | 판정 | 근거(실측) |
|---|---|---|
| `autometa-loss` | **parallel** | 적용 DB 에 **읽기만 한다.** 스크립트 안에 `INSERT`·`UPDATE`·`DELETE`·`CREATE`·`DROP`·`ALTER`·`TRUNCATE` 0건(질의는 `WITH … SELECT` 하나). 도커·임시파일·잠금 0. 경합 자원은 적용 DB 하나이고 읽기 전용이므로 실행 순서가 판정을 바꾸지 않는다. 같은 DB 를 같은 방식으로 읽는 `schema-diff` 가 이미 parallel. |
| `autometa-loss-selftest` | **parallel** | **자기 일회용 컨테이너 안에서만** 산다. `_pg.sh` 의 `pg_start`(이름 = PID＋난수 · `--rm` · 포트 미공개) ＋ 자기 DB ＋ 자기 `mktemp -d`. 게이트에 psql 을 주입해 **적용 DB URL 을 아예 쓰지 않는다**(주입된 psql 이 첫 인자를 버린다). 도커 데몬 경합은 `_pg.sh` 의 선언 한도가 받는다 — `rls-coverage`·`rls-effect`·`schema-diff`·`stage2-markers` 와 같은 배치. `db-selftest` 를 serial 로 둔 이유(한 적용 DB 를 순서대로 훼손해 가며 본다)는 여기 해당하지 않는다. |

속도를 위해 바꾼 값 0건 — 두 건 다 **미선언 → 선언**이지 `serial` → `parallel` 이 아니다.

## 4. 배포 스케줄 설치기의 형제 결함

`infra/staging/pipeline/install-schedule.sh` 는 백업 쪽에서 고친 뒤에도 **쓰고 나서 되돌리는** 방식이었다.

- `crontab -l 2>/dev/null` 이 「크론탭 없음」과 「명령 실패」를 같은 빈 출력으로 만든다.
- 그 빈 출력을 `{ current; block; } | crontab -` 로 밀어 넣는다 — **읽기와 쓰기가 같은 대상에 동시에** 간다.
- 사후에 줄 수를 대조해 red 를 내지만, **이미 지워진 뒤**다. 스냅숏은 되돌릴 손잡이일 뿐 막지 못한다.
- `remove` 는 스냅숏도 사후 확인도 없었다.

고친 모양 = 백업 쪽 그대로. ⓐ `read_crontab()` 이 **읽기 실패와 「없음」을 가르고**, 읽지 못했으면 한
글자도 쓰지 않는다 ⓑ 설치·제거 양쪽 사전 스냅숏 ⓒ 스냅숏 파일에서 새 내용을 만들어 넣는다(동시 읽기·쓰기 없음)
