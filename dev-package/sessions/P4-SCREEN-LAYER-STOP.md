### 3.4 결과 헤드의 건수 — 정본이 침묵한 자리에 실물이 셋으로 갈려 있다

| 자리 | 실물 |
|---|---|
| 계약 | `contracts/schemas/common.json:212` — 「`totalCount` 는 **화면이 반드시 표시하는 값**이라 선택 항목이 아니다(결과 헤드 `4건을 찾았어요`)」 |
| 서버 | `catalog.py` — `search_datasets` 가 낸 **진짜 총계 `total` 을 버리고** `"totalCount": len(items)`(그 쪽 **드롭 뒤** 길이)를 낸다 |
| 화면 | `SearchResultsPage.tsx` — `found={state.results.items.length}`. **`totalCount` 를 아예 읽지 않는다** |

그리고 정문에 **말없는 드롭 경로**가 있다.

```python
row = by_id.get(hit["datasetId"])
if row is None:
    # 경계 밖이거나 지워진 식별자다. **없는 카드를 지어내지 않는다** (P-9·P-10).
    continue
```

- 드롭 건수를 **어디에도 드러내지 않고**, 요약값(`totalCount`)은 **드롭 뒤 길이로 다시 세어진다.**
  이것이 이 레포가 이름 붙인 **green-by-skip 의 모양**(「요약줄이 건너뛴 건수를 숨긴다」 · `CLAUDE.md §4`)이다.
- **다만 도달 가능성은 실측상 낮다** — `_SEARCH` 와 `_ROWS` **양쪽 다 `WHERE d.deleted_at IS NULL`** 이고 둘 다 RLS 아래 돈다.
  갈리는 자리는 **세션이 둘**(검색은 `read_only_scope` 의 `ro`, 조립은 요청 세션 `db`)이라는 점뿐이고,
  그 사이의 동시 삭제라는 **경합**만 남는다. ⟹ **잠재 결함이지 관측된 결함이 아니다.** 이 회차는 재현하지 않았다.
- `next_cursor` 는 **드롭 전** 길이와 진짜 `total` 로 계산되고, `totalCount` 는 **드롭 후** 길이다 — **두 값의 기준이 다르다.**
- 오늘 화면에서는 안 보인다 — 화면이 `limit` 을 넘기지 않아 `searchSource.ts` 의 기본 **20** 이 쓰이고, staging 적재분은 **12건**이다.

**⟹ 고치지 않았다.** 무엇이 옳은지가 정본 침묵 ⓐⓑⓒ 에 걸려 있다. **제품 판정 자리이지 이 회차가 정할 자리가 아니다.**

### 3.5 화면 층 대조를 지금 잴 수 없는 이유

`〈208〉` 이 요구하는 것은 **「화면(S-01·S-06)이 내는 결과」** 와 평가셋의 대조다. 현행 오라클은 **화면 층이 아니다.**

새로 만든 검사기·시험 **0건**이므로 「대상 있음 → 검사 / 명시 면제 → 건수 노출 / 미선언 → 실패」를 새로 박을 자리가 없었다.
대신 **기존 세 상태가 살아 있는지 실측으로 확인**했다 — `autometa-loss-selftest` 가 **ⓑ 면제 선언 부재 → red · ⓕ 면제 선언 → green ＋ 면제 건수 노출 · ⓒ 대상 0건 → red** 를 **실패 픽스처로 증명**하고 전건 기대대로 났다(§5).
**주장이 아니라 픽스처가 증명한다** — 이 회차가 그 성질을 새로 만들지 않았을 뿐 확인은 했다.
