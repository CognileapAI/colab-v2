## 2. 준비 실패(readiness) 를 판정 실패와 가른다

### 2.1 무엇이 문제였나

DB 게이트의 `red` 는 **두 가지 뜻을 겹쳐** 갖고 있었다.

| 갈래 | 뜻 | 해야 할 일 |
|---|---|---|
| 판정 red | 검사 대상이 규율을 어겼다 | 대상을 고친다 |
| 준비 red | **검사기가 아예 못 돌았다**(일회용 postgres 가 제때 안 뜸 등) | 대상은 **아직 판정되지 않았다** |

둘이 같은 글자로 나오니 부하에서 뜨는 간헐 red 를 결함으로 오인했고, 그 모호함이
**이 레포의 모든 측정값**(병합 판정 포함)을 못 믿을 것으로 만들었다.

### 2.2 고친 모양 — 늘리지도, 재시도하지도, 건너뛰지도 않는다

**바뀐 것은 red 가 자기 원인을 말한다는 것뿐이다.** 상한 연장 0 · 재시도 0 · 병렬도 축소 0 · skip 0.

- **한 줄 표식**(기계가 읽는다) — `gates/tools/_pg.sh` `pg_readiness_report()`
  `::gate-readiness-failure::gate=<게이트>|waited_for=<무엇을 기다렸나>|limit=<상한>|elapsed=<실경과>|detail=<사유>`
- **전용 종료코드 78**(`PG_READINESS_EXIT`) — 판정 red 는 그대로 1.
- **실행기 요약이 세 갈래로 센다**(`gates/run.sh`) — `green` / `red(판정)` / `red(준비)`
  ＋ 계 줄 ＋ 「이 건들에 대해 검사 대상은 아직 판정되지 않았다」 경고. **총계에서 빠지지 않고 종료코드도 실패 그대로.**

### 2.3 어디까지 넓혔나 — 형제를 찾았다

| 자리 | 종전 | 지금 |
|---|---|---|
| 도커 부재 · 이미지 확보 실패 · 컨테이너 생성 실패 · `pg_isready` 시간초과 · 슬롯 고갈 | 전부 `red`(구분 없음) | **`red(준비)` ＋ 대기 대상·상한·실경과** |
| `rls-effect.sh` 의 **복제된** 준비 경로 | 같은 로직 두 벌 | `_pg.sh` 의 것을 **그대로 호출**(한쪽만 관대해지는 것을 막는다) |
| `stage2-markers` 의 venv 부재 | `red`(판정으로 보였다) | **`red(준비)`** — 「시험이 틀렸다」가 아니라 「돌릴 환경이 없다」 |
| `pg_apply` 의 스키마 적용 실패 | 사유를 **통째로 버렸다** → 서버 탓도 「적용되지 않는 스키마」로 나옴 | `PG_APPLY_ERR` 보존 ＋ `pg_is_readiness_error()` 로 **서버 계열 / SQL 계열**을 가른다 |
| 셀프테스트 안에서 뒤집힌 케이스 | 「fail-closed 아님」= **거짓 결함 보고** | `red(준비)` 로 분리 ＋ 셀프테스트 전체가 78 로 나간다 |

⭑ **가장 조용했던 자리** — 셀프테스트의 `expect red` 가 **준비 실패를 「기대한 red」로 세고 있었다.**
보호 장치를 떼고 red 를 기대한 케이스가 준비 실패로 red 가 나면 **그 보호 장치는 판정된 적이 없다.**
green-by-skip 의 정확한 모양이다. 기대값을 `green|red|**ready**` 세 값으로 만들어,
**준비 실패는 「그것을 재는 케이스」에서만 통과**다.

| 구분: rls-coverage 도커 부재 | 준비 red = exit 78 ＋ 표식 ＋ `waited_for`·`limit`·`elapsed` |

## 5. 백업 스케줄 설치기의 형제 결함 (`infra/staging/backup/install-schedule.sh`)

배포 쪽(`infra/staging/pipeline/install-schedule.sh`)에서 이미 고친 두 모양이 여기 그대로 남아 있었다.

| 결함 | 종전 | 지금 |
|---|---|---|
| **「붙였다 ≠ 가리킨다」** | `crontab -` 종료코드만 보고 「설치됨」 | **설치 뒤 읽어서** 판정(`verify_installed`) — 블록 표식 · **실행 줄 2건** · 블록 밖 줄 수 3항 실측 |
| **「없음」과 「못 읽음」의 혼동** | `crontab -l 2>/dev/null` 이 둘을 같은 빈 출력으로 만들고, 그 빈 출력이 `crontab -` 로 들어가 **형제 블록까지 지운 채 「설치됨」** | `read_crontab()` 가 **가른다** — `no crontab for …` 만 「없음」이고 나머지(권한 오류 등)는 **읽기 실패 → 한 글자도 쓰지 않고 중단** |
| 되돌릴 손잡이 | 없음 | 설치·제거 **양쪽 모두** 사전 스냅숏 ＋ 블록 밖 줄 수(`PRE_N`) 대조 |
| 설치 없이 묻기 | 없음 | `verify` 갈래 신설 |

### 5.1 시험 먼저 — 픽스처가 파괴 경로를 막았음을 증명한다

**고치기 전 실행에서 5건 전부 FAIL**(＝ 파괴 경로가 실제로 열려 있었다), 고친 뒤 전건 통과.

| 픽스처 | 재는 것 | 고치기 전 |
|---|---|---|
| `F13-0` | **픽스처가 실물 crontab 에 닿지 않는다**(주입이 먹는지 먼저 증명 · 안 먹으면 중단) | — (사고 뒤 신설) |
| `F13-a` | `crontab` **읽기 실패** 시 설치를 **거부**한다 — 형제 블록·남의 줄 생존 | **FAIL** — 「설치됨」 |
| `F13-b` | 「크론탭 없음」은 실패가 아니다 — 걸리고, 걸린 것을 읽어서 확인한다 | **FAIL** |
| `F13-c` | 설치가 **형제 블록(배포)과 남의 줄을 보존**한다 | **FAIL** |
| `F13-d` | **쓰기를 삼키는** crontab 에서 「설치됨」을 내지 않는다 | **FAIL** |
| `F13-e` | `remove` 도 읽기 실패에서 **쓰지 않는다** | **FAIL** |

**실측 건수** — 백업 셀프테스트 **16건 → 22건 GREEN**(＋6). **검사 범위를 줄인 곳 0건.**
**실물 crontab 접촉 0건**(픽스처 재작성 이후 · `crontab -l` 읽기만 별도로 수행).

### 5.2 형제 하나 — 발견하고 고치지 않았다

`infra/staging/pipeline/install-schedule.sh` 는 스냅숏·`PRE_N` 으로 막고 있으나
**읽기 실패와 「없음」을 여전히 가르지 않는다**(`current()` 의 `crontab -l 2>/dev/null`).
막는 시점이 **쓴 뒤**라 「사라졌다가 스냅숏으로 되돌린다」이고, 백업 쪽은 이번에 **쓰기 전 거부**로 갔다.
**다른 항목의 파일 면이라 손대지 않았다** — 판정 대기(`§7`).

## 6. 데이터 처리 단위의 의존 핀 어긋남 — `[미확인]` 해소

**직전 회차의 물음** — 핀과 설치본이 정확히 일치하는데 시험 3건이 실패한다.
**레포 결함인가, 내 사본 구성 문제인가**(`I3-DEPLOY-AUTOMATION-PREP §5.2`).

**푸는 법대로 했다** — CI 가 쓰는 것과 같은 도커 이미지(`services/pipeline-worker/Dockerfile`)를
빌드해 그 안에서 같은 선택자로 돌렸다.

| 재는 자리 | 수집 | 통과 | 실패 | 설치본 |
|---|---|---|---|---|
| 호스트 venv (직전 회차 · WSL) | 34 | 31 | **3** | pydantic 2.13.4 · pydantic_core 2.46.4 · rio-cogeo 7.0.2 |
| **CI 이미지 안**(`python:3.12-slim` · `pip install --no-deps -r requirements.txt`) | **34** | **34** | **0** | **동일** — pydantic 2.13.4 · pydantic_core 2.46.4 · rasterio 1.5.1 |

**판정 — 레포 결함이 아니다. 사본(호스트 venv) 구성 문제다.**
근거 = **같은 핀 · 같은 파이썬 부(3.12) · 같은 시험 · 같은 선택자**인데 이미지 안에서는 전건 통과.
직전 회차가 표면 사유로 지목한 `pydantic-core` 컴파일 불일치는 **호스트에서 만들어진 휠/venv 의 성질**이고
`requirements.txt` 의 핀이 만든 것이 아니다.

⚠ **핀을 한 글자도 고치지 않았다.** 고칠 것이 없다는 것이 이 절의 결론이다.
⚠ 이번 워크트리에는 venv 자체가 없어 `stage2-markers` 가 **`red(준비)`** 다(`§3`). 성질이 또 한 번 바뀌었다 —
「측정된 실패 3건」이 아니라 **「이 체크아웃에 환경이 없다」**이고, 그렇게 출력에 적힌다.

## 7. 판정 대기 (Ted)
