## 3. 레벨과 계보의 관계 — 정본이 이미 말한 것

### 3.1 이미 있는 것 — **위로 미는 규칙 하나뿐**

정본이 말한 레벨↔계보 관계는 전부 **자동 보정(위로)** 이다:

- `DataModel_공통_기반.md:69` — 「(주입력 부모 중 가장 높은 Lv) + 1」
- `POL-020` — 「연결된 가공 전 데이터 중 가장 높은 Lv + 1, 상한 Lv2 … 사람이 이미 고른 값은 덮어쓰지 않는다」
- `Policy_업로드와_계보_확정.md:211` (축자) — `| 가공 단계 칸 | 보조입력 부모만 확정됨 | Lv가 오르지 않는다 — 보조입력은 계산에서 빠지기 때문이다 (공통 기반 E-00) | "보조입력은 가공 단계를 올리지 않아요" |`

### 3.2 없는 것 — **「부모보다 아래로 못 간다」는 `정본 무근거`**

**판정 = `정본 무근거`.** 근거:

1. **문서 실측** — 기획 정본 폴더 · 260825 스펙 · 260826 결정문 전체에서 `부모보다` / `보다 낮` 문자열 **0건**(2026-08-29 실측).
2. **`POL-020` 은 하한이 아니라 보정값이다.** 그리고 그 보정은 **사람이 고른 값 앞에서 물러난다**(축자 「사람이 이미 고른 값은 덮어쓰지 않는다」 · 스펙 17 「사람이 직접 고른 값은 시스템이 되돌리지 않는다」). 즉 **정본은 사람이 부모보다 낮은 값을 고르는 것을 명시적으로 허용하는 쪽에 가깝다.**
3. **코드 실측** — 사람이 고른 값을 부모 Lv 와 대조하는 자리가 **어디에도 없다.** `routes/catalog.py:460-466` 은 `0..LV_CAP` 범위만 본다. `d3_catalog.processing_level` 은 `user_set` 이 있으면 **부모를 아예 보지 않는다**(`if user_set is not None: return …` 이 첫 분기).
4. **DB CHECK 도 범위만 본다** — `d3_dataset_processing_level_user_set_range` (`BETWEEN 0 AND 2`).

⭑ **따라서 Ted 판정의 「고른 부모보다 아래로는 못 간다」는 신설이다.** ⚠ 그리고 그 신설은 **`POL-020` 의 「사람이 고른 값은 덮지 않는다」와 `〈140〉`-㉯ 의 「사람의 선택은 낡지 않는다」를 부분적으로 되돌리는 방향**이다 — 사람의 선택 위에 계보가 만드는 하한을 얹기 때문이다. 판정하지 않고 자리만 적는다.

### 6.3 ⚠ 「사람이 확인한 것만」 규칙과의 충돌 — 정확히 어디가 부딪히나

3. `DataModel_공통_기반.md §4.2` (축자): "역할을 나중에 붙일 수 없는 이유는 저장 방식이라서가 아니라 **1차에 가공 기능이 없기 때문이다.** 계보는 시스템이 가공을 실행하며 자동으로 남기는 것이 아니라 **올리는 사람이 그 자리에서 신고하는 것**이고 …"

### 9.1 `processing_level_user_set` 이 실제로 쌓여 있는가 — **0 건** (2026-08-29 실측)

읽기 전용 조회 1회(`colab_v2_staging_pg` · DB `colab_platform`):

```
SELECT count(*) AS total, count(processing_level_user_set) AS user_set_rows FROM d3_dataset;
→ total = 12 · user_set_rows = 0
```

⭑ **판정 ⑵(사람이 레벨을 직접 정하지 못한다)의 제거 작업에 데이터 이행이 붙지 않는다.**
컬럼·계약·수용 경로를 걷어내도 **바뀌는 표시 Lv 가 0 건**이다 — `〈140〉-㉴` 가 「적재된 12건의 표시 Lv 가 하나도 바뀌지 않는다」고 적은 것과 같은 값이 반대 방향에서도 성립한다.
⚠ **사후 판정을 관측 개수로 쓰지 않는다** — 「0건 삭제」가 아니라 **「대상 0건 실측(2026-08-29)」** 이다. 제거 착수 시점에 다시 센다.
⚠ **`§8` 의 「운영 스택 실제 Lv 분포 미측정」 중 `user_set` 축만 닫혔다.** 파생 Lv 의 분포는 여전히 미측정이다.

### 9.2 계보 기록이 **지울 수 있는 구조인가** — **지울 수 있다** (2026-08-29 실측)

| 축 | 실측 | 근거 |
|---|---|---|
| append-only 트리거 | **없다** | `db/platform/schema.sql` 의 `CREATE TRIGGER` 8건 중 append-only 는 `d2_permission_change_append_only`(`:163`) · `d8_activity_append_only`(`:670`) · `d8_download_append_only`(`:683`) **셋뿐**. `d4_lineage_edge` 에 트리거 0건 |
| 운영 DB 실물 | **트리거 0 · 룰 0** | `SELECT tgname FROM pg_trigger WHERE tgrelid='d4_lineage_edge'::regclass AND NOT tgisinternal` → 0행 ／ `SELECT count(*) FROM pg_rules WHERE tablename='d4_lineage_edge'` → 0 |
| 삭제 경로 | **이미 있다** | `services/core-api/src/colab_core/domains/d4_lineage.py:97` `_DELETE_EDGE` = `DELETE FROM d4_lineage_edge WHERE child_dataset_id = :child AND parent_dataset_id = :parent RETURNING id` (호출 `:192`) |

⭑ **그러므로 「계보도 권한 이력처럼 추가만 되는가」의 답은 아니다.** `d2_permission_change` 는 트리거로 `UPDATE`·`DELETE` 를 막지만(`schema.sql:66` 축자 "append-only 기록이다 — 수정·삭제 경로를 만들지 않는다 (PLAN-SoT 9-28)") **계보 엣지는 그 규율의 대상이 아니었다.**

⚠ **그래서 「연결만 끊기고 이름은 상수로 남는다」는 지금 구조가 주지 않는다.** 엣지를 지우면 `parent_dataset_id` 도 같이 사라져 **「무엇에서 왔다」가 남지 않는다.** 이 회차는 판정하지 않고 **선택지만** 적는다(→ `PLAN-SoT §9 〈195〉`).

⚠ **`§5.4` 의 「코드는 뒤엣것과 앞엣것이 섞여 있다」가 여기서 값으로 확인됐다** — 260826 결정은 AI 전면 제외인데 **코드는 자동 호출을 유지한다.**
