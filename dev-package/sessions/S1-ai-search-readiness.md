## D. 비용과 순서 — 판단 재료

> 이 절은 **전부 INTERPRETATION 이다(잠정).** 근거는 A~C 의 실측뿐이고, 기능 설계는 하지 않는다.

### D-1. 검색을 만들기 전에 **반드시** 있어야 하는 것 — 의존의 실물

정본이 「데이터를 먼저 올려야 검색할 수 있다」고 적은 문장은 **없다**(`[정본 무근거]`).
실제 의존은 문서가 아니라 **계약·스키마·완료 정의의 형태**에서 나온다:

1. **`SearchHit` 은 `datasetId` 를 돌려준다**(`core-ai.yaml` `cat -n` 393행). 카드의 나머지 값(이름·포맷·Lv·요약·기간·소유·Verified·잠김)은
   **core-api 가 D3·D2 에서 붙인다**(102~104행). → 결과 화면이 그려지려면 **D3 카탈로그 읽기 경로**가 있어야 한다.
   **이것은 P1 로 이미 닫혀 있다**(`03-HANDOFF` 85행: P1 ✅, 4 op 구현, staging green).
2. **후보 추출의 대상 텍스트가 있어야 한다** — `d3_dataset`·`d3_dataset_description` 에 행이 있어야 관련도가 의미를 갖는다.
   행을 넣는 유일한 허용 경로는 **업로드 모달 경로**다(`㊾-③` — DB 직접 INSERT 금지).
   → **S2(초기 데이터 적재)** 가 필요하고, S2 진입조건은 **P2**(업로드·계보)다.
3. **평가셋이 실데이터를 요구한다**(C-2). K4 의 완료 정의가 평가셋에 걸려 있으므로,
   **K4 의 완료는 S2 뒤로 밀린다** — 착수가 아니라 완료가.
4. **정본이 요구하는 0건 문구가 실수(實數)를 요구한다** — 「우리 연구실 데이터 **128개**를 뒤졌지만」(`P02 §3.3`).
   계약의 `AiSearchScope.searchedCount` 가 그 자리다. 데이터 0건이면 「0개를 뒤졌다」가 된다.
   **기능은 성립하지만 시연이 성립하지 않는다.**

> **결론(잠정): 순서의 강제는 「업로드 먼저」가 아니라 「검증 가능성 먼저」다.**
> K4 를 **만드는 일**은 P2/S2 없이도 착수 가능하다(진입조건이 `K2·G2·D2` 뿐이고 셋 다 닫혔다).
> 그러나 K4 의 완료 판정과 P4 의 완료 판정(목업 대비 화면 검증 + staging green)은 데이터 없이 통과할 수 없다.
> **착수 의존과 완료 의존이 다르다** — 이 구분을 흐리면 「빈 DB 위에서 green」이라는 v1 식 거짓 완료가 재현된다.
