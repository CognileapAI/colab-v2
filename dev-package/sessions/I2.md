# WU-I2 — Walking skeleton 을 staging 에 올린다

> **상태: ✅ 완료.** 완료 오라클(`WORK-UNITS.md` I2 행) = 「staging 에서 5개 전부 헬스 green,
> 배포·롤백 각 1회 성공」. 둘 다 충족했고 증거는 §3 에 응답 코드와 시각으로 있다.
> 작업 전 `www.colab-hydro.com/healthz` **200** → 작업 후 **200**. 중간에도 끊기지 않았다.
>
> **I2 는 이 트랙의 분수령이다**(`WORK-UNITS.md §4`). 여기를 지난 뒤로 각 WU 의 완료 판정에
> `staging 배포 green` 이 붙는다.

---

## 1. 올린 것

배포 단위 5개 + 저장소 1개. **전부 컨테이너 하나씩**이고, 호스트로 나오는 포트는 `127.0.0.1:3000` **하나뿐**이다.

| 배포 단위 | 이미지 | 컨테이너 | 안쪽 포트 | 공개 헬스 경로 | 응답 |
|---|---|---|---|---|---|
| core-api | `colab-v2/core-api:i2` | `colab_v2_staging_core_api` | 8000 | `/healthz/core-api` | `{"unit":"core-api","status":"alive","implemented":true}` |
| pipeline-worker | `colab-v2/pipeline-worker:i2` | `colab_v2_staging_pipeline_worker` | 8000 | `/healthz/pipeline-worker` | `…"implemented": false` |
| viz-render | `colab-v2/viz-render:i2` | `colab_v2_staging_viz_render` | 8100 | `/healthz/viz-render` | `…"implemented": false` |
| ai-service | `colab-v2/ai-service:i2` | `colab_v2_staging_ai_service` | 8200 | `/healthz/ai-service` | `…"implemented": false` |
| frontend | `colab-v2/frontend:i2` | `colab_v2_staging_frontend` | 8080 | `/healthz/frontend` | `{"unit":"frontend","status":"alive","implemented":true}` |
| (저장소) postgres | `postgres:16-alpine` | `colab_v2_staging_pg` | 5432 | 공개 안 함 — `pg_isready` 헬스체크 | `healthy` |
| (엣지) nginx | `nginx:1.27-alpine` | `colab_v2_staging_nginx` | 80 → `127.0.0.1:3000` | `/healthz` | `ok` |

`implemented` 필드가 **거짓말을 막는 자리**다. 세 단위는 비어 있고, 그 사실이 응답에 적혀 있다.
`"status":"alive"` 만 있으면 "떠 있다" 와 "동작한다" 가 구분되지 않는다.

### 세 빈 단위에 무엇을 넣었나 — 그리고 무엇을 넣지 않았나

`app/health.py` 하나뿐이다. **표준 라이브러리만** 쓰고 런타임 의존이 0 이라 이미지에 `pip install` 이 한 줄도 없다.

이유는 절약이 아니다. 빈 단위에 프레임워크를 지금 넣으면 **그 단위를 실제로 채우는 WU 의 선택을 미리 써 버린다.**
D5 가 큐 워커일지 배치일지, D7 이 무엇으로 렌더할지는 이 WU 가 답할 질문이 아니다.
walking skeleton 이 요구하는 것은 「프로세스가 살아 있고 오케스트레이터가 그것을 기계로 확인한다」 뿐이고, 딱 그것만 넣었다.

**도메인 로직은 한 줄도 넣지 않았다.** `services/` 에 들어간 변경은 전부 배포 배관이다 —
`Dockerfile` 4개 · `health.py` 3개 · core-api 의 `/healthz` 라우트 1개 · `frontend/nginx.conf`.

### core-api 의 `/healthz` 가 계약을 흔들지 않는 이유

- 경로가 `API_PREFIX`(`/api/v1`) **밖**이다. 라우트 표 오라클(`tests/test_route_table.py`)은
  `API_PREFIX` 로 시작하는 라우트만 세므로 **34 는 그대로다** (배포된 이미지 안에서 재확인: `API_PREFIX 라우트 34`).
- `include_in_schema=False` 이고, 애초에 앱의 `openapi_url` 이 `None` 이다. 계약 정본은 여전히 `contracts/seams/fe-core.yaml` 뿐이다.
- **DB 를 건드리지 않는다.** 프로세스 생존과 DB 도달성은 다른 질문이다. 섞으면 DB 가 잠깐 흔들릴 때
  오케스트레이터가 멀쩡한 프로세스를 죽인다.

### 엣지 라우팅

터널 ingress 는 `www.colab-hydro.com → http://nginx:80` **한 줄뿐**이다(IS2 가 IaC 로 못 박은 그것).
5개 단위를 가르는 일은 **오리진 안쪽 nginx** 가 한다 — `infra/staging/nginx.i2.conf`.

```
/healthz                → 엣지 자신 (200 "ok")  ← IS1 이 쓰던 그 경로. 의미를 바꾸지 않았다
/healthz/<unit>         → 각 단위의 /healthz
/api/v1/                → core-api
/                       → frontend  (정문은 역할별 구조화 화면이다)
```

`proxy_pass` 를 상수가 아니라 변수로 쓴다. 상수로 쓰면 뒷단 하나가 안 떠 있을 때 nginx 자체가
기동에 실패하고, **"어느 단위가 죽었나" 를 물어볼 창구까지 같이 사라진다.**

## 2. postgres — 이번에 내가 내린 결정

### 왜 지금 올리는가

I2 의 문구는 「5개 배포 단위를 **빈 상태로**」다. 그런데 core-api 는 빈 단위가 아니다 —
P0 이 실질의 5개(`getCurrentAccount` `getLab` `listDatasets` `listDatasetFiles` `createProject`)를
DB 를 읽는 코드로 만들어 뒀다. **저장소 없이 올리면 그 5개가 staging 에서 기동조차 못 한다**
(`kernel/config.py` 가 접속 문자열이 없으면 뜨지 않게 돼 있고, 그게 맞다).
"빈 상태" 는 *도메인 로직이 비어 있다* 는 뜻이지 *뒷단을 빼고 띄운다* 는 뜻이 아니다.

두 번째 이유는 IS3 다. `sessions/IS3.md §5-1`·`§6-1` 이 백업 미달 사유를 **「실대상은 I2 와 함께 온다」**
한 줄로 적어 두고 대기 중이다. I2 가 postgres 를 안 올리면 IS3 는 영원히 🟧 다.

### 어떻게 올렸는가 — 체인은 갈라진 채로 둔다

**두 체인 = 두 데이터베이스**다. `colab_platform` · `colab_ai`. 한 데이터베이스 안의 두 스키마로 합치지 않았다.

합치면 `CLAUDE.md §3-3`(체인 분리)이 **이름 규칙으로만 남는다.** 지금은 갈라진 것이 실물이다 —
version_table 이 다르고(`alembic_version_platform` / `alembic_version_ai`), 접속 문자열이 다르고,
마이그레이션 러너를 **한 번에 한 체인만** 돌린다.

적용 결과:

| 체인 | 데이터베이스 | head | 실물 |
|---|---|---|---|
| platform | `colab_platform` | `0001_p0_platform` | 테이블 20 · RLS enabled 18 · FORCE 18 |
| ai | `colab_ai` | `0003_k2_ontology_seed` | K2 시드 22 행 (`d9_method_term` 13 · `d9_place_alias` 4 · `d9_topic_synonym` 5) |

### 롤 모델 — P0 이 세운 것을 그대로 가져왔다

여기가 조용히 무너지기 가장 쉬운 자리다. **앱이 소유자나 BYPASSRLS 로 붙는 staging 은 P0 이 방금 만든
경계 증명 전부를 무효로 만든다** — 코드는 그대로인데 증명만 거짓 green 이 된다.

그래서 롤 정의를 새로 쓰지 않고 `services/core-api/ops/app-role.sql` **그 파일을 그대로 먹였다.**
그 파일의 마지막 두 검사가 fail-closed다(앱 롤이 superuser·BYPASSRLS 이거나 테이블 소유자면 거기서 예외를 던진다).

실측 (`infra/staging/db-bootstrap.sh verify`):

```
   rolname   | rolsuper | rolbypassrls | rolcreatedb | rolcreaterole
-------------+----------+--------------+-------------+---------------
 colab_app   | f        | f            | f           | f
 colab_owner | f        | f            | f           | f

 tableowner  | count          ← colab_app 소유 0
-------------+-------
 colab_owner |    20

 rls_enabled | rls_forced | tables
-------------+------------+--------
          18 |         18 |     20
```

`P0-rls-proof.md` 의 일회용 DB 실측과 **숫자가 정확히 같다.** 순서도 지켰다 —
① 롤·DB → ② 마이그레이션(**소유자 롤**) → ③ 앱 롤 GRANT. GRANT 를 테이블보다 먼저 주면
`GRANT ON ALL TABLES` 가 빈 집합에 걸려 조용히 아무것도 안 준다.

마이그레이션 러너를 core-api 이미지에 넣지 않고 따로 뒀다(`infra/staging/migrator/`).
앱 컨테이너에 alembic 을 같이 넣으면 앱 롤에서 DDL 을 회수한 의도가 흐려지고,
`db/ai` 체인은 애초에 core-api 의 것이 아니다.

### 노출

**postgres 는 포트를 하나도 열지 않는다.** 접근 경로는 compose 네트워크와 `docker exec` 뿐이다.
PoC 에서 5432 가 `0.0.0.0` 에 열려 있던 실패(`DEPLOY-CURRENT.md §4`)를 반복하지 않는다.
전체 스택에서 호스트로 나오는 포트는 `127.0.0.1:3000` 하나이고, `docker ps` 에 `0.0.0.0` 은 **0 건**이다.

### 데이터 디렉터리 — named volume 을 쓰지 못했다

이 호스트의 docker root 가 Windows 드라이브(9p) 위에 있어 POSIX 퍼미션이 없다.
named volume 에 `PGDATA` 를 두면 `initdb` 가 디렉터리 권한을 바꾸지 못해
**`Operation not permitted` 로 무한 재시작**한다(실제로 겪었다. `PGDATA` 를 하위 디렉터리로 내려도 같다).

그래서 WSL 쪽 ext4 경로에 바인드 마운트했다. 그 경로 값은 홈의 0600 env 파일에만 있고
compose 는 `${COLAB_STAGING_PGDATA_DIR:?…}` 로 받는다 — 레포·문서에 절대경로를 적지 않는다(`CLAUDE.md §5`).
**이건 이 호스트의 성질이지 설계 선택이 아니다.** I1(AWS IaC)이 오면 함께 사라진다.

## 3. 배포·롤백 — 명령과 증거

### 대칭 구조

`compose.yml`(자리표시 오리진 = 직전 릴리스)과 `compose.i2.yml`(walking skeleton)이
**같은 프로젝트명·같은 컨테이너 이름**을 쓴다. 그래서 두 파일이 같은 자리를 두고 앞뒤로 교체된다.

```bash
infra/staging/deploy.sh      # → walking skeleton
infra/staging/rollback.sh    # → 직전 서빙 상태
```

DNS·터널을 어느 쪽도 건드리지 않으므로 **전파를 기다릴 일이 없다.**
롤백은 pgdata 를 지우지 않는다 — 롤백이 데이터를 지우면 그건 롤백이 아니라 재해다.

### 배포 시퀀스 (`deploy.sh` 가 하는 일)

```
① docker compose -f compose.i2.yml --profile migrate build
      배포되는 것이 커밋의 산출이 되게 이미지 안에서 빌드한다.
      frontend 는 npm ci + vite build 를 이미지 안에서 돈다 — 호스트의 dist/ 를 복사하지 않는다.
      (PoC 가 8주 전 수동 빌드 이미지를 돌린 실패가 정확히 그것이었다)
② docker compose … up -d postgres          + healthy 대기
③ db-bootstrap.sh roles                    롤 · 데이터베이스 2개
④ docker compose run --rm migrate-platform upgrade head
   docker compose run --rm migrate-ai       upgrade head      ← 체인별로 따로, 소유자 롤로
⑤ db-bootstrap.sh app-grants               앱 롤 GRANT + fail-closed 검사
⑥ docker compose … up -d --remove-orphans  5개 단위 + 엣지 교체
```

마이그레이션 러너는 compose profile `migrate` 뒤에 있다 — **`up -d` 가 마이그레이션을 몰래 돌리지 않는다.**
배포 절차가 명시적으로 부른다.

### 증거 — 왕복 4회 측정 (전부 `https://www.colab-hydro.com` 공개 주소)

응답 코드만으로는 판정할 수 없다. 자리표시 오리진은 **모든 경로에 안내 페이지를 200 으로 준다** —
그래서 `/healthz/core-api` 도 200 이었다. 그러므로 **코드 + 본문**을 같이 본다.

| 시각 | 국면 | `/healthz` | `/healthz/core-api` | `/api/v1/me` | 본문으로 본 서빙 주체 |
|---|---|---|---|---|---|
| 04:29:07 | **배포 전** (자리표시) | 200 `ok` | 200 `<!doctype html>…` | 200 `<!doctype html>…` | 자리표시 안내 페이지 |
| 04:34:26 | **배포 후** | 200 `ok` | 200 `{"unit":"core-api",…}` | **401** `{"code":"UNAUTHORIZED",…}` | walking skeleton |
| 04:36:45 | **롤백 후** | 200 `ok` | 200 `<!doctype html>…` | 200 `<!doctype html>…` | 자리표시 안내 페이지 (= 직전 상태 복귀) |
| 04:37:39 | **재배포 후 (최종)** | 200 `ok` | 200 `{"unit":"core-api",…}` | **401** `{"code":"UNAUTHORIZED",…}` | walking skeleton |

**판정 근거를 명시한다.**

- **배포 1회 성공** = 04:34:26 에 5개 단위가 전부 자기 `unit` 이름으로 대답했다.
  같은 시각 `docker ps` 의 헬스체크도 7개 컨테이너 전부 `healthy`.
- **롤백 1회 성공** = 04:36:45 에 응답 본문이 **배포 전과 같은 것**으로 돌아왔다.
  "내려갔다" 가 아니라 **"직전 상태가 다시 서빙되고 있다"** 를 본문으로 보였다. IS1 의 200→530→200 과 같은 기준이다.
- **끊김 없음** = 네 시점 모두 `/healthz` 200. IS1 은 오리진을 통째로 내려 530 을 거쳤지만,
  이번 롤백은 엣지 컨테이너를 교체만 하므로 530 구간이 아예 없다. 더 좋은 결과지 다른 기준이 아니다.
- **데이터 생존** = 롤백·재배포를 거친 뒤에도 두 체인의 head 와 K2 시드 22 행이 그대로다.
- `/api/v1/me` 의 **401 은 정상**이다. 주체 표(P-17 의 심어 둔 계정)를 staging 에 두지 않았다 — §6 참조.
  200 이면 오히려 경계가 뚫린 것이다.

## 4. 스코프 커널·앱 롤이 staging 에서도 살아 있는가

P0 은 **일회용 DB** 에서 증명했다. 그 증명이 staging 에도 성립하는지는 별개의 질문이다 —
롤·정책·FORCE RLS 중 하나만 다르게 깔려도 조용히 무너진다. 그래서 실물에 대고 다시 물었다.

`infra/staging/scope-proof.sh` — **core-api 와 같은 앱 롤(`colab_app`)** 로 접속하고,
전부 한 트랜잭션 안에서 돌린 뒤 `ROLLBACK` 한다(staging 에 데이터를 남기지 않는다).

| # | 물은 것 | 결과 |
|---|---|---|
| ① | 스코프 없이 붙으면 `current_lab_id()` 는 | `NULL` — 기본 거부 |
| ① | 그 상태에서 **남의 연구실 행을 심으면** | `ERROR: new row violates row-level security policy for table "d1_lab_profile"` |
| ② | 스코프 안에서의 쓰기·읽기 (양성 대조군) | `1 행` — 막기만 하고 통과시키지 못하면 그것도 고장이다 |
| ③ | 같은 트랜잭션에서 **다른 연구실로 스코프를 바꾸면** | `0 행` — cross-tenant 음성 |
| ④ | 스코프를 지우면 | `0 행` |
| ⑤ | 증명이 끝난 뒤 잔여물 | `0 행` |

②가 있어야 ①③④가 의미를 갖는다. **아무것도 안 되는 DB 도 ①③④를 통과한다.**

앱 롤 속성 실측은 §2 에 있다 — `rolsuper=f` · `rolbypassrls=f` · `colab_app` 소유 테이블 **0**.
`P0-rls-proof.md` 의 숫자와 같다.

## 5. 터널·라우팅 — 변경분 0, 그리고 그것이 결론이다

**터널 선언을 한 글자도 고치지 않았다.** IS2 가 `www.colab-hydro.com → http://nginx:80` 하나를
레포의 산출로 만들어 뒀고, 이번 WU 는 5개 단위를 가르는 일을 **오리진 안쪽에서** 처리하도록 설계했기 때문이다.

호스트명마다 ingress 를 늘리는 길도 있었지만 택하지 않았다.
그 길은 ① 매 단위마다 DNS 레코드와 엣지 규칙이 늘고 ② 노출면이 5배가 되며
③ 무엇보다 **staging 라우팅을 바꾸는 일이 곧 Cloudflare 를 바꾸는 일**이 된다.
오리진 안쪽 nginx 는 롤백이 컨테이너 교체 한 번이다 — §3 의 무중단 롤백이 그 덕이다.

레포 선언과 실물이 같다는 증명:

```
$ terraform plan          # infra/staging/tunnel/
```

**대시보드는 손으로 건드리지 않았다.** IS2 가 되돌린 것이 정확히 그 습관이다.

## 6. 아직 비어 있는 것 · 다음 WU 가 채울 것

| # | 비어 있는 것 | 지금 무엇이 대신 서 있나 | 채울 곳 |
|---|---|---|---|
| 1 | **주체 표(인증)** — `COLAB_CORE_SUBJECTS_FILE` 을 staging 에 두지 않았다. `/api/v1/me` 는 **401**이다 | 계약이 정한 그대로의 401 `ErrorEnvelope` | **P1**. 심어 둔 토큰(P-17)을 staging 에 어떻게 넣을지는 배포 배관이 아니라 인증 결정이다 |
| 2 | **staging 시드 데이터** — 두 체인 다 스키마만 있고 platform 은 0 행 | 없음 | 시드를 staging 에 두는 것 자체가 판단이다. `tests/fixtures/seed.sql` 을 그대로 밀어 넣지 않았다 — 테스트 픽스처와 staging 데이터는 다른 것이다 |
| 3 | **pipeline-worker·viz-render·ai-service 의 실체** | liveness 응답(`implemented:false`) | P2(D5) · P3(D7) · K 트랙(D9·D10) |
| 4 | **오브젝트 스토리지** — 업로드 원본이 갈 곳이 없다 | 없음 | P2. 용량·보존 정책을 먼저 정해야 한다(`IS3 §5-2`) |
| 5 | **배포 자동화** — 지금은 `deploy.sh` 를 사람이 부른다 | 스크립트 2개(deploy·rollback) | **I3**. 이 스크립트가 그 파이프라인의 마지막 단계가 된다 |
| 6 | **레디니스와 라이브니스의 분리** — 지금 `/healthz` 는 전부 liveness 다. core-api 가 DB 를 못 붙어도 200 이다 | 컨테이너 헬스체크 + postgres `pg_isready` 의존 | 뒷단이 늘어나는 WU. 지금 만들면 확인할 뒷단이 하나뿐이라 껍데기다 |
| 7 | **HTTPS 오리진 구간** | 터널 안쪽은 평문 HTTP (PoC 와 같음) | I1/I5. 엣지 종료 정책과 함께 정한다 |

### 곧바로 열리는 것 — IS3

`IS3 §6` 이 「1번(I2 로 staging postgres 가 올라온다)이 열리는 즉시 2·3 은 한 세션 안에 끝난다」고 적어 뒀다.
**1번이 지금 열렸다.** 붙일 값은 이것이다(실값은 홈의 백업 env 파일에):

```
COLAB_BACKUP_TARGET=postgres
COLAB_BACKUP_PG_CONTAINER=colab_v2_staging_pg
COLAB_BACKUP_PG_DB=colab_platform
COLAB_BACKUP_PG_USER=postgres
```

**이 WU 에서 실행하지 않았다.** IS3 는 다른 레인의 WU 고, 그 레인의 완료 판정(백업 1회 + 복원 1회)은
그쪽에서 증거를 남겨야 한다. 여기서는 **진입조건이 열렸다는 사실만** 넘긴다.
`db/ai` 는 아직 백업 대상이 아니다 — 체인이 분리라 프로파일이 하나 더 필요하다(`IS3 §5-3`).

## 7. 이 WU 가 레포에 남긴 것

| 경로 | 무엇 |
|---|---|
| `infra/staging/compose.i2.yml` | walking skeleton 스택 — 5개 단위 + postgres + 엣지 + 러너 2개(profile) |
| `infra/staging/nginx.i2.conf` | 엣지 라우팅 (헬스 5경로 · `/api/v1/` · `/`) |
| `infra/staging/deploy.sh` · `rollback.sh` | 배포·롤백. 대칭이고, 롤백이 데이터를 지우지 않는다 |
| `infra/staging/db-bootstrap.sh` | `roles` / `app-grants` / `verify` — 스키마는 만들지 않는다 |
| `infra/staging/scope-proof.sh` | staging 실물에 대고 도는 경계 증명 |
| `infra/staging/migrator/Dockerfile` | 체인 러너 (앱 이미지와 분리) |
| `services/*/Dockerfile` (4개) · `frontend/Dockerfile` · `frontend/nginx.conf` | 이미지 정의 |
| `services/{pipeline-worker,viz-render,ai-service}/src/*/app/health.py` | liveness — 표준 라이브러리만 |
| `services/core-api/src/colab_core/app/main.py` | `/healthz` 라우트 1개 (계약 밖·DB 미접촉) |

`compose.yml`(자리표시)은 **지우지 않고 남겼다.** 그게 롤백 대상이다.
`gates/` · `contracts/` · `db/` 는 손대지 않았다.

**비밀은 전부 홈의 0600 파일에만 있다.** 이번에 늘어난 키는 넷이고(DB 비밀 3 + 데이터 디렉터리 경로 1),
값은 이 문서에도 레포에도 없다. 절대경로도 없다.
