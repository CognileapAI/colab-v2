# 배포 정책 전용 브랜치 인계

사용자 요청: “배포 정책은 브랜치 새로파서 거기에 분리해서 넣어줄래? 여기선 ai검색 개발 재개하려고하는데”.

브랜치: `codex/deployment-policy`. 분기 기준: `d5867e0f` (local-stage의 ST 온톨로지 보호 적용 기록). 이 브랜치에서 배포 정책 후속을 진행하며 AI 검색 기능 변경은 넣지 않는다. 현재는 계획 인계이며 아래 후속 구현은 미착수다.

## 작업 순서

1. 실행 계정과 권한 조사: 에이전트의 Docker·sudo·postgres 관리자 접속 및 PGDATA 직접 접근 경로를 실제로 확인한다. 비밀은 출력하지 않는다.
2. 개발 계정과 관리 계정 분리: 개발자는 작업 저장소·일회용 DB만 사용한다. 관리자 자격은 개발 프로세스에서 접근할 수 없는 별도 주체가 보유한다. 현재 세션의 권한을 임의로 제거해 작업을 끊지 말고 전환·복구 경로를 먼저 검증한다.
3. 제한된 배포 실행기: 검증된 커밋만 입력받아 백업→온톨로지 보호 검사→배포→검증을 실행한다. 임의 셸/SQL 전달 통로를 열지 않는다.
4. 환경별 배포 원천 강제: ST(local-srv)=local-stage, DEV(AWS)=main, PR(AWS 운영)=production. cron 재설치에도 명시한 원천을 보존한다. 현재는 실제 ST cron 환경 선언만 반영돼 있고 스크립트 기본값 main 및 직접 실행 검사는 후속이다.
5. AWS 온톨로지 보호: RDS 관리자 권한의 특성을 고려한 소유권 분리와 백업·마이그레이션을 검증한다. ST용 보호 설치기는 AWS를 지원하지 않는다.
6. 검증: 직접 DB 삭제/PGDATA 삭제/관리자 역할 획득/잘못된 브랜치 배포는 거부되고 정상 ST 배포는 성공한다. 파괴 시험은 일회용 복제 환경에서만 한다.

## 완료와 승인 경계

- 상태 정본 `dev-package/work-items.yaml`의 ONTO-PROTECT는 open이다. 일반 ST 배포/앱 역할 삭제 차단만 적용됐으며 관리자/root/Docker 권한 분리와 AWS 보호는 미완료다.
- ST 온톨로지 5표103행은 보호 적용 전후 동일하다. 이미 적용한 보호를 되돌리지 않는다. `infra/staging/ontology-protection.sql`과 `verify/verify-ontology.sh`, `sessions/20260913-ontology-protection.md` 참조.
- 배포 정책 논의·브랜치 분리가 main/DEV/운영 배포나 운영 자원 생성 승인을 의미하지 않는다. 현재 승인된 배포 범위는 local-stage/ST까지다.
- production은 첫 운영 승인 커밋에서 생성할 계획이며 아직 만들지 않았다.
- 이 브랜치는 별도 task를 자동 실행하지 않는다. 별도 작업을 시작할 때 이 파일을 진입점으로 사용한다.
