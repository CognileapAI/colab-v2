# WU-I3 — 배포 자동화 (커밋 → 빌드 → staging 자동 배포)

> **읽는 순서** `CLAUDE.md` → `03-HANDOFF.md` → 이 문서 → 해당 레인 절. 이 문서가 I3 의 작업 정본이다.
> **진입조건은 열려 있다** — `WORK-UNITS.md` I3 행의 진입조건은 **I2** 하나이고, I2 는 ✅ 다.
> **I2 를 지났으므로 완료 판정에 `staging 배포 green` 이 붙는다**(`WORK-UNITS.md §4` · `CLAUDE.md §4`).
>
> **이 WU 는 배포 경로 자체를 고친다.** 다른 레인이 staging 에 대고 시험 중일 수 있으므로,
> 실배포는 **다른 레인이 전부 닫힌 뒤** 한 번에 몰아서 한다(§5-7).

## 0. 이 WU 의 조직 목표 — **배포가 자기 자신에 대해 참말을 하게 만든다**

`03-HANDOFF §5.5` 의 **DR-4 · DR-5 · DR-6 세 줄이 I3 소유**다. 셋을 각각의 결함으로 세면 이 WU 를 잘못 읽는다.
**하나의 증상이 세 자리에 나타난 것**이고, 뿌리도 하나다 —

> **배포 도구가 자기 능력을 실제보다 크게 말한다. 검증한 것보다 많이 단언한다.**

| 얼굴 | 도구가 하는 말 | 실제 | 정본 |
|---|---|---|---|
| **DR-4 — 무엇을 굽는가** | 「배포되는 것이 **커밋의 산출**」(주석) | **워킹트리**를 굽는다. 배포 순간의 파일시스템이 올라간다 | `03-HANDOFF §5.5` DR-4 |
| **DR-5 — 무엇으로 돌아갈 수 있는가** | `rollback.sh` 가 있으니 되돌릴 수 있다 | 태그가 `:i2` 고정이라 **직전 이미지가 이름을 잃는다.** 돌아갈 대상이 없다 | 같은 절 DR-5 |
| **DR-6 — 무엇이 성공했는가** | `exit 0` | 앱 5종이 `health: starting` 인 채로 0 을 반환한다. **판정은 `dc ps` 뿐** | 같은 절 DR-6 |

**세 줄의 공통 형태는 「모른다」를 「성공」으로 바꿔 말하는 것이다.** 이건 이 레포의 표준 keep 과 정확히 반대다 —
`㊺`·`㊽`·`D3b` 가 전부 **「모르면 red 를 내라」**(fail-closed) 위에 서 있는데, 지금의 `deploy.sh` 는 **fail-open** 이다.
따로따로 고치면 이 성질이 보이지 않는다. **I3 의 산출은 「배포가 빨라진 상태」가 아니라 「배포가 하는 말이 검증 가능해진 상태」다.**

### 0-1. 실측 증거 — 이론이 아니다

- **2026-08-23 P1 배포**: `deploy.sh` 가 **컨테이너가 아직 `starting` 인 상태에서 `exit 0`** 을 냈다.
  그 배포가 green 으로 판정된 것은 **사람이 따로 기다렸다가 헬스 6종을 확인해서**이지, 스크립트가 판정해서가 아니다.
- 즉 **현재 파이프라인의 판정기는 사람이다.** 트리거만 자동화하면 그 사람이 사라진다 — 판정기 없이 도는 파이프라인이 된다.

### 0-2. 주석 정정은 곁다리가 아니라 작업 항목이다

**거짓말하는 주석 2개는 그것이 설명하는 코드와 같은 변경 안에서 고친다.**

| 위치 | 지금 적힌 말 | 왜 고쳐야 하는가 |
|---|---|---|
| `deploy.sh:13` | 「배포되는 것이 커밋의 산출이 되도록 이미지 안에서 빌드한다」 | 코드는 워킹트리를 굽는다. **읽는 사람은 SHA 재현성이 보장된다고 믿는다**(DR-4) |
| `deploy.sh:16` | 「앱보다 postgres 가 먼저 healthy 여야 한다」 | 헬스가 판정에 **필요하다는 것을 알면서** postgres 에만 걸었다. 앱 5종은 비어 있다(DR-6) |

**옳은 구현을 거짓 주석 아래에 놓으면 다음 읽는 사람에게 같은 문제를 다시 만든다.**
DR-4·DR-6 이 위험한 이유의 절반은 코드가 아니라 **주석이 코드를 대신 증언했다**는 데 있다.
따라서 **주석이 정정되지 않은 커밋은 해당 항목의 완료로 치지 않는다**(§6-12·§6-13).

### 0-3. 순서 규칙 — **태그 보존은 빌드보다 먼저다**

DR-5 의 처치 순서는 이번 세션에서 실증됐다.

1. **빌드 전에** 현행 이미지 5종을 `:prev` 로 태그한다(`docker tag …:i2 …:prev`).
2. 그 다음 빌드한다.
3. **빌드 후에는 늦다** — `:i2` 는 이미 새 이미지를 가리키고, 직전 이미지는 이름 없는 dangling 이 된다.

> **이번 세션의 P1 배포는 이 순서대로 했고**, 보존된 5종의 **이미지 ID 가 새 이미지와 전부 다름**을 확인했다.
> 즉 되돌릴 대상이 실제로 남았다. **`rollback.sh` 를 고치는 일보다 이 순서가 먼저다** — 스크립트가 옳아도 돌아갈 이미지가 없으면 소용없다.

**아래 §2 의 현행 실측은 그대로 유효하다.** 이 절은 그 발견을 **다시 묶는 것**이지 대체하지 않는다 —
§2-3 = DR-5 의 하류, §2-4 = DR-5, §2-5 = DR-6, 그리고 §2-2 의 1번은 **DR-4 로 뒤집혔다**(아래).

## 1. 범위

정본 `WORK-UNITS.md` I3 행 그대로 — **「배포 자동화 — 커밋 → 빌드 → staging 자동 배포. prod 는 승인 게이트」**,
완료 오라클 **「파이프라인 1회 완주」**.

| # | I3 가 덮는 것 | 왜 여기인가 |
|---|---|---|
| 1 | **트리거** — `main` 에 커밋이 들어오면 사람이 부르지 않아도 파이프라인이 돈다 | 정본 문구의 「커밋 →」가 이것이다 |
| 2 | **빌드** — 커밋을 이미지로 굽고, **그 이미지가 어느 커밋의 산출인지 이름에 박는다** | 지금은 태그가 `:i2` 고정이라 두 릴리스가 구분되지 않는다(§2-4) |
| 3 | **배포** — 게이트 → 백업 → 마이그레이션 → 교체 → **배포 후 검증**까지 한 흐름 | `deploy.sh` 는 ⑥에서 끝나고 자기 결과를 묻지 않는다(§2-2) |
| 4 | **롤백** — 「직전 **릴리스**」로 되돌아가고, 그것이 자동으로 증명된다 | 지금 `rollback.sh` 는 직전 릴리스가 아니라 **I2 이전 자리표시**로 간다(§2-3) |
| 5 | **승인 게이트(설계)** — prod 승격은 사람의 승인 없이는 넘어가지 않는 구조 | 정본의 「prod 는 승인 게이트」 · 결정 `㊵` |

### 범위 밖 — 명시한다

| 밖 | 근거 |
|---|---|
| **prod 로의 실배포 · AWS 자원 생성 · I0·I1·I5 착수** | 결정 `㊻`. **AWS 는 보류다.** v2 완주 판정은 `staging 배포 green` 까지 |
| **살아 있는 prod 에 배선된 승인 게이트** | 대상이 없다. I3 는 **게이트를 설계·구현하되 타깃을 staging 하나로 둔다.** prod 타깃 자리는 비워 두고, 열리는 조건(`㊻-③`)을 문서로 못 박는다 |
| 분산 추적 · 로그 집계 · 알람 · 시점 복구 리허설 | **I4** 의 몫이다(`WORK-UNITS.md` I4 행). I3 는 파이프라인이 남기는 **원장과 로그의 자리만** 만든다 |
| push 알림 채널(메일·메신저) | `IS3 §12-2` 와 같은 이유로 **레포 밖 결정**이다. 정본 확인 필요 → `[정본 무근거]` |
| 오브젝트 스토리지 · 시드 데이터 · 레디니스/라이브니스 분리 | `I2 §6` 의 2·4·6 번. 각각 P2 · P2 · 뒷단이 늘어나는 WU |
| 게이트 자체의 신규 구현 (`generated-up-to-date`) | 별도 착수 항목이다(`03-HANDOFF` 상단). I3 는 **기존 게이트를 파이프라인에 배치**할 뿐 게이트를 새로 쓰지 않는다 |
| 도메인 코드 · 계약 | 한 줄도 건드리지 않는다. I3 는 배포 배관이다 |

**타깃은 staging 하나다.** 승인 게이트는 **구조로 존재하되 건너편이 비어 있는 상태**로 만든다 —
비어 있다는 사실이 코드와 문서에 적혀 있어야 하고, 나중에 `㊻` 이 열릴 때 **타깃 하나를 추가하는 일**이어야 한다.

## 2. 현행 실측 — `deploy.sh` · `rollback.sh` 가 지금 하는 일

파일을 읽어서 적는다. 이 절의 모든 문장은 `infra/staging/deploy.sh` · `rollback.sh` · `compose.i2.yml` ·
`compose.yml` · `db-bootstrap.sh` · `README.md` 의 실제 내용이다. **실행하지 않았다**(다른 레인이 staging 을 쓰고 있다).

### 2-1. `deploy.sh` — 7 단계

| 단계 | 하는 일 | 판정 |
|---|---|---|
| — | `ENV_FILE` = `COLAB_STAGING_ENV` 또는 홈의 `.colab-v2-staging.env`. `set -a; . "$ENV_FILE"` 로 주입 | **비밀은 레포 밖.** 유지한다 |
| ① | `dc --profile migrate build` — 5개 단위 + 러너 2개를 **이미지 안에서** 빌드 | **I3 가 요구하는 「빌드」의 절반은 이미 여기 있다.** 호스트 산출물을 복사하지 않는다 |
| ② | `up -d postgres` → `docker inspect` 로 `healthy` 를 최대 120초(60×2s) 대기 | 대기는 한다. **다만 60회를 다 써도 루프를 그냥 빠져나온다** — 타임아웃이 실패가 아니다(§2-5) |
| ③ | `db-bootstrap.sh roles` — 롤 2개 + 데이터베이스 2개 | 순서(롤→마이그레이션→GRANT)가 맞다 |
| ④ | `run --rm migrate-platform upgrade head` · `migrate-ai upgrade head` — **체인별로 따로, 소유자 롤로** | `CLAUDE.md §3-3` 준수. **자동화에서도 이 분리를 깨지 않는다** |
| ⑤ | `db-bootstrap.sh app-grants` — GRANT + `NOBYPASSRLS`·비소유자 fail-closed 검사 | 앱 롤 경계가 여기서 강제된다 |
| ⑥ | `up -d --remove-orphans` — 5개 단위 + 엣지 교체 | 무중단 교체(터널·DNS 미접촉) |
| ⑦ | `dc ps` | **사람이 눈으로 본다.** 기계 판정이 아니다 |

`set -euo pipefail` 이라 각 단계의 non-zero 는 즉시 중단이다. 여기까지는 성립한다.

### 2-2. 이미 I3 를 만족하는 것 — 다시 만들지 않는다

1. ~~**빌드가 커밋의 산출이다**~~ → **틀렸다. DR-4 로 뒤집혔다.** `build` 를 이미지 안에서 도는 것은 맞으나,
   빌드 컨텍스트가 **워킹트리**이므로 산출은 커밋이 아니라 **배포 순간의 파일시스템**이다. PoC 의 "8주 전 수동 빌드 이미지"
   실패는 **절반만** 뒤집혔다 — 호스트 산출물 복사는 없어졌지만 **SHA 로 특정할 수 없다**는 성질은 남았다(`§0`).
   **이 줄이 원래 「이미 만족」 목록에 있었다는 사실 자체가 DR-4 의 증상이다** — 주석이 사람을 속인 것과 같은 경로로 문서도 속았다.
2. **마이그레이션이 `up -d` 에 딸려 오지 않는다** — profile `migrate` 뒤에 있고 배포 절차가 명시적으로 부른다.
3. **두 체인이 갈라진 채로 돈다** — 러너가 둘, version_table 이 둘, 접속 문자열이 둘.
4. **앱 롤 fail-closed 검사가 배포 경로 안에 있다**(⑤). 파이프라인이 이걸 우회하면 P0 의 경계 증명이 무효가 된다.
5. **터널·DNS 를 건드리지 않는다** — 전파 대기가 없고 롤백이 컨테이너 교체 한 번이다.
6. **호스트 노출이 `127.0.0.1:3000` 하나뿐**이다. 자동화가 포트를 늘려서는 안 된다.

### 2-3. 못 미치는 것 ①: **롤백이 「직전 릴리스」가 아니다**

`rollback.sh` 는 `compose.yml` 로 `up -d --remove-orphans` 한다. `compose.yml` 은 **I2 이전 자리표시 오리진**
(nginx + cloudflared 둘뿐, 안내 페이지)이다. 즉 지금의 롤백은

> **「직전 릴리스로 되돌린다」가 아니라 「제품 이전 상태로 되돌린다」**

이다. I2 시점에는 그게 정확히 직전 상태였으므로 옳았다. 그러나 릴리스가 둘 이상 쌓이는 순간
이 스크립트는 **N-1 이 아니라 0 으로 간다.** I3 의 「파이프라인 1회 완주」에 롤백이 포함되는 이상, 여기가 본체다.

원인은 하나다 — **어디에도 「직전에 green 이었던 릴리스가 무엇인가」를 적어 두는 자리가 없다.**

### 2-4. 못 미치는 것 ②: **이미지 태그가 릴리스를 구분하지 않는다**

`compose.i2.yml` 의 태그는 `colab-v2/core-api:i2` 처럼 **전부 고정 `:i2`** 다.
빌드할 때마다 같은 이름을 덮어쓰므로,

- 지금 돌고 있는 컨테이너가 **어느 커밋의 산출인지 이미지 이름으로는 알 수 없고**,
- 이전 이미지는 **이름을 잃은 dangling 이미지**가 되어 되돌릴 손잡이가 없다.

`compose.i2.yml` 이라는 **파일 이름 자체가 WU 이름**인 것도 같은 문제의 표면이다. 릴리스가 늘어나면
`compose.i3.yml`·`compose.i4.yml` 이 생기거나, 아니면 이름과 내용이 어긋난다.

### 2-5. 못 미치는 것 ③: **배포가 자기 결과를 묻지 않는다**

- ⑦ 이 `dc ps` 로 끝난다. **헬스 6종(루트 + 단위 5)을 확인하지 않는다.**
- ② 의 healthy 대기가 타임아웃해도 그대로 ③ 으로 넘어간다.
- `I2 §3` 이 이미 증명한 것 — **상태 코드만으로는 판정할 수 없다.** 자리표시 오리진은 모든 경로에 200 을 준다.
  **응답 코드 + 본문**을 같이 봐야 "무엇이 서빙되고 있는가"가 판정된다. 그 판정 로직이 지금은 **사람 머릿속에만** 있다.
- `RESTART.md §2-③` 이 같은 이유로 「루트 하나만 보고 넘어가지 않는다」를 문서로 못 박아 뒀다.
  그 문장이 **스크립트가 되어야** I3 다.

### 2-6. 못 미치는 것 ④: **트리거가 사람이다**

`I2 §6-5` 가 그대로 적어 뒀다 — 「배포 자동화 — 지금은 `deploy.sh` 를 사람이 부른다 … **I3**. 이 스크립트가
그 파이프라인의 마지막 단계가 된다」. 커밋과 배포 사이를 잇는 것이 아무것도 없다.

`.github/workflows/ci.yml` 은 있다(`push: main` · `pull_request`). 그러나 그것은 **`ubuntu-latest` 클라우드 러너**이고,
이 WSL 호스트에 **닿을 수 없다.** 인바운드 경로가 터널 하나뿐이고 그 터널은 `www → nginx:80` 한 줄이다(`IS2`).
즉 **클라우드 CI 는 빌드·게이트까지만 할 수 있고, 배포는 호스트 쪽에서 당겨 와야 한다.**

### 2-7. 못 미치는 것 ⑤: **배포 전 백업이 없다 · 동시 실행 잠금이 없다**

- IS3 가 백업·복원을 **실 staging 대상으로** 세워 뒀다(`backup.sh` 두 프로파일 · `restore-rehearsal.sh`).
  그런데 `deploy.sh` 는 ④ 에서 **마이그레이션을 돌리기 직전에 백업을 부르지 않는다.**
  스키마를 바꾸는 순간이 데이터가 가장 위험한 순간인데, 그 앞에 아무것도 없다.
- `deploy.sh` 를 두 번 겹쳐 부르는 것을 막는 장치가 없다. 자동 트리거가 붙는 순간 이건 가정이 아니라 시간문제다.

## 3. 결정해야 할 것 — 포크와 권고

**레인이 임의로 정하지 않는다.** 아래 6건은 이 문서가 권고를 달아 두되, 채택은 세션 시작 시 확정하고
`PLAN-SoT §9` 에 값과 근거를 적는다(`CLAUDE.md §6-3`).

### 결정 1 — 무엇이 파이프라인을 켜는가

이 호스트에는 **클라우드 CI 계정으로 접근할 수 있는 배포 대상이 없다**(`㊻` 으로 AWS 는 닫혀 있고,
staging 은 인바운드가 터널 한 줄뿐인 WSL2 + Docker Desktop 이다).

| 안 | 내용 | 대가 |
|---|---|---|
| **A. 호스트 폴링** | 호스트의 워처가 주기적으로 `git fetch` → `origin/main` 이 앞서 있으면 파이프라인 1회 | 커밋→배포 지연이 폴링 주기만큼. 호스트가 꺼져 있으면 안 돈다 |
| B. self-hosted runner | GitHub Actions 러너를 이 호스트에 등록 | **레포가 public 이다**(`R1`). self-hosted 러너를 public 레포에 붙이면 외부 PR 이 이 호스트에서 코드를 실행할 수 있는 구조가 된다. 방어를 걸 수는 있으나 **노출면을 늘리는 방향**이다 |
| C. 인바운드 webhook | 터널에 webhook 엔드포인트를 하나 더 판다 | `IS2` 가 ingress 를 **`www→nginx:80` + catch-all 404 둘뿐**으로 좁혀 놓은 것을 되돌린다. 인증까지 직접 만들어야 한다 |

**권고 = A(호스트 폴링).** 이유 셋 — ① **인바운드를 0 으로 유지한다**(IS2 가 만든 상태를 깨지 않는다)
② 자격증명이 **읽기 전용 git fetch** 하나로 끝난다 ③ 호스트가 꺼져 있으면 안 도는 성질이 **정직하다** —
`RESTART.md` 가 이미 「staging 은 자동으로 뜨지 않는다」를 전제로 서 있다.
클라우드 CI(`ci.yml`)는 **게이트·빌드 검증**을 계속 맡고, **배포 권한은 갖지 않는다.** 역할이 갈린다.

> 폴링 주기 값 · 워처를 systemd 로 걸지 cron 으로 걸지 → **`[정본 무근거]`**. 세션에서 정하고 근거를 적는다.
> (IS3 의 크론이 이 호스트에서 실제로 돌고 있음은 확인된 사실이다 — `IS3 §10`.)

### 결정 2 — 빌드 산출물이 어디에 사는가

| 안 | 내용 | 대가 |
|---|---|---|
| **A. 호스트 로컬 이미지 + 커밋 SHA 태그** | `colab-v2/core-api:<short-sha>` 로 굽고 `:current` 를 옮긴다. 최근 N 개 태그를 남긴다 | 호스트가 죽으면 이미지도 죽는다. 대신 **커밋에서 재생 가능**하다 |
| B. GHCR 푸시 후 호스트 pull | 원격 레지스트리에 보관 | 자격증명·용량·**public 레포의 이미지 공개 범위** 판단이 새로 필요하다. staging 하나뿐인 지금 이득이 적다 |

**권고 = A.** 근거 — 이미지는 **커밋의 결정론적 산출**이므로 원본은 git 이다(레지스트리는 캐시지 진실원이 아니다).
`㊻` 으로 대상이 staging 한 대뿐인 동안 B 는 비용만 늘린다. **다만 태그를 SHA 로 바꾸는 일은 반드시 한다**(§2-4).

**그리고 SHA 태깅이 붙기 전까지의 잠정 규칙 — 태그 보존을 빌드 앞에 둔다**(§0-3).
SHA 태깅이 완성되면 `:prev` 는 원장의 「직전 green」으로 대체되지만, **그때까지도 빌드 전 보존은 유지한다.**
**빌드가 먼저 돌면 되돌릴 대상이 그 시점에 이미 사라진다** — 이건 순서의 문제이지 스크립트 품질의 문제가 아니다.
또한 **빌드 대상을 워킹트리에서 커밋으로 옮기는 변경과 `deploy.sh:13` 주석 정정은 같은 커밋에 넣는다**(§0-2).

> 레지스트리 사용 여부 · 이미지 보존 개수 → **`[정본 무근거]`**.

### 결정 3 — 릴리스를 무엇으로 기억하는가

롤백이 「직전 릴리스」로 가려면 그 사실이 **호스트 위 파일**로 남아야 한다.

**권고** — `infra/staging/` 아래에 릴리스 원장을 둔다(레포 밖 홈이 아니라 **레포 산출**로 두되 값은 런타임 생성물,
`.gitignore` 로 커밋 차단). 한 줄에 **커밋 SHA · 이미지 태그 · 시각 · 배포 판정(green/red) · 롤백 여부**.
`rollback.sh` 는 **원장에서 「직전 green」을 읽어** 그 태그로 되돌린다.

`compose.i2.yml` 은 **파일명을 릴리스 중립으로 바꾸고**(예: 스택 정의는 하나, 태그만 변수) `compose.yml`(자리표시)은
**지우지 않는다** — 그건 여전히 「제품 이전」으로 가는 마지막 손잡이다. **롤백 대상이 두 종류라는 사실을
문서와 명령에 드러낸다**(직전 릴리스 / 자리표시).

> 원장 파일 형식 · 보존 개수 → **`[정본 무근거]`**. `IS3 §10` 의 표식 파일 3종(`BACKUP-FAILED.txt` 등)이
> 이미 같은 계열의 관행이므로 그것과 모양을 맞추는 것을 권한다.

### 결정 4 — 두 postgres 체인에 대해 마이그레이션을 어떻게 세우는가

두 체인은 **다른 데이터베이스**이고 합치지 않는다(`CLAUDE.md §3-3` · `I2 §2` · `IS3 §7`).
자동화가 새로 답해야 하는 것은 **순서·전제·되돌림** 셋이다.

**권고**

1. **마이그레이션 앞에 IS3 백업을 강제한다** — `backup.sh` GREEN(**두 프로파일 전부**)이 아니면 배포를 중단한다.
   `IS3 §7` 이 「한쪽만 덮은 백업이 전체 성공으로 기록되는 것」을 F9 fixture 로 못 박아 뒀다. 그 판정을 그대로 쓴다.
2. **순서는 `deploy.sh` 의 ③→④→⑤ 를 그대로 보존한다.** GRANT 를 테이블보다 먼저 주면 `GRANT ON ALL TABLES` 가
   빈 집합에 걸려 **조용히 아무것도 안 준다**(`I2 §2`). 이건 이미 값을 치르고 알아낸 순서다.
3. **체인은 끝까지 따로 돈다.** 러너 한 번에 두 체인을 돌리는 "최적화"를 하지 않는다.
4. **마이그레이션은 forward-only 로 간주한다** — 롤백은 **이미지만** 되돌리고 스키마는 되돌리지 않는다.
   따라서 **한 릴리스의 마이그레이션은 직전 이미지와도 호환되어야 한다**(추가는 되고 파괴는 안 된다).
   이걸 지키지 못하는 변경은 **배포 자동화가 아니라 사람이 처리할 사건**으로 분류하고 멈춘다.
5. 배포 전에 `migration-single-head` 게이트를 **호스트에서 다시** 돈다(클라우드 green 을 신뢰로 대체하지 않는다).

> 「이미지 롤백 시 스키마를 그대로 둔다」는 판단은 **정본에 명시가 없다** → **`[정본 무근거]`**로 표시하되,
> 되돌리는 마이그레이션이 데이터를 지울 수 있다는 점에서 **`rollback.sh` 의 기존 원칙(「롤백이 데이터를 지우면
> 그건 롤백이 아니라 재해다」)의 직접 연장**이다. 세션에서 확정한다.

### 결정 5 — 배포 성공·롤백 성공을 무엇으로 판정하는가

**권고 = `I2 §3` 의 판정 방법을 스크립트로 옮긴다.** 새 기준을 만들지 않는다.

- **헬스 6종**(`/healthz` + `/healthz/{core-api,pipeline-worker,viz-render,ai-service,frontend}`)이 **전부 200**.
- **본문까지 대조한다** — 각 단위가 **자기 `unit` 이름**으로 대답해야 한다. 200 만으로는 자리표시와 구분되지 않는다.
- `docker ps` 헬스체크가 **8개 전부 `healthy`**(`RESTART.md §2-③` 의 그 목록).
- **호스트 노출 검사** — `0.0.0.0` 바인딩 **0 건**(`I2 §2` 노출 정책).
- 실패하면 **자동으로 직전 green 릴리스로 되돌리는가**는 별도 판단이다 → **`[정본 무근거]`**.
  권고는 **① 판정 red → 배포 중단 + 표식 파일 + 사람 호출**을 기본으로 하고, 자동 롤백은 **명시 옵션**으로 둔다.
  판정기를 신뢰하기 전에 자동 되돌림을 켜면 **멀쩡한 릴리스를 판정 버그가 계속 걷어내는** 상태가 된다.

### 결정 6 — prod 승인 게이트를 어떤 모양으로 남기는가

정본이 「prod 는 승인 게이트」라고만 적었고, `㊵` 이 **승인의 성질**을 이미 정해 뒀다 —
① 구현·확인은 전부 staging ② **Ted 가 staging 에서 직접 보고 승인한 뒤**에 넘어간다
③ 승인 단위는 WU 가 아니라 **눈으로 확인 가능한 화면·흐름**. 그리고 `㊻` 이 **prod 착수 시점 자체를 닫아** 뒀다.

**권고** — 파이프라인에 **타깃 개념**을 도입하되 타깃 목록은 `staging` 하나로 둔다.

- `prod` 타깃은 **선언은 하되 실행 경로가 비어 있고**, 호출하면 **`㊻` 을 인용하며 즉시 거부**한다(조용한 no-op 금지).
- 승인은 **자동 판정이 아니라 사람의 기록**이다 — 원장에 `승인자·시각·무엇을 눈으로 봤는가`.
- **승인 없이 prod 타깃이 도는 경로가 존재하지 않음**을 red fixture 로 증명한다(음성 게이트, `ai-no-lineage-write` 와 같은 계열).

> 승인 기록의 보관 위치·형식·승인자 표기 → **`[정본 무근거]`**.

## 5. 멈춤 규칙

1. **게이트를 우회하거나 임시로 끄지 않는다.** 파이프라인이 게이트를 부르는 방식이지, 게이트를 파이프라인 사정에 맞추지 않는다
2. **게이트를 green 으로 만들려고 검사 대상을 줄이지 않는다** — 헬스 6종을 5종으로, 두 체인을 한 체인으로 줄이는 것이 정확히 이것이다
3. **계약을 고치지 않는다.** 34 op · 필드 · enum 동결. 고쳐야 할 것 같으면 멈추고 보고한다
4. **정본이 값을 주지 않으면 만들지 않는다** — `[정본 무근거]` 로 남기고 보고한다
5. **서브에이전트는 커밋하지 않는다.** 커밋과 `03-HANDOFF`·`PLAN-SoT` 갱신은 메인 세션만
6. **일회용 컨테이너는 레인 접두사**(`i3cd_`·`i3v_` 등)로 짓고 **호스트 포트를 공개하지 않는다.** 끝나면 지운다
7. **다른 레인이 staging 을 쓰는 동안 실배포·롤백을 돌리지 않는다.** `deploy.sh`·`rollback.sh`·`compose up/down` 은
   **파이프라인 완주 세션에서 한 번**만. 그 전까지의 검증은 일회용 대상으로 한다(`IS3 §4`·`§9` 의 관행)
8. **prod·AWS 자원을 만들지 않는다** — `㊻`. `terraform apply` 는 이 WU 의 명령이 아니다
9. **터널 선언을 고치지 않는다.** ingress 는 `www→nginx:80` + catch-all 404 **둘뿐**이다(`IS2`). 늘리려면 멈추고 보고한다
10. **호스트 노출을 늘리지 않는다** — `127.0.0.1:3000` 하나. 자동화 편의로 포트를 여는 것을 금지한다
11. **비밀·절대경로를 레포·문서에 적지 않는다**(`CLAUDE.md §3-8`·`§5`). 값은 홈의 `0600` 파일
12. **롤백이 데이터를 지우지 않는다.** pgdata 를 건드리는 롤백은 롤백이 아니다
13. **주석을 코드보다 뒤에 고치지 않는다.** `deploy.sh:13`·`:16` 은 지금 **코드와 반대되는 말**을 한다(§0-2).
    동작을 고치면서 주석을 남겨 두는 커밋을 만들지 않는다 — 그건 결함을 문서 층으로 옮기는 것이다
14. **모르면 red 를 낸다.** 대기 타임아웃·판정 불가·응답 없음은 전부 **red** 다. `exit 0` 은 **검증된 green** 에만 준다(`㊺`·`㊽`·`D3b` 계열)

## 7. 위험 · 한계 — 이 호스트에서 증명되지 않는 것

**정직하게 적는다.** 아래는 I3 를 어떻게 만들어도 **이 단일 WSL2 호스트 위에서는 증명이 성립하지 않는** 것들이다.
`㊻` 으로 AWS 가 닫혀 있는 한, 이것들은 **결손이 아니라 대상의 상태**다.

| # | 증명되지 않는 것 | 왜 |
|---|---|---|
| 1 | **호스트가 꺼져 있는 동안의 자동 배포** | 도커 데몬이 자동 기동하지 않는다(`RESTART.md §1`). 커밋이 들어와도 호스트가 꺼져 있으면 파이프라인은 **돌지 않는다.** 「커밋 → 자동 배포」는 **호스트가 켜져 있다는 조건 아래에서만** 참이다 |
| 2 | **무중단의 진짜 의미** | 배포·롤백이 컨테이너 교체라 `I2` 에서 530 구간이 없었다. 그러나 **인스턴스가 하나뿐**이라 교체 순간의 짧은 연결 단절을 부하 상태에서 잰 적이 없다. 지금의 "무중단"은 **저부하·단일 관측자 조건의 무중단**이다 |
| 3 | **동시 배포·경합** | 잠금을 걸어도 **한 호스트 안의 잠금**이다. 이 호스트가 죽는 동안의 상태 일관성은 다룰 수 없다 |
| 4 | **롤백의 데이터 측면** | 이미지만 되돌리고 스키마는 두는 설계(결정 4)는 **하위호환 마이그레이션만 온다는 가정** 위에 선다. 그 가정이 깨진 릴리스는 **자동화가 처리하지 못하고 사람이 처리해야 하는 사건**이다. 파이프라인은 그것을 탐지하지 못한다 |
| 5 | **실규모 배포 시간 · 마이그레이션 소요** | staging platform 이 사실상 0 행이다(`IS3 §8` — 「데이터 행 1건」은 `alembic_version` 한 줄). 지금 재는 배포·마이그레이션·복원 시간은 **실규모의 예측이 되지 못한다** |
| 6 | **실패가 사람에게 도달하는 경로** | `IS3 §10` 과 **정확히 같은 한계**를 물려받는다. 표식 파일·로그는 **가서 봐야 보이는 자리**다. push 알림 채널이 없으므로 자동 배포가 조용히 실패해도 **다음에 누가 볼 때까지 침묵**한다. 자동 트리거가 붙으면 이 침묵의 비용이 **I2 이전보다 커진다** — 사람이 부르던 때는 부른 사람이 결과를 봤다 |
| 7 | **호스트 밖 사본** | 백업도 이미지도 원장도 **같은 머신 1대** 위에 있다(`IS3 §5-4`). 호스트가 죽으면 파이프라인의 기억도 같이 죽는다. 복구 경로는 git 의 커밋뿐이고, 이미지는 **다시 굽는** 것이지 되찾는 것이 아니다 |
| 8 | **terraform state** | `IS4` 가 🟧 다 — 마지막 `apply` 미실행 · 맨몸 호스트 조건 미실험. I3 는 터널을 건드리지 않으므로 막히지 않지만, **호스트 상실 시 복구의 약한 고리**는 그대로다 |
| 9 | **prod 승인 게이트의 실동작** | 건너편이 비어 있다. 증명할 수 있는 것은 **「승인 없이는 넘어가지 않는다」의 음성뿐**이고, **「승인하면 넘어간다」의 양성은 증명되지 않는다.** `IS3 §3` 의 표현을 빌리면 **양성 대조군이 없는 증명**이고, 그 사실을 여기 적어 두는 것이 지금 할 수 있는 전부다 |
| 10 | **클라우드 CI 와 호스트 게이트의 이중화** | 같은 게이트를 두 곳에서 돌리므로 **두 결과가 갈릴 수 있다**(러너 OS·도구 버전 차이). 갈리면 **호스트 쪽을 정본으로 삼는다** — 배포가 일어나는 곳이 거기다. 다만 그 차이를 **자동으로 탐지하지는 못한다** |

**그리고 하나 더.** I3 가 만드는 것은 **배포를 빠르게 하는 장치가 아니라 배포를 판정하는 장치**다.
자동화 자체는 하루면 붙는다 — `deploy.sh` 를 워처가 부르면 끝이다. 이 WU 의 실제 부피는
**§0 의 세 얼굴**(DR-4 무엇을 굽는가 · DR-5 무엇으로 돌아가는가 · DR-6 무엇이 성공했는가 = §2-3~2-5 의 세 결손)이고,
그것을 고치지 않은 채 트리거만 붙이면 **사람 없이 도는, 무엇이 서빙 중인지 아무도 모르는 파이프라인**이 된다.
그건 v1 이 겪은 실패의 배포판이다.

**지금 그 판정기는 사람이다.** 2026-08-23 P1 배포가 green 이 된 것은 스크립트가 아니라 사람이 기다렸다 6종을 봤기 때문이다(§0-1).
**트리거 자동화는 그 사람을 지우는 일이다.** 그러므로 순서가 정해져 있다 — **판정기를 먼저 세우고, 그 다음에 트리거를 붙인다.**
반대로 하면 이 WU 는 **거짓말을 더 빠르게 반복하는 장치**를 만든 것이 된다.
