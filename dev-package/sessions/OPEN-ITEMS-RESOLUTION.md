## 1. `fileId` 승계 — `[정본 무근거]`, 권고 있음

### 1.1 정본이 무엇을 말하는가 — 아무것도 말하지 않는다

- 정본 전수 grep 결과 **`파일 ID`·`fileId`·`업로드 ID` 라는 어휘가 한 건도 없다.** 정본은 식별자 층을 다루지 않는다 — 화면·정책 문서이기 때문이다.
- 정본의 「승계」는 **소유권 승계(P1, A-06)** 를 가리키는 말이다 (`E-00/documents/DataModel_공통_기반.md:70-71` 「소유자 … 승계(P1)로 바뀔 수 있다 / 올린 사람 … 승계해도 그대로다」). **식별자 승계와 같은 단어를 쓰면 안 된다** — 개정문에서는 `fileId 동일성` 같은 다른 말을 쓸 것을 권한다.
- 정본이 준 인접 사실은 하나뿐이다 — **등록 전에는 저장하지 않는다**(`E-04/documents/Policy_업로드와_계보_확정.md:227` 「파일을 버리고 목록으로 돌아간다 … 등록하지 않아서 파일이 사라졌어요」). 즉 등록 전 파일은 임시물이고, 그 임시물의 ID 를 영구 레코드가 물려받을지는 **구현 결정**이다.

### 1.2 레포가 이미 정한 것 / 안 정한 것

### 1.3 두 선택지의 계보 추적 귀결

| | (가) 승계한다 — 업로드 `fileId` = `d3_file.id` | (나) D3 가 새로 만든다 |

| 위험 | 등록하지 않고 버린 업로드의 ULID 가 영구히 소모된다(ULID 공간상 무의미). 임시물 ID 가 영구 레코드 ID 가 되는 데 대한 심리적 저항 `[추론]` | 매핑 컬럼 1개 + 그 컬럼을 채우는 등록 경로 + 게이트(`G-a 식별자 도달성`)가 볼 간선 1개가 는다 |
| `CLAUDE.md §3-1` | 위반 아님 — D3 가 D5 테이블을 참조하는 것이 아니라 **같은 ULID 를 자기 PK 로 쓰는 것**뿐이다 | 위반은 아니나 bare 컬럼 1개가 는다 |

**권고 = (가) 승계한다.** 근거 — ① 봉투가 `datasetId` 를 금지한 상태에서 업로드↔등록을 잇는 값이 `fileId` 밖에 없다 ② `d3_file.dataset_id NOT NULL`(`schema.sql:275`)이라 「등록 전 파일 행」은 어차피 만들 수 없으므로 **ID 충돌 자체가 발생하지 않는다** — 승계는 「같은 ULID 를 나중에 처음으로 INSERT 한다」일 뿐이다 ③ D5 스키마가 아직 없어 비용이 0 이다.
**개정문에 적어야 할 문장** — 「등록 시 D3 파일 레코드는 업로드 세계의 `fileId` ULID 를 **자기 PK 로 그대로 쓴다.** 새로 만들지 않는다.」 + 그 근거 한 줄.
**⚠ Ted 확인 필요.** 정본에 근거가 없다. 위 권고는 계약 구조에서 나온 것이지 정본 인용이 아니다.

## 3. 렌더 실패 3종 코드값 — **종류는 해결, 값 표기만 무근거**

### 3.1 종류 3개는 정본이 준다 (감사가 「무근거」로 분류한 것은 과다)

정본 `E-03/documents/Policy_데이터셋_상세.md §8 「미리보기를 그릴 수 없을 때」` 표 7행 중, **렌더 작업이 시작된 뒤의 전부 실패**는 정확히 셋이다.

| # | 정본 상황 문구 | 정본 사용자 안내 | 파일:줄 |
|---|---|---|---|
| 1 | **그리는 서버에 연결 못 함** | "지금 미리보기를 만들 수 없어요. 잠시 뒤 다시 시도해 주세요" | `Policy_데이터셋_상세.md:203` |
| 2 | **그리다 시간 초과** | "그리는 데 너무 오래 걸려요. 조각 하나나 좁은 기간으로 다시 해 보세요" | `:202` |
| 3 | **그리다 알 수 없는 오류** | "미리보기를 만들다 문제가 생겼어요" | `:204` |

- 같은 3종이 E-04 쪽에도 대응한다(`Policy_업로드와_계보_확정.md:236`·`:237` + 개정 이력 `:271` 「실패에 서버 연결 불가·시간 초과·형식 3종을 더했고」).
- **계약이 이미 이 셋을 산문으로 정확히 인용하고 있다** — `contracts/seams/core-viz.yaml:351-353` 「그리는 서버 연결 불가 · 시간 초과 · 알 수 없는 오류 (`Policy_데이터셋_상세 §8`)」. 설계 판단도 기록돼 있다(`dev-package/sessions/D2-ai-viz.md:122`).
- **나머지 4행은 `RenderJob.failure` 가 아니다**(경계를 개정문에 함께 적을 것) — `그릴 수 없는 형식`·`기준 격자 파일 없음`·`파일이 너무 큼`(`:199-201`)은 **렌더 요청 자체의 4xx 거부**이고, `조각 일부를 못 읽음`(`:205`)은 `status=완료` + `partialFailure` 다(`core-viz.yaml:355-359`).
- 이벤트의 `FailureReason` 8값(`envelope.json:85-97`)은 **다른 축**이다 — 파이프라인 처리 실패이고, 그중 `미리보기 준비 실패`·`시간 초과` 가 인접하나 값 집합을 공유하지 않는다. 개정문에서 두 축을 합치지 말 것.

### 3.2 무근거인 것은 **값 표기 문자열 하나뿐**

- 정본은 **문장**을 주지 `code` **값 라벨**을 주지 않는다. `ErrorEnvelope.code` 는 자유 문자열이다(`contracts/schemas/common.json:28`) → 감사 I-19 는 이 지점에서만 유효하다.
- 표기 규칙은 이미 못 박혀 있다 — **「enum 값은 정본 한국어 표기 그대로. 영문 코드값을 만들면 정본에 없는 어휘를 새로 만들고 코드↔DB↔화면 사이에 매핑 테이블이 생긴다」**(`contracts/schemas/common.json:4` · `PLAN-SoT §9-㉗`).

**권고** — `common.json` 에 `RenderFailureCode` 를 신설하고 **정본 상황 문구를 그대로** 값으로 쓴다.

```
"RenderFailureCode": { "enum": ["그리는 서버에 연결 못 함", "그리다 시간 초과", "그리다 알 수 없는 오류"] }
```

- `core-viz.yaml` 의 `RenderJob.failure.code` 를 이 enum 으로 좁힌다(`ErrorEnvelope` 는 그대로 두고 `code` 만 제약하거나, `failure` 를 전용 타입으로 분리).
- **효과** — 감사 `G-d`(공유 값 집합 재선언)가 이 자리를 자동으로 지킨다. 사용자 문구는 **싣지 않는다** — `envelope.json:86` 과 같은 이유로 문구는 화면이 소유한다.
- **⚠ Ted 한 줄 확인 필요.** 값을 정본 문장 그대로 쓸지(권고), 더 짧은 라벨(`연결 불가`·`시간 초과`·`알 수 없는 오류`)로 줄일지는 표기 판단이다. **셋의 개수와 의미는 확인 대상이 아니다 — 정본이 이미 정했다.**

## 4. 「업로드 seam」의 형태 — 별도 파일이 아니라 `fe-core.yaml` 안의 op

### 4.1 이미 난 결정이 답을 절반 좁힌다

- **이벤트 seam 이 정본**이라는 결정은 「업로드 세계의 **비동기** 절반이 어디 사는가」에 답했다 — `contracts/events/core-pipeline.json`. 그 파일은 **이미 존재하고 이미 동결돼 있다.**
- 남은 것은 **동기 절반**이다: FE 가 파일을 올리고(`upload.accepted` 를 촉발), 진행·실패를 묻고, 등록으로 넘기는 HTTP 표면. 이건 **FE ↔ core-api** 통신이다.
- → **「업로드 seam」이라는 제3의 seam 은 애초에 없어도 된다.** `fe-core.yaml:16` 이 가리킨 대상은 **두 조각**으로 이미 존재한다: 비동기 = `events/core-pipeline.json`, 동기 = `fe-core.yaml` 자신. **위임문이 자기 자신에게 보낸 셈이다.**

### 4.2 `contracts/README.md` 의 규칙이 파일 분리를 밀어낸다

| 규칙 | 파일:줄 | 이 항목에 대한 함의 |
|---|---|---|
| 「**seam 은 손으로 쓴다. 안정적이고 수가 적고 값이 높다**」 | `contracts/README.md:16` | 다섯 번째 파일은 「수가 적다」를 깎는다 |
| seam 목록이 **배포 단위 쌍 4개**로 열거된다(FE↔core · core↔viz · core↔ai · core↔pipeline) | `contracts/README.md:23-30` | **파일의 단위는 도메인이 아니라 배포 단위 쌍이다.** `fe-upload.yaml` 은 한 쌍(FE↔core-api)을 **파일 둘로 쪼개는 첫 사례**가 된다 |
| `fe-core.yaml` 의 tag 는 `identity·access·catalog·lineage·project·insight` — **도메인별 묶음이 이미 파일 안 장치다** | `contracts/seams/fe-core.yaml:35-46` | D5 중계 op 은 **새 tag** 로 충분하다. 파일을 늘릴 이유가 아니다 |
| 소비자는 생성물만 쓴다 | `contracts/README.md:19` | 파일을 쪼개면 FE 가 **같은 서버에 대해 클라이언트 2벌**을 갖는다 — 인증·에러 봉투·baseURL 이 두 벌로 갈린다 |

### 4.3 게이트 난이도 (감사 §5 `G-a…G-e`)

| 게이트 | 단일 파일(권고) | 별도 `fe-upload.yaml` |
|---|---|---|
| **G-a 식별자 도달성** | 동일 — 어차피 네 계약 전체를 그래프로 본다 | 동일(파일 수만 늘어남) |
| **G-b `const` 능력 주장** | **쉽다** — `source: core-api` → core-api 의 seam 파일이 하나로 확정 | **어렵다** — 「core-api 의 seam 파일」이 둘이 되어 검사기가 배포 단위→파일 **다대일 매핑 표**를 들어야 한다 |
| **G-c 짝 op 대칭** | **쉽다** — `create↔delete`·`link↔unlink` 를 한 파일 안 경로 패턴으로 뽑는다 | **어렵다** — `createDataset`(업로드 쪽) ↔ `deleteDataset`(카탈로그 쪽)이 **파일을 가로질러** 짝이 된다. 파일 단위로 보면 **거짓 red**, 안 보면 놓친다 |
| **G-d 공유 값 집합** | 동일 | 동일 |
| **G-e 산문 위임 참조 검증** | **가장 쉽다** — 위임문 자체가 사라진다(§4.4). 검사할 참조가 줄어드는 것이 가장 강한 통과다 | 통과는 하나(파일이 실재하므로) — 다만 **「실재하는 파일을 가리키기 위해 파일을 만든다」** 는 본말전도다 |
| 계약 게이트 배관 | 변경 0 | 변경 0 — `contract-breaking.sh:82` 이 `seams/*` 를 **glob** 으로 잡고 `codegen/` 에 하드코딩된 파일 목록이 없다. **기계적 비용은 어느 쪽도 없다** |

> 즉 **기계 비용은 동률이고, 게이트 *설계* 비용은 단일 파일이 싸다.** `G-b`·`G-c` 두 곳에서 「배포 단위 = 파일」이라는 단순 가정이 유지되느냐가 갈린다.

### 4.4 권고

**별도 seam 파일을 만들지 않는다. 업로드 표면은 `fe-core.yaml` 안의 op 으로 넣는다.** 함께:

1. **`fe-core.yaml:13-16` 의 위임 3줄을 고쳐 쓴다** — 이것이 `DR-7` 의 뿌리다(감사 I-02). 특히 `:16` 의 「이벤트/업로드 seam」이라는 **없는 대상**을 지우고, ① 업로드 HTTP 입구·상태 조회·등록 전환은 **이 파일이 맡는다** ② 파싱·변환의 비동기 절반만 `events/core-pipeline.json` ③ 「프로젝트 연결 생성」은 **이 파일이 맡는다**(봉투가 `projectId` 를 금지하므로 — `envelope.json:5`) 로 바로잡는다.
2. **tag 를 2개 더한다** — `ingestion`(D5 중계) · `visualization`(D7 중계). 파일 안에서 업로드·렌더 표면이 한눈에 묶인다. 도메인 경계는 **tag 와 라우터**가 지키지 파일 이름이 지키지 않는다(`CLAUDE.md §3-4` 는 core-api 에 geo **라이브러리** 금지이지 중계 op 금지가 아니다).
3. **판정 기준 한 줄을 같은 개정문에 못 박는다** — 「**FE 가 도달할 수 있는가**」(감사 선택지 C). 이 한 줄이 없으면 다음 세션이 또 「저 seam 이 맡는다」를 쓴다.

**⚠ Ted 확인 필요.** 「파일을 늘리지 않는다」는 `contracts/README.md:16`·`:23-30` 에서 **연역**한 것이지 정본이 정한 값이 아니다. 반대 논거도 정직하게 적는다 — `fe-core.yaml` 은 이미 34 op 이고 업로드·렌더 중계를 더하면 45 op 안팎이 된다 `[추론]`. **파일이 커지는 것은 사실이고, 그것이 유일한 반대 근거다.**
