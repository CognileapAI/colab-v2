## 4. Ted 판정 필요 목록 (11건)

advisor 가 올린 5건은 ①②④⑤⑥⑦⑧ 에 녹였고, 각 항 끝에 출처를 적었다.

### ① 「올리다 만 것 지우기」를 이번 묶음에 넣을 것인가

- 배경 = 업로드를 중간에 멈추면 메인 화면 위쪽에 「올리다 만 것이 있어요」 줄이 뜨고, 그 줄에는 「이어서 하기」 버튼 하나만 있다. 버리는 길이 없다. 이 요청(#32)에는 분류 표시가 붙지 않았다.
- 왜 문제인가 = 이 판정이 업로드 레인의 절단 형태를 정한다. 포함하면 폐기 동작을 세 자리가 공유하므로 공통 부품을 먼저 세워야 하고, 빼면 그 부품을 세울 근거가 없어진다(부르는 자리가 하나뿐).
- 선택지 = ⓐ 이번에 함께 고친다 ⓑ 이번엔 빼고 나중 묶음으로 돌린다.
- 고르면 달라지는 것 = ⓐ 는 화면 작업 50~90행이 늘고 레인이 4단이 되며 공통 부품을 세운다. ⓑ 는 레인이 3단이 되고 공통 부품을 세우지 않으며, 메인 화면 줄은 그대로 남아 같은 요청이 다시 들어온다.
- 출처 = advisor 9(레인 절단이 이 판정에 종속).

### ② 창을 닫을 때의 세 번째 선택지 — 만들 것인가, 「취소」는 무엇을 지우는가

- 배경 = 조사본은 이것을 「화면이 취소한다고 말하는데 취소하지 않는 결함」으로 적었다. advisor 대조 결과 그 등급이 성립하지 않는다 — 「올린 파일이 취소돼요」 문면은 **사용자가 아무것도 입력하지 않은 갈래**의 것이고, 확인 창 자체가 입력이 있을 때만 뜨므로 이 장면에서 실제로 보이는 문면은 다른 것이다.
- 왜 문제인가 = 남는 것은 결함이 아니라 **선택지를 하나 더 만들자는 제안**이다. 선택지 구성과 문면은 이전 판정(PRD-34 문면표)이 고정했으므로, 늘리려면 그 표를 고쳐야 한다. 더해서 「취소」가 무엇을 지우는지가 정해져 있지 않다 — 브라우저 기억만 지우면 서버에 올라간 것은 24시간 뒤 자동 정리까지 남고, 서버에서 즉시 지우려면 새 창구가 필요하다.
- 선택지 = ⓐ 선택지를 만들고, 「취소」는 이 브라우저에서 감추는 것으로 하되 문면이 그 사실을 말한다 ⓑ 선택지를 만들고 서버에서도 즉시 지운다(새 창구 = 계약 개정 · 별도 작업) ⓒ 만들지 않는다.
- 고르면 달라지는 것 = ⓐ 는 문면표 개정 ＋ 60~110행, 계약 변경 0. ⓑ 는 여기에 계약 개정과 서명 절차가 붙고 250행 이상이 별도로 선다. ⓒ 는 창을 닫을 때의 선택지가 둘로 유지된다.
- 출처 = advisor 1·3(등급 재분류 ＋ 문면과 처리 초안의 어긋남).

### ③ 「분석 중」에 다음 버튼을 어떻게 할 것인가

- 배경 = 파일을 올리면 서버가 확장자·용량을 확인하는 동안 「다음」 버튼이 눌리지 않는다. 화면 어디에도 왜 못 누르는지 적혀 있지 않다.
- 왜 문제인가 = 눌리지 않는 것 자체는 이미 확정된 정책이다. 승인 문서 축자 「분석이 끝나야 다음 버튼이 켜진다」·「분석 완료 전 다음 비활성; 전송100%와 분석완료 구분」(`dev-package/reports/upload-layout-preview/policy-map.md` 정책 6). 버튼을 켜는 수정은 그 판정을 뒤집는다.
- 선택지 = ⓐ 사유 한 줄을 버튼 옆에 붙이고 비활성은 유지 ⓑ 분석 중에도 누를 수 있게 바꾼다.
- 고르면 달라지는 것 = ⓐ 는 10~20행이고 기존 판정과 회귀 기준(`dev-package/prd/rounds/R-UPLOAD-PREVIEW.md` 축자 「등록 조기 활성」 미달 판정)을 유지한다. ⓑ 는 판정 재개봉이므로 승인 문서와 회귀 기준을 함께 고쳐야 한다.
- 조사 권고 = ⓐ.

### ④ 「이어서 하기」를 두 경우로 갈라 다룰 것인가

- 배경 = 「이어서 하기」가 듣지 않는다는 보고 하나에 서로 다른 두 상황이 섞여 있다. ㉠ 파일 전송이 덜 끝난 것 — 화면 부품 하나가 값을 넘겨주지 않아서 끊긴 것이고, 값 하나를 이으면 이미 있는 이어받기 경로가 그대로 동작한다. ㉡ 전송은 끝나고 등록만 남은 것 — 브라우저에 파일 실물이 없는 상태에서 입력 화면을 다시 세워야 하므로 없던 것을 새로 설계해야 한다.
- 왜 문제인가 = 조사본이 둘을 한 건으로 묶어 「배선 누락」으로 적었고, 같은 조사본의 다른 절은 「복원 경로가 애초에 없다」고 적어 서로 어긋난다. 하나로 두면 작은 수정이 새 설계에 묶여 함께 지연된다.
- 선택지 = ⓐ 둘로 갈라 ㉠ 만 이번에 고치고 ㉡ 은 설계 뒤로 돌린다 ⓑ 둘을 한 건으로 두고 함께 설계한다.
- 고르면 달라지는 것 = ⓐ 는 지금 10~30행으로 절반이 닫히고, 나머지 110~190행은 설계 뒤로 간다. ⓑ 는 둘 다 설계가 끝날 때까지 열리지 않는다.
- 출처 = advisor 2. 조사 권고 = ⓐ.

### ⑤ 그림 위 작은 축소본을 지울 것인가

- 배경 = 미리보기 그림 왼쪽 위에 64×64 크기의 작은 그림이 하나 더 보인다. 이것은 실수가 아니라 이전 결정의 산출물이다 — 코드 주석이 그 결정 번호를 직접 가리키고, 그 결정은 「렌더가 성공할수록 축소본이 안 보였다」는 문제를 닫은 것이다.
- 왜 문제인가 = 지우면 그 결정을 뒤집는다. 동시에, 그 축소본을 보여 주는 자리가 화면에 하나 더 있다(대표 그림 고르개). 그 자리가 이미 같은 목적을 채우고 있다면 지도 자리의 것은 중복이다.
- 선택지 = ⓐ 지도 자리의 축소본을 없앤다(이전 결정 재판정) ⓑ 접히는 자리 안으로 옮긴다 ⓒ 그대로 둔다.
- 고르면 달라지는 것 = ⓐ·ⓑ 는 5~15행이지만 이전 결정의 재판정 기록이 필요하다. ⓒ 는 「그림이 둘로 보인다」는 보고가 유지된다.
- 판정에 필요한 확인 = 대표 그림 고르개가 그 결정의 표시 목적을 이미 채우는가.
- 출처 = advisor 5. 조사본의 「서버가 두 산출물을 중복 생성」 가설은 그 결정 축자(「①②가 항상 함께 구워진다」)로 성립하지 않는다.

### ⑥ 파일·변수·시각 고르개를 미리보기 틀 밖으로 뺄 것인가

- 배경 = 그 고르개는 그림이 나오면 화면에서 밀려나 보이지 않는다. 조사본은 틀 밖 고정 줄로 옮기자고 적었다. 그런데 「틀 **안**의 컨트롤 줄」이라는 배치는 이전 라운드가 확정한 규약이고, 부품 머리 주석과 라운드 문서가 둘 다 그렇게 적고 있다.
- 왜 문제인가 = 틀 밖으로 옮기면 그 규약을 뒤집는다. 조사본은 반대로 「기존 취지에 부합한다」고 적었으므로, 판정 없이 착수하면 확정 규약을 조용히 바꾸게 된다.
- 선택지 = ⓐ 틀 밖 고정 줄로 옮긴다(이전 규약 재판정) ⓑ 틀 안에 둔 채 밀려나지 않게 해소한다 ⓒ 그대로 둔다.
- 고르면 달라지는 것 = ⓐ 는 20~40행 ＋ 규약 개정. ⓑ 는 틀 안에서 해소할 방법이 있는지 먼저 확인해야 한다(현재 미확인). ⓒ 는 보고가 유지된다.
- 출처 = advisor 6.

### ⑦ 확대·축소 버튼의 자리를 어떻게 정할 것인가

- 배경 = 세 버튼이 인라인 미리보기에서는 스크롤 맨 아래에 있어 보이지 않고, 확장보기에서는 그림 오른쪽에 눌려 글자가 두 줄로 접힌다. 요청자는 그림 위 한쪽에 고정되기를 원한다.
- 왜 문제인가 = 「접히고 보이지 않는다」는 표시 결함이지만 「그림 위 한쪽에 계속 고정」은 새 배치 요구다. 조사본이 두 판정을 모두 적고 승자를 고르지 않았는데, 같은 조사본의 레인 계획은 이미 「확대 줄을 뷰포트 안 절대 배치」를 작업 항목으로 넣어 그 판정을 앞질렀다.
- 선택지 = ⓐ 접힘·가림 해소까지만 고친다 ⓑ 고정 배치까지 새로 만든다 ⓒ 나중 묶음.
- 고르면 달라지는 것 = ⓐ 는 30~80행이고 세 화면 공유 규약을 유지한다. ⓑ 는 배치 규칙을 공용 부품이 쥐게 하는 재설계를 포함한다. 어느 쪽이든 **판정 전에는 레인 작업 항목으로 넣지 않는다.**
- 출처 = advisor 8.

### ⑧ 분석·렌더 소요의 합격선을 무엇으로 할 것인가

- 배경 = 조각 141개·48MB 를 올렸을 때 분석이 길고, 이어서 미리보기 그림도 오래 그린다는 보고가 있다. 두 구간은 같은 업로드에서 **연달아** 일어난다. 실제 소요는 한 번도 재지 않았다.
- 왜 문제인가 = 재지 않으면 고쳐야 할 결함인지 가릴 수 없다. 그리고 조사본은 기존 성능 눈금(다수 표본의 상위 통계치)을 이 파일 한 건의 합격 여부로 쓰려 했다. 그 눈금을 만든 측정은 같은 계열의 **다른 산출물**이었고 그 값 자체가 이미 눈금을 넘었다.
- 선택지 = ⓐ 두 구간을 한 번의 측정 회차로 함께 재고, 그 값을 보고 Ted 가 합격선을 정한다 ⓑ 기존 눈금을 그대로 합격선으로 쓴다 ⓒ 재지 않고 화면 표시만 손본다.
- 고르면 달라지는 것 = ⓐ 는 코드 변경 0이고 다른 작업과 동시에 돌릴 수 있으며, 두 이슈의 판정 입력이 한 번에 나온다. ⓑ 는 다른 산출물의 값으로 이 파일을 판정하게 된다. ⓒ 는 원인을 모른 채 표시만 바꾼다.
- 출처 = advisor 10·12. 조사 권고 = ⓐ.

### ⑨ 부모 데이터 찾기를 어디까지 볼 것인가

- 배경 = 등록 마지막 단계에서 부모 데이터를 고르는 창은 필터 6칸짜리 폼이고, 결과는 이름과 단계 표시만 있는 한 줄 목록이다. 요청자는 데이터셋 목록 화면처럼 표·열·정렬로 찾게 해 달라고 적었다. 첨부 화면에는 결과가 0행이다.
- 왜 문제인가 = 두 사안이 한 요청에 섞여 있다. 0행이 조회 결함이면 지금 고칠 것이고, 찾는 방식을 바꾸는 것은 새 화면 작업이다.
- 선택지 = ⓐ 0행 재현 확인만 이번에 하고 화면 형태는 새 항목으로 등재 ⓑ 화면 형태 재구성까지 이번에 한다 ⓒ 둘 다 나중 묶음.
- 고르면 달라지는 것 = ⓐ 는 조사 1회. ⓑ 는 이번 회차의 크기가 크게 늘고 조사본은 이를 사용성 개선으로 분류했다. ⓒ 는 0행이 결함인지 모른 채 넘어간다.
- 조사 권고 = ⓐ. 새 항목 제안명 = 「계보 부모 찾기 창을 데이터셋 목록 화면과 같은 표·열·정렬로 재구성」.

### ⑩ 미리보기 위에 보이는 기간 입력을 어떻게 볼 것인가

- 배경 = 미리보기를 크게 열면 그림 위에 「기간 · 한 시점이면 비워 둬요 · 달력에서 고르기」가 겹쳐 보인다. 그 컨트롤은 오른쪽 입력 폼의 것이다. 요청자는 미리보기에서 「올린 이미지 중에서 고르는」 방식도 제안했다. **겹침은 아직 재현되지 않았다**(화면 캡처 재취득 불가).
- 왜 문제인가 = 겹쳐 보이는 것이 결함인지, 좁은 창에서 두 칸이 위아래로 접힌 것을 겹침으로 본 것인지 아직 갈리지 않았다. 기간 달력 자체는 이미 판정으로 존치가 정해진 항목이고(`.claude/rules/colab-rules.md §6-2` 축자 「Ted 지정 예외는 판정으로만 성립(실례 = rev2 기간 달력 팝오버 판정-2 ⓑ)」), 조사본은 「이 이슈는 그 컨트롤의 존치를 다투지 않는다」고 판단했다. 그 판단의 승인이 필요하다.
- 선택지 = ⓐ 재현부터 하고 결과에 따라 판정 ⓑ 「이미지에서 고르기」도 이번에 설계 ⓒ 기존 판정에 덮인 것으로 보고 닫는다.
- 고르면 달라지는 것 = ⓐ 는 측정 회차에 포함되고 코드 변경 0. ⓑ 는 요구가 미확정이라 설계부터 필요하고 계약 확인 결과에 따라 동결 해제 서명 대상이 될 수 있다. ⓒ 는 겹쳐 보이는 상태가 남는다.
- 출처 = advisor 7. 조사 권고 = ⓐ.

### ⑪ 이번 회차 밖 한 건을 항목으로 세울 것인가

- 배경 = 여러 서버를 쓸 때 로그인 실패 횟수를 공유하고 프록시가 전달한 접속자 주소를 신뢰 판정 후 쓰는 후속 작업(#11)은, 유예 문장이 **이미 완료된 항목의 완료 정의 안에만** 있고 열린 항목이 없다.

- 선택지 = ⓐ 새 항목으로 등재하고 착수는 하지 않는다 ⓑ 지금은 등재하지 않는다.
- 고르면 달라지는 것 = ⓐ 는 대장에 항목 1개가 늘고, 세 번째 단계 목록을 담은 괄호를 같은 회차에 갱신해야 한다(게이트가 그 괄호를 대장과 대조). ⓑ 는 집계 누락이 유지된다.
