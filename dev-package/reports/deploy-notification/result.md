# 배포 자동 알림 구현 결과

사용자 승인 “그렇게해라”에 따라 공통 배포 실행기를 구현하고 현재 작업 사본의 ST 진입점·파이프라인 및 DV 웹 업로드 진입점에 연결했다.

- DV/ST 모든 배포 후 모든 검증을 다시 실행하고 Slack 한 번 전송한다.
- Git common directory 잠금을 자식에게 상속해 실행기 강제 종료 후에도 중복 배포를 막는다.
- 배포 ID별 계획·상태·로그를 분리하고 같은 완료 ID의 재실행은 전송하지 않는다.
- 배포 성공과 알림 실패를 분리한다. 명확한 전송 실패만 검증 재실행 후 알림 재시도하며 배포는 반복하지 않는다. 전송 결과 불명확은 자동 재전송하지 않는다.
- ST 기존 실행은 자동 연결된다. DV 업로드 직접 쓰기는 관리 실행기를 사용하도록 실행 전 거부한다. 공통 계획 사용법은 infra/releases/README.md에 있다.

## 검증

- 새 자동 알림 회귀 23/23 통과. 실제 CLI·ST 진입점·watch·pipeline은 격리 fixture로 검증했다.
- 잠금 상속 및 ID 충돌 결함을 각각 실패 재현 후 수정했다. 읽기 전용 코드 재검토 승인.
- agent-bridge 게이트: 74건 중 64 통과, Windows 전용 10건 Linux에서 명시적 skip. 요구 게이트 1/1 GREEN, 현재 작업 파일 및 작업 ID 검증 GREEN.
- pipeline selftest 54건 및 verifier selftest 22건 GREEN.
- DV 업로드 순수 단위 검사 5/5 통과 (`pytest --noconftest tests/test_deploy_web.py -q`). 최초 기본 실행은 전역 DB fixture 준비 실패였으며, DB를 쓰지 않는 해당 5건만 전역 fixture 없이 재검증했다.
- 실제 Slack 연결 점검 1건: HTTPS 정상 접수 확인. 비밀 URL은 출력·기록하지 않았다. receipt: slack-smoke.json. 새 제품 배포 완료 메시지로 가장하지 않았다.

## 적용 범위

현재 작업 사본의 코드에 반영했다. 이번 작업에서 제품 재배포·DB 변경·main push는 하지 않았다. 별도 자동배포 사본은 기존 로그인 호환성 검증 사유로 cron이 HOLD 상태이며 그대로 유지했다. 해당 사본에는 정상 코드 반영 절차로 변경을 전달해야 한다.

관리 진입점 밖에서 직접 실행하는 Docker/AWS 명령을 OS 차원에서 막는 기능은 아니다. 실제 검증의 충실도는 승인된 배포 계획의 verify 명령에 달려 있다. Stop hook의 수동 prepare와 독립이며 동일 배포를 이중 알림 준비하지 않는다.
