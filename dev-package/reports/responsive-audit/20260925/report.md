## 7. 입력 방식 규칙 후보 (터치 vs 마우스)

1. **누름 칸 44px**: `(pointer: coarse)`면 폭과 관계없이 44px로 한다. 고정 px 부품은 `--control-height`를 쓴다. 대상은 누름 칸 합계 262개(744·820·844x390)와 350개(1024·1180)다.
2. **입력 글자 16px**: `(pointer: coarse)` 전체에 적용한다. 9곳에 흩어진 선언을 1곳으로 합친다. 대상은 33–34개 장면이다.
3. **마우스를 올려야만 보이는 정보 금지**: `title`에만 있는 정보 9곳을 화면에 보이게 하거나, 누르면 보이게 한다.
4. **hover 색 변화는 마우스 기기에서만 켠다**: `:hover` 34개를 `(hover: hover)` 조건 안에 넣는다.
5. **마우스 전용 동작마다 누름 대안을 둔다.**
   - 좌표 표시: 누른 점의 좌표를 보여 준다.
   - 더블클릭 맞춤: 같은 일을 하는 단추를 둔다.
   - 휠 확대·끌어다 놓기: 대안 단추가 이미 있다.
   - 핀치: 지금은 일부러 무시한다(`useZoomPan.ts:404`).
6. **문구**
   - "커서"·"휠"·"끌어다"는 입력 방식에 맞게 쓴다.
   - "표를 좌우로 밀면"은 표가 실제로 넘칠 때만 보인다.
7. **축 분리**
   - 폭 규칙은 배치만, 입력 규칙은 크기·정보 접근만 다룬다.
   - `(max-width: 640px), (pointer: coarse)`처럼 두 조건이 섞인 규칙은 입력 쪽으로 옮긴다.

## 8. 우선순위 제안

1. **지도 미리보기**: 합의된 첫 시범이다.
   - 가려지는 비율: 100%(긴 이름 · 대표값), 69–91%(짧은 이름 · 하한 참고)
   - 320에서 스크린샷 단추를 누를 수 있는 면적: 0%
   - 지도 위 도구 원칙과 입력 규칙을 이 화면에 처음 적용한다.
2. **공통 입력 규칙과 맨 위 메뉴**: 토큰, 기본 규칙, 메뉴 한 부품만 고치면 28–35개 장면에 적용된다.
3. **낮은 높이**: 844x390에서 2줄 고정 메뉴가 화면 높이의 28%를 차지한다. 창·화면 5종이 영향을 받는다.
4. **넓은 표 3종**: 데이터셋 목록, 계정 관리, 프로젝트 상세. 작업 단추가 화면 밖에 있다.
5. **업로드 등록**: 320–360에서 칸이 잘리고, 변수 표의 누름 칸이 작다.
6. **나머지**
   - 작은 링크
   - 말줄임되거나 `title`에만 있는 정보
   - 표 안내 문구

## 9. 새 intent 1라운드 질문 초안

> (주 2026-09-26) 아래는 advisor ② 검토 **전** 원판이다. Q3 서두(44px 전제)와 Q6 대표값(짧은 이름 기준)이 틀렸고, Q7·Q8 은 다른 질문에 종속돼 다음 라운드로 옮겼다. Ted 에게 간 수정본과 판정 결과는 `dev-package/intent/2026-09-26-device-width-input-rules.md` 설계트리에 있다.

❓ **Q1** - **폭 단계 수와 값**: 지금 폭 경계 값은 17종(520–1536)이고, 같은 경계가 여러 값으로 흩어져 있다(패드 경계 860·861·880·900, 중간 경계 720·740·760). 디자인 시스템에 허용 값을 정한다.
- ⓐ 3단 640·1024 (휴대폰·패드·PC)
  - 대가: 규칙 26개를 옮긴다(합 2764px). 901–1023 노트북 창에서 맨 위 메뉴가 2줄이 된다. 패드 가로(1133·1180)에서 메뉴를 좁히던 규칙이 빠져 메뉴가 넘칠 수 있다.
- ⓑ 4단 640·900·1180 (휴대폰·패드 세로·패드 가로·PC)
  - 대가: 이름이 4개가 된다. 규칙 23개를 옮긴다(합 1909px). 641–720 폭(작은 휴대폰 가로)에서 폼이 1열에서 2열로 바뀐다.
- ⓒ 4단 640·768·1024 (흔히 쓰는 값)
  - 대가: 규칙 26개를 옮긴다(합 2347px). 900에서 바뀌던 메뉴 2줄·목록 필터·대시보드 경계가 1023으로 옮겨진다. 패드 가로 메뉴 위험은 ⓐ와 같다.

➡️ ⓑ: 20px 간격 측정에서 가장 많은 장면이 바뀐 경계 640(30개)·900(26개)을 그대로 두고, 옮기는 규칙도 가장 적다. 패드를 세로·가로로 나눠 부르면 휴대폰·패드·PC 세 분류와도 맞는다.

❓ **Q2** - **기준: 화면 폭 vs 부품 칸 폭**: 지도 위 도구가 얼마나 가리는지는 화면 폭이 아니라 지도 상자 폭(390 화면에서 332px)으로 정해진다. 계정 표 경계(1024·1536)와 표 가로 스크롤 안내(1100)는 표 내용 폭에서 나온 값이다. 부품 칸 폭 규칙(container query)은 지금 0개다.
- ⓐ 화면 폭만
  - 대가: 지도 상자가 좁아지는 다른 배치에서는 규칙이 맞지 않는다. 표가 다 들어가도 스크롤 안내가 보이는 문제(744–1100)가 남는다.
- ⓑ 화면 폭 기본 + 내용 폭으로 정해지는 부품(지도 위 도구·넓은 표·표 안내)만 부품 칸 폭
  - 대가: 방식이 2개가 되어 문서와 점검 규칙도 두 갈래가 된다.
- ⓒ 모든 부품을 부품 칸 폭으로
  - 대가: 기존 폭 규칙 55개를 모두 다시 써야 한다. 맨 위 메뉴처럼 화면 전체 폭을 쓰는 부품은 결과가 같다.

➡️ ⓑ

❓ **Q3** - **터치 규칙 범위**: 지금은 44px 누름 칸·16px 입력 글자가 폭 640 이하에만 걸려 있어, 641px 이상 터치 기기의 35개 장면이 마우스용 크기다. 터치가 주 입력인 기기에 거는 규칙의 범위를 정한다.
- ⓐ 크기만: 누름 칸 44px, 입력 글자 16px
  - 대가: 마우스를 올려야만 보이는 정보 9곳과, 마우스로만 되는 지도 동작(커서 좌표 표시·더블클릭 맞춤)이 남는다.
- ⓑ 크기 + 정보 접근: ⓐ에 더해 마우스를 올려야만 보이는 정보를 금지하고, 마우스 전용 동작마다 누름 대안을 두고, "커서·휠·끌어다" 문구를 입력 방식에 맞추고, hover 색 변화는 마우스 기기에서만 켠다.
  - 대가: 문구·표시 변경이 여러 화면에 생긴다(정보 9곳, hover 선택자 34개).
- ⓒ ⓑ + 핀치 확대 같은 터치 전용 제스처 추가
  - 대가: 지도 확대 코드에 두 손가락 처리를 새로 써야 한다. 지금은 두 번째 손가락을 일부러 무시한다.

➡️ ⓑ: 핀치로 하는 일은 확대·축소 단추로 할 수 있으니 뒤로 미룬다.

❓ **Q4** - **낮은 화면 높이(휴대폰 가로) 처리**: 844x390에서 맨 위 메뉴가 2줄로 고정돼 약 108–110px(높이 28%)를 계속 차지한다. 머리·바닥이 고정된 창은 본문이 약 178px만 남는다. 폭만으로는 휴대폰 가로(667–932)와 패드 세로(744–1024)를 구분할 수 없다.
- ⓐ 높이 조건 추가(높이 약 500px 이하): 맨 위 메뉴를 1줄로 하고 스크롤하면 올라가게 하며, 창 머리·바닥을 줄인다.

- ⓑ 높이 조건 없이 폭 규칙만
  - 대가: 휴대폰 가로에서 본문 높이 약 280px(메뉴 때문), 178px(창 안)이 그대로 남는다.
- ⓒ 휴대폰 가로를 지원 범위에서 빼고 문서에 적는다
  - 대가: 기기를 가로로 돌린 사용자는 지금 상태를 그대로 겪는다.

➡️ ⓐ

❓ **Q5** - **좁은 화면의 넓은 표 배치 원칙**: 데이터셋 목록(1065px)·계정 관리(1304px)·프로젝트 데이터셋 표(680px)는 휴대폰에서 가로 스크롤만 된다. 행 작업 단추가 맨 오른쪽 열에 있어서, 390 화면에서는 약 700–880px를 밀어야 보인다. 640 이하에서 카드로 바뀌는 표는 구성원 권한 표 하나다.
- ⓐ 가로 스크롤을 유지하고 이름 열·작업 열을 고정
  - 대가: 390 화면(보이는 폭 약 280–356px)에서 고정 열 두 개가 폭 대부분을 차지해 가운데 열은 거의 보이지 않는다.
- ⓑ 휴대폰 폭에서는 행을 카드로 바꾸고, 패드 이상은 ⓐ
  - 대가: 표마다 카드 설계가 필요하다(표 3–4개). 표와 카드 두 모양을 모두 점검해야 한다.
- ⓒ 지금처럼 가로 스크롤 + 안내 문구
  - 대가: 휴대폰에서 작업 단추에 닿으려면 옆으로 밀어야 하는 상태가 남는다.

➡️ ⓑ

❓ **Q6** - **지도 위 도구 배치 원칙(첫 시범 화면)**: 범례·값 패널·확대 단추·좌표 표시·스크린샷이 지도 네 모서리에 떠 있고, 크기가 지도 폭과 관계없다. 실제 변수 이름 기준으로 지도 이미지가 390 화면에서 69%, 320에서 91% 가려진다.
- ⓐ 지도 상자가 좁으면 범례·값 패널을 지도 아래로 내리고, 지도 위에는 확대·축소 단추만 둔다.

- ⓑ 좁을 때 범례·값 패널을 접힌 채로 시작하고, 단추를 누르면 펼친다.
  - 대가: 첫 화면에 범례가 없어 색의 뜻을 보려면 한 번 눌러야 한다. 펼치면 다시 지도를 가린다.
- ⓒ 크기만 줄인다(글자·여백 축소, 범례 폭 상한).
  - 대가: 320–390에서 가림 비율이 얼마나 줄지 재지 않았다. 범례 높이는 등급 수로 정해져 그대로 남는다.

➡️ ⓐ: 이 결정을 "지도·캔버스 위 도구" 원칙으로 디자인 시스템에 넣고, 업로드 미리보기에도 같은 원칙을 쓴다.

  - 대가: 공통 부분을 바꾸면 28–35개 장면의 캡처가 한꺼번에 바뀌어 대조할 양이 많다.
- ⓒ 표·창까지 전 화면
  - 대가: 표 카드 설계와 창 높이 설계까지 한 번에 들어가 범위가 가장 크다.

❓ **Q8** - **검증 방법**: 지금 캡처 기준은 375·768·1440 세 폭, 높이 900이고 터치 모의가 없다. 이번 문제 대부분은 이 세 폭 밖(844x390·1024·1180)이나 터치 상태에서 나왔다. 디자인 점검 게이트는 `@media` 값을 검사하지 않는다.

  - 대가: 실기기 준비와 수동 확인 시간이 든다. iOS 포커스 확대·화면 키보드·safe-area는 실기기로만 확인된다.

  - 대가: 터치 상태와 휴대폰 가로의 회귀를 매번 잡지 못한다.
