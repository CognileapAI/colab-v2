02결정 ① ㊹ — 미구현 29개를 501 로 두는 것

core-api 는 계약의 34 op 을 전부 등록했지만 실제로 도는 것은 5개다. 나머지 29개가 무엇을 대답할 것인가가 이 결정이다.

비유 하나 — 건물 준공 전 층별 안내판이다. 아직 입주 안 한 층에 안내판을 뭐라고 쓰느냐의 문제다. "정상 영업 중"이라 쓰면 거짓말이고, "그런 층은 없습니다"라고 쓰면 층 번호 자체가 사라진다. 비유가 깨지는 지점: 안내판은 사람만 읽지만 여기서는 테스트가 읽는다. 그래서 "무엇이라 쓰는가"가 곧 진척 계측기가 된다 — 안내판이 하나씩 사라지는 속도가 진척이다.

네 갈래 — 고르면 나중에 무슨 일이 생기나

ⓐ 200 스텁 (빈 값을 정상 응답으로) 나중에 — 29개가 전부 "정상"이라고 주장한다. FE 가 그 위에 붙기 시작하면 어디까지가 진짜인지 아무도 모른다. 그리고 그렇게 붙은 테스트는 "29개는 진짜다"를 함의하게 된다. v1 이 로컬 green 을 완료로 착각한 것과 같은 구조.
ⓑ 404 나중에 — ㊱ 이 404 를 「연구실 경계 밖」 하나로 못 박았다. 미구현에 404 를 쓰면 같은 코드가 두 뜻이 되고, 경계 위반과 미구현을 구분할 수 없게 된다. 경계 버그가 "아직 안 만든 건가 보다"로 묻힌다.
ⓒ 계약(yaml)에 501 을 명시 나중에 — 501 이 영구 약속이 된다. P6 이 승인 처리를 구현하고 501 을 지우는 순간 oasdiff 가 breaking change 를 낸다. 즉 제대로 만드는 행위가 게이트를 red 로 만든다. 계약 동결의 취지와 정면 충돌.
ⓓ 501 + ErrorEnvelope.code 두 종 (현재 채택) NOT_IMPLEMENTED_NO_STORE = 저장할 테이블 자체가 없다 (access-request 4 · verification-request 2 · downloadDataset = 7건. P6·P2 가 연다) / NOT_IMPLEMENTED_P1 = 저장처는 있고 로직만 미착수.
나중에 — 계약은 한 줄도 안 바뀐다(501 은 계약이 아니라 배포 상태). contract-lint 는 yaml 만 보므로 충돌 없음. P1 이 하나 구현할 때마다 501 목록이 29 → 28 → … 로 줄고 그게 곧 진척 수치가 된다. 테스트가 op 별 code 를 고정하므로 조용히 가짜 200 으로 되돌아가는 길이 막힌다.

왜 두 종으로 나누는가 — 이게 이 결정의 진짜 알맹이

7건과 22건은 다른 종류의 미완이다. 앞의 7건은 "코드를 쓰면 되는" 게 아니라 DB 에 테이블이 없다(요청 큐는 E-06 규칙 본체이고 P6 의 몫). 뒤의 22건은 테이블이 이미 있고 라우트만 비었다. 하나의 501 로 뭉개면 "이건 오늘 할 수 있는 일인가"를 코드에서 읽을 수 없다.

권고 — 그대로 간다 (ⓓ)

이건 정직성 문제이고, 네 갈래 중 셋은 각각 다른 방식으로 거짓말을 한다. 되돌리는 비용 = 매우 낮다. 501 은 레포 코드에만 있고 계약·DB·FE 어디에도 새겨지지 않았다. 마음이 바뀌면 라우트 핸들러의 응답만 갈아 끼우면 되고, 그 시점에 계약은 손댈 것이 없다. 지금 승인하지 않아도 잃는 것이 없고, 나중에 뒤집어도 잃는 것이 없다 — 이 결정을 낮은 위험으로 만드는 것이 바로 "계약에 박지 않았다"는 선택이다.

인출 연습 — 만약 ⓒ 를 골랐다면, P6 을 완성한 날 무슨 게이트가 red 를 낼까?

contract-breaking(oasdiff). 계약에 있던 501 응답을 지우는 것은 응답 스펙 제거 = breaking 이다. 결과적으로 "기능을 완성했더니 CI 가 막는" 상태가 되고, 그걸 피하려면 계약에 죽은 501 을 영원히 남겨야 한다. 계약이 배포 상태를 기억하기 시작하면 계약이 썩는다.

03결정 ② ㊺ — 앱이 어떤 DB 롤로 붙는가

이 문서에서 가장 중요한 장면이다. 똑같은 시험 묶음이 롤 하나 때문에 결과가 뒤집힌다. 그리고 뒤집힌 쪽이 하필 전부 통과로 보인다.

먼저 — RLS 가 적용되지 않는 세 경우

Postgres 의 Row Level Security 는 모든 접속에 걸리지 않는다. 아래 셋은 정책이 통째로 무시된다.

① 테이블 소유자

기본적으로 자기 테이블의 RLS 를 건너뛴다. FORCE ROW LEVEL SECURITY 를 걸어야 소유자에게도 적용된다.

② superuser

정책 자체가 평가되지 않는다. FORCE 를 걸었든 말든 무관하다.

③ BYPASSRLS 속성 롤

superuser 가 아니어도 이 속성 하나로 모든 정책을 통과한다.

즉 "RLS 정책을 걸었다"와 "그 접속에 RLS 가 걸린다"는 다른 사실이다. 그리고 앱이 저 셋 중 하나로 붙으면, 경계 시험은 전부 초록인데 아무것도 증명하지 않는다.

보라 — 같은 시험, 다른 롤

지금 보라는 것 — 오른쪽 칸 17개의 색. 앱 롤에서는 17개 전부 초록이고, superuser 로 바꾸면 13개가 빨강이 된다. 핵심은 어느 쪽이 초록인가가 아니라 어느 쪽이 초록일 때 의미가 있는가다. 버튼으로 몇 번이든 다시 볼 수 있다.

뒤집어 생각하라 — 만약 앱이 소유자 롤이었다면

superuser 로 돌린 결과에서 통과한 4개는 전부 양성 계열이었다("보여야 하는 것이 보인다"). 양성 시험은 롤이 뭐든 통과한다 — 막는 장치를 아예 떼어내도 통과한다. 그래서 거짓 green 을 잡아 주는 것은 음성 시험뿐이고, 롤이 틀리면 그 음성 시험조차 무력해진다. 이것이 ㊺-② 가 없으면 P0 이 세운 경계 증명 전부가 조용히 무효가 되는 이유다. 조용히 — red 가 뜨지 않는다.

그래서 rls-effect 게이트가 롤 자체를 검사한다

정책이 걸렸는지 만 보는 rls-coverage 는 USING(true) 같은 가짜 정책을 통과시킨다. 그래서 D3b 가 실효를 증명하는 게이트를 따로 세웠고, 그 게이트는 판정에 쓰는 롤의 성질을 스스로 확인한다.

㊺ 의 나머지 두 항

  • ① colab_platform / colab_ai 두 데이터베이스로 분리. 한 DB 안에 스키마 둘로 넣으면 CLAUDE.md §3-3 의 체인 분리가 서류상 사실이 된다 — 같은 접속에서 둘 다 만져지므로 언제든 섞을 수 있다. 두 DB 면 섞으려면 접속을 새로 열어야 하고, 그 순간 눈에 띈다.
  • ③ 호스트 노출은 127.0.0.1 만. PoC 가 0.0.0.0 으로 열어 뒀던 반복을 막는다. I2 실측 0.0.0.0 0건.

권고 — 그대로 간다

①②③ 셋 다 지금 뒤집을 이유가 없고, ②는 뒤집으면 이미 지불한 P0·D3b 의 증명값이 전부 0 이 된다. 되돌리는 비용 — ①(DB 분리)만 유일하게 비싸다. 데이터가 쌓인 뒤 하나로 합치려면 마이그레이션 체인을 재작성해야 한다. 다만 지금 platform 은 0행이고 ai 는 22행이라, 뒤집을 거면 지금이 가장 싸다 — P1 이 실데이터를 쌓기 시작하면 값이 올라간다. ②③은 설정 한 줄이라 언제든 되돌릴 수 있다(되돌릴 이유가 없을 뿐).

인출 연습 — 경계 시험이 전부 green 이다. 이 green 이 의미 있는지 확인하려면 무엇을 봐야 하나?

세 가지. ① 시험을 돌린 롤이 rolsuper=f·rolbypassrls=f 이고 대상 테이블의 소유자가 아닌가. ② 통과한 시험 중 음성(막혀야 할 것이 막혔다)이 몇 개인가 — 양성만 통과했다면 아무것도 증명되지 않았다. ③ 보호 장치를 하나 떼면 실제로 red 가 나는가(P0 는 이 red 증명을 9회 자동화했고 D3b 는 18건으로 게이트화했다). green 은 증거가 아니다. "떼면 red 가 난다"가 증거다.

04결정 ③ 백업 실패 알림 채널 — 만들 것인가

IS3 는 닫혔다. 백업은 돈다. 복원도 실측했다. 그런데 실패했을 때 그 사실이 사람에게 도달하지 않는다.

이 프로젝트가 이미 아는 사건 — 빈 백업 8주. 그때 백업은 돌고 있었다. 문제는 결과가 아무에게도 가지 않은 것이다. 그래서 IS3 가 고친 것은 두 가지고, 셋째는 아직 안 고쳐졌다.

침묵 창 — 실패가 사람에게 닿기까지 걸리는 최악의 시간

지금 보라는 것 — 막대의 길이. 이것은 "백업이 얼마나 자주 도는가"가 아니라 실패가 사람 눈에 닿기까지의 최악 지연이다. IS3 는 이 막대를 8주에서 1주로 잘랐다. 0 으로 만들지는 못했다.

ⓑ 채널 하나만 정해 준다 (Ted 가 값 하나 주기) 필요한 것은 URL 또는 주소 한 개다 — 웹훅(Slack/Discord/카카오웍스 등) 또는 수신 메일 주소. 구현은 반나절 이하이고, 실패 시 표식 파일을 쓰는 자리에 전송 한 줄을 더하는 일이다.
나중에 — 침묵 창이 1주 → 사실상 즉시가 된다. 대가는 알람 피로다. 그리고 알람 피로가 바로 8주 침묵의 메커니즘이었다 — 그래서 실패에만 보내고 성공엔 침묵해야 한다(주간 재검사는 지금처럼 유지).
ⓒ 알림 + 오프호스트 사본을 한꺼번에 나중에 — 오프호스트는 AWS(I0)에 걸려 있다. 즉 이 선택은 자동으로 "AWS 계정을 먼저 준다"와 묶인다. 알림만 먼저 붙이는 것과 비교해 지금 당장 얻는 것이 없고 대기만 생긴다.

권고 — ⓑ. 단 P1 착수 전에, 그리고 실패에만 보내는 조건으로.

이유 셋. ① 지금 붙이는 비용이 가장 싸다 — 붙일 자리(표식 파일을 쓰는 그 지점)가 이미 만들어져 있다. ② P1 부터 staging 에 실데이터가 쌓이고, 그때부터 침묵 1주는 실제 손실 1주가 된다. ③ 이건 Claude 가 정할 수 없는 값이다 — 어디로 보낼지는 레포 밖 결정이다. 되돌리는 비용 = 거의 0(설정 한 줄 제거). 다만 성공까지 보내면 반드시 되돌리게 된다 — 그게 알람 피로다.

당신이 줄 것 = 웹훅 URL 하나 또는 메일 주소 하나.

인출 연습 — 백업이 매일 돌고, 검사도 통과하고, 복원도 실측했다. 그런데도 v1 사건이 재현될 수 있는 경로는?

둘. ① 크론 자체가 멈춘다(호스트 재부팅·데몬 사망). 이건 주간 재검사가 늦어도 월요일에 RED 로 잡지만, RED 를 파일에만 쓰므로 아무도 안 본다. ② 백업 파일과 원본이 같은 머신 위에 있다 — 그 머신이 사라지면 둘 다 사라지고, 이건 알림으로도 못 막는다(I0 대기). ①은 오늘 값 하나로 닫히고, ②는 AWS 가 열려야 닫힌다.

  2. 비용의 시작 시점. OpenAI 키는 주는 순간부터 호출 과금이 시작될 수 있다 — 쓸 자리가 없는 동안 주는 것은 이르다. AWS 는 I0 가 예산 알람 설정을 포함하므로 계정을 먼저 여는 것이 오히려 비용 통제의 시작이다.
  3. 부수 효과. AWS 가 열리면 오프호스트 백업(§04 의 남은 구멍 ②)이 같이 열린다. 지금 백업은 원본과 같은 머신 위에 있다.

인출 연습 — AWS 계정을 오늘 줬다. 오늘 밤 Claude 가 prod 에 배포할 수 있나?

없다. ㊵ 가 세 겹으로 막는다 — ① 구현·확인은 전부 staging 에서 ② AWS 이관은 당신이 staging 에서 직접 보고 승인한 뒤 ③ 승인 단위는 WU 가 아니라 눈으로 확인 가능한 화면·흐름. 게다가 I5(prod 전환)는 I4 와 P7 뒤에 놓여 있다. 계정을 주는 것은 사슬을 시작시키는 것이지 끝으로 건너뛰는 것이 아니다.

06결정 ⑤ 다음 WU — P1 인가

P0 가 닫히면서 P1 의 진입조건이 충족됐다. 그리고 앞서 봤듯 지금 열 수 있는 P 는 P1 하나뿐이다.

P1 이 담는 것

  • S-03 카탈로그 + 데이터셋 상세 헤더
  • 연구실 설정 > 구성원·권한 — G4 가 P1 로 배정했다. P1 단계 취지 문구도 함께 개정됐다: 권한 값의 원천 하나만 예외로 쓰기 화면을 연다

왜 P1 이 지금 최선인가

  1. P1 은 다섯 갈래의 목이다. P2·P3·P4·P5 가 전부 P1 뒤에 있다. P1 을 지나기 전에는 어떤 병렬화도 P 트랙을 넓히지 못한다.
  2. I2 를 지났으므로 이제부터 완료 판정에 staging 배포 green 이 붙는다. 즉 P1 은 당신이 눈으로 볼 수 있는 첫 화면이 되고, 그게 ㊵ 의 승인 단위("눈으로 확인 가능한 화면·흐름")를 처음으로 만족시킨다.
  3. P1 이 501 목록을 처음 줄인다. ㊹ 가 만든 진척 계측기가 여기서 처음 움직인다.
  4. P1 이 미해결 두 건을 실제로 만난다 — fileCount 계약 모순과 /api/v1/me 401(주체 표 미배치). 뒤로 미룰수록 위에 쌓이는 코드가 늘어난다.

인출 연습 — I3(배포 자동화)를 P1 보다 먼저 하면 무엇이 손해인가?

I3 는 배포할 것이 늘어날수록 값이 커지는 작업이다. 지금 배포 대상은 자리표시에 가까운 5개 단위이고, P1 이 끝나면 실제 화면이 붙은 상태가 된다 — 자동화가 다뤄야 할 실물이 그때 생긴다. 반대로 P1 은 지금 유일하게 열린 목이라 미루면 다섯 갈래가 전부 대기한다. 목을 먼저 뚫는다.

07아직 남은 미해결 4건

닫힌 WU 뒤에 남은 것들이다. 넷 다 지금 진행을 막지 않는다. 그러나 넷 다 만나는 시점이 정해져 있다.

① ai-no-lineage-write ⑧ 이 무뎌졌다 K3 에서 조인다

이 게이트는 "AI 가 계보에 쓰지 않는다"를 증명하는 음성 게이트다(CLAUDE.md §3-2 의 기계 강제). 문제는 ai-service 에 아직 실제 코드가 없다는 것이다. 밤새 빈 도메인 자리가 생기면서, 이 게이트가 검사하는 대상이 사실상 비어 있는 것을 검사하는 상태가 됐다. "AI 가 계보에 쓰지 않는다"와 "AI 가 아직 없다"는 다른 사실이다 — D3 세션이 0건을 green 으로 세지 않겠다고 명시한 바로 그 구분이 여기서 다시 문제가 된다.

언제 조이나 — K3 가 첫 실코드를 넣을 때. 그 순간이 이 게이트가 처음으로 진짜 일을 하는 시점이고, 동시에 가장 조용히 뚫릴 수 있는 시점이다. K3 착수 시 조건으로 못 박아 둘 것.

② fileCount — 계약과 스키마가 어긋난다 P1 이 만난다

계약의 DatasetRow.fileCount 는 minimum: 1 이다. 그런데 조각 수의 유일한 출처인 d3_file 은 body_access RESTRICTIVE 정책이 막아 잠긴 데이터셋에서 0행이 된다. 즉 계약이 1 이상을 약속했는데 실제로 0 이 나온다.

P0 는 1 을 지어내지 않았다 — 보이는 만큼(0)을 그대로 내렸다. 계약을 어기는 쪽이, 값을 지어내는 쪽보다 낫다는 판단이다(지어낸 1 은 아무도 못 잡지만, 계약 위반은 게이트가 잡는다).

해소는 둘 중 하나 — ⓐ d3_dataset_autometa 에 조각 수 컬럼을 더한다(스키마 개정) ⓑ D3 이 본체 정책 밖에서 세는 Port 를 낸다. ⓑ 가 경계 규칙에 맞는 형태지만, "잠긴 것의 메타는 보인다"(P-13)에 조각 수가 포함되는지는 기획이 답할 문제다. P1 이 카탈로그를 그리면서 반드시 만난다.

③ IS4 🟧 — terraform state 가 이 호스트에만 있다 호스트가 사라지면

복구 절차는 저작됐고 리허설도 돌았다 — scratch 에 .tf 만 복사해 init → import → plan, 실자격증명으로. 원본 state md5 동일, 실디렉터리 plan = No changes., staging 은 내내 200.

미달 두 가지 — ⓐ 마지막 apply 미실행(실 터널을 건드리는 일이라 밤샘 자율 범위 밖) ⓑ 맨몸 호스트 조건(terraform 미설치·자격증명 파일 없음) 미실험. 절반을 완료로 세지 않았다. 원격 백엔드는 I0(AWS)에 걸어 뒀으므로, AWS 를 먼저 주면 이 항목의 성격이 바뀐다(로컬 state 복구 절차 → 원격 백엔드).

④ 정본이 아직 답하지 않은 것 기획이 답해야 한다

가장 중요한 것부터 — P0-schema §7-③:

잠긴 데이터셋의 본체를 소유자·교수가 볼 수 있는지 정본이 말하지 않는다.

정본 §4.1 은 잠김이면 「볼 수 있는 사람 목록」만 말한다. 소유자 예외·교수 예외·업로더 예외가 어디에도 없다. body_access 정책은 정본에 적힌 것만 구현했다 — 열림(데이터셋 값 또는 연구실 기본값) 또는 만료되지 않은 허용 줄. 그 결과 자기가 올린 데이터를 잠그면 소유자 본인도 DB 층에서 본체를 못 받는다.

안전한 쪽(fail-closed)으로 닫았지만 운영상 거의 확실히 틀린 형태다. 값의 정본은 E-06(Policy_승인_처리)이고 P6 전에 기획 확인이 필요하다.

P0-schema §7-② — 정본 §2 가 연구실 이름을 두 곳에 적는다("연구실 = 이름·개설일" 과 "연구실 정보 = … 유일한 자리"). 구현은 d1_lab.name 한 곳으로 정했다 — 근거는 이름을 profile 에 두면 연구실 목록·전환기가 RLS 에 걸린다는 것(경계 판정 전에 필요한 값이다). 정본이 두 곳에 적은 사실 자체는 남는다.

그 밖 — 계보 상태 원천/기록 없음 판정 순서 [정본 무근거] · K2 의 [정본 무근거] 5건(정본이 준 주제 동의어는 강우데이터 하나뿐이었고 지명 별칭은 0건이었다 — 나머지를 만들지 않았다). 만들어 채우지 않은 자리가 남아 있다는 것 자체가 산출물이다.
