#1 을 실물로 확인했다 — backup.sh 는 pg_dump 전용이다

infra/staging/backup/backup.sh 를 직접 읽은 결과.

  • 덤프 명령은 pg_dump -U … -d "$DB" --no-owner --no-privileges | gzip 단 하나다(직결 시 pg_dump "$COLAB_BACKUP_PG_URL").
  • 대상은 프로파일 목록 — platform(colab_platform) · ai(colab_ai). 둘 다 데이터베이스다.
  • 산출물은 <프로파일>-<타임스탬프>.sql.gz ＋ .sha256. 볼륨을 담는 경로·명령·프로파일이 스크립트 어디에도 없다.
  • 검사(verify-artifact.sh C1~C6)도 전부 SQL 덤프 파일을 세는 검사다 — CREATE TABLE 수 · 데이터 행 수 · gzip 무결성 · mtime 신선도.

즉 「볼륨 백업 절차가 없다」는 문서의 주장이 아니라 코드의 사실이다. R1-RESTORE-DRAFT §2 도 같은 판정을 내린다 — 백업되는 것은 원장 DB 둘뿐이고, uploads 볼륨(colab-v2-staging_uploads)·previews 볼륨·비밀 파일 넷·이미지 여섯이 비어 있다.

이걸 안 하고 재기동하면 무슨 일이 생기나 — 이 문서에서 가장 강한 대비다.

  • 지금 재기동은 무보험이다. 「백업은 있는데 되돌리는 절차가 없다」가 그 자체로 모순이고, 미루면 그 사이 모든 재기동이 무보험이다(〈158〉-㉯).
  • 백업 GREEN 은 복원 가능성을 보증하지 않는다. C1~C6 은 파일을 읽어 센 것이지 psql 에 먹여 본 것이 아니다. 그리고 platform·ai 두 덤프는 순차로 떠서 원자적 스냅숏이 아니다(실측 8초 차).
  • sha256 은 만들 뿐 검증 경로가 없다. 어떤 스크립트도 복원 전에 이 값을 다시 대조하지 않는다 — 그리고 이 기구화의 소유 WU 가 비어 있다(위 표 #9).
  • 오프호스트 사본이 0 이다. 백업이 원본과 같은 WSL2 머신 1대 위에 있다(IS3 §5-4).

  • ⓑ 메일. 외부 SMTP 자격증명이 호스트에 하나 더 놓인다.
  • ⓒ 메신저 webhook. 아웃바운드 하나. 다만 webhook URL 자체가 비밀이라 비밀 목록이 7종 → 8종이 된다.

고르면 나중에 무슨 일이

ⓐ 를 고르면 — 배포 실패가 사람이 볼 때까지 조용하다. 호스트가 자동 기동하지 않는 이 환경에서는 그 침묵이 며칠 갈 수 있다. ⓑ·ⓒ 를 고르면 — 비밀이 하나 늘고, R-1 의 「백업하지 않고 재발급한다」 목록에 한 줄이 추가된다(〈163〉-㉲). R-1 완료 정의가 그만큼 넓어진다.

권고

ⓐ 표식 파일 · staging 한정. 근거 셋 — ① ㊻ 로 대상이 staging 한 대뿐이고 사용자가 붙기 전이다 ② 비밀을 늘리지 않는 쪽이 R-1 과 정합이다 ③ IS3 §10 의 침묵 감지(latest-check.sh)가 이미 같은 계열로 돌고 있어 새 기구가 아니라 기존 관행의 확장이다.

되돌리는 비용 — 낮다. 채널 추가는 표식 파일을 남긴 채 발신 한 줄을 얹는 일이다. 반대로 ⓑ·ⓒ 를 먼저 켰다가 끄는 것은 비밀 회수 절차가 따라온다.

② 폴링 주기 · 워처를 systemd 로 걸 것인가 cron 으로 걸 것인가 막힘

원문 · I3.md:197 — 「폴링 주기 값 · 워처를 systemd 로 걸지 cron 으로 걸지 → [정본 무근거]. 세션에서 정하고 근거를 적는다. (IS3 의 크론이 이 호스트에서 실제로 돌고 있음은 확인된 사실이다 — IS3 §10)」

배경

트리거 방식은 이미 결정 1 에서 권고가 나 있다 — A 호스트 폴링. 근거 셋 — ① 인바운드를 0 으로 유지한다(IS2 가 ingress 를 www→nginx:80 ＋ catch-all 404 둘뿐으로 좁혔다) ② 자격증명이 읽기 전용 git fetch 하나로 끝난다 ③ 호스트가 꺼져 있으면 안 도는 성질이 정직하다. 나머지 둘(self-hosted runner · webhook)은 레포가 public 이거나 ingress 를 넓힌다는 대가가 붙는다. 남은 것은 그 워처를 어디에 매다는가와 주기 값이다.

지금 상태

IS3 의 백업 크론이 이 호스트에서 실제로 돌고 있다(schedule.crontab·install-schedule.sh). 즉 선례가 cron 쪽에 있다. systemd 는 이 환경(WSL2 + Docker Desktop)에서 새 의존이다.

선택지

  • ⓐ cron · 기존 crontab 에 한 줄. 설치 스크립트 패턴이 이미 있다. 실행 로그·잠금은 스크립트가 직접 진다.
  • ⓑ systemd timer. 실행 상태·실패 이력을 systemctl 이 지지만, WSL2 에서 systemd 활성 여부가 환경 조건이 된다.

주기 — 「커밋→배포 지연 = 폴링 주기」가 이 방식의 유일한 대가다(결정 1 표).

고르면 나중에 무슨 일이

ⓑ 를 고르면 — 호스트 재기동 절차(RESTART.md)에 systemd 항목이 하나 늘고, 그것이 안 뜬 상태에서도 staging 은 정상으로 보인다. RESTART.md 가 이미 「한 글자 빼면 조용히 롤백되고 루트 헬스는 200」인 환경이라 침묵 실패의 자리가 하나 더 생긴다. 주기를 짧게 잡으면 — git fetch 가 잦아지는 것 자체는 싸지만, 파이프라인 동시 실행 위험이 커진다(I3 §2-7 — 단일 실행 잠금이 지금 없다).

권고

ⓐ cron ＋ 주기 5분. 근거 — ① 이 호스트에서 이미 도는 기구를 쓴다(새 환경 의존 0) ② install-schedule.sh 계열 설치 패턴을 재사용한다 ③ 5분은 「빌드+마이그레이션+교체」 1회보다 짧다 — 즉 단일 실행 잠금이 없으면 반드시 겹친다. 그래서 주기 값과 잠금은 한 묶음으로 결정하고, 잠금 없이 워처를 켜지 않는다.

되돌리는 비용 — 낮다. crontab 한 줄 · 주기 값은 설정이다. 단 「잠금 없이 먼저 켠 뒤 나중에 붙인다」의 비용은 낮지 않다 — 겹친 배포가 남기는 상태는 되돌리기 어렵다.

③ 레지스트리를 쓸 것인가 · 이미지를 몇 개 보존할 것인가 막힘

원문 · I3.md:215 — 「레지스트리 사용 여부 · 이미지 보존 개수 → [정본 무근거]」

배경

DR-5 의 본체다. 지금 태그는 전부 고정 :i2 라 빌드할 때마다 같은 이름을 덮어쓴다. 그래서 ⓐ 지금 도는 컨테이너가 어느 커밋의 산출인지 이미지 이름으로 알 수 없고 ⓑ 이전 이미지는 이름을 잃은 dangling 이 되어 되돌릴 손잡이가 없다. 문서 권고는 A — 호스트 로컬 이미지 ＋ 커밋 SHA 태그이고 근거는 「이미지는 커밋의 결정론적 산출이므로 원본은 git 이다 — 레지스트리는 캐시지 진실원이 아니다」.

지금 상태

digest 대장은 이미 섰다 — reference/IMAGE-DIGESTS.md 8건(〈165〉-㉱). 대조는 되고 복원은 재빌드다(R1-RESTORE-DRAFT §2 #9). 그리고 I3.md §0-3 이 순서 규칙 하나를 실증으로 확정했다 — 태그 보존은 빌드보다 먼저다(빌드 후에는 늦다. :i2 가 이미 새 이미지를 가리킨다). 이번 세션 P1 배포가 그 순서대로 했고 보존 5종의 이미지 ID 가 새 것과 전부 다름을 확인했다.

선택지

  • ⓐ 로컬 이미지 ＋ SHA 태그 · 보존 N 개. 호스트가 죽으면 이미지도 죽지만 커밋에서 재생 가능하다.
  • ⓑ GHCR 푸시 후 pull. 자격증명·용량, 그리고 public 레포의 이미지 공개 범위 판단이 새로 필요하다.

고르면 나중에 무슨 일이

ⓑ 를 고르면 — 비밀이 하나 늘고(레지스트리 자격), ㊻ 로 대상이 staging 한 대뿐인 동안 이득이 없다. 보존 개수를 너무 작게 잡으면 — DR-5 가 부분적으로 되살아난다(N-1 은 있는데 N-2 가 없다). 너무 크게 잡으면 — WSL2 호스트 디스크가 백업 보관처(colab-v2-backups/staging/)와 같은 디스크다. 이미지가 백업 자리를 밀어낸다.

권고

ⓐ 로컬 ＋ SHA 태그 · 보존 3개(현행 ＋ N-1 ＋ N-2). 근거 — ① 문서 권고 A 를 그대로 따른다 ② 3 이면 「직전으로 돌아갔는데 그것도 red」인 경우가 커버된다 ③ 백업 보존이 14일 · 프로파일별 최신 1개는 절대 삭제 안 함인 것과 같은 형태다 — 「기한 초과분은 지우되 마지막 하나는 안 지운다」. 같은 규칙 모양을 쓰면 운영자가 두 규칙을 따로 외우지 않는다.

되돌리는 비용 — 낮다(ⓐ→ⓑ), 높다(ⓑ→ⓐ). 로컬에서 레지스트리로 가는 것은 push 를 얹는 일이다. 반대는 자격증명 회수 ＋ 공개된 이미지의 회수 불가가 따라온다 — public 레포라 한 번 공개되면 되돌릴 수 없다.

④ 배포 원장 파일 형식 · 보존 개수 막힘

배경

롤백이 「직전 릴리스」로 가려면 그 사실이 호스트 위 파일로 남아야 한다. 지금 rollback.sh 는 compose.yml(I2 이전 자리표시 — nginx ＋ cloudflared 둘뿐, 안내 페이지)로 간다. 즉 「직전 릴리스로 되돌린다」가 아니라 「제품 이전 상태로 되돌린다」이다. 원인은 하나 — 「직전에 green 이었던 릴리스가 무엇인가」를 적어 두는 자리가 어디에도 없다.

지금 상태

문서 권고는 infra/staging/ 아래 릴리스 원장(레포 산출 · 값은 런타임 생성물 · .gitignore 로 커밋 차단). 한 줄에 커밋 SHA · 이미지 태그 · 시각 · 배포 판정(green/red) · 롤백 여부. 롤백 대상이 두 종류라는 사실을 문서와 명령에 드러낸다 — 직전 릴리스 / 자리표시. compose.yml 은 지우지 않는다.

선택지

  • ⓐ 한 줄 텍스트 append (IS3 표식 파일 모양). 사람이 cat 으로 읽는다. 파싱은 awk.
  • ⓑ JSON Lines. 기계 파싱이 쉽지만 셸에서 읽으려면 jq 의존이 생긴다.

보존 개수 — 원장은 이력이라 이미지 보존 개수와 성질이 다르다.

고르면 나중에 무슨 일이

보존을 짧게 잡으면 — 「깬 적 있는가」를 물을 자리가 사라진다. 계약 게이트가 이미 같은 결함을 갖고 있다(X-2 §4 4번 — 「기준이 HEAD 라 파괴적 변경도 커밋과 동시에 green 이 된다. 게이트는 「방금 깼는가」만 보고 「깬 적 있는가」는 못 본다 → 회차 기록이 곧 유일한 이력」). 배포 원장이 그 자리의 배포판이다. ⓑ 를 고르면 — 롤백 스크립트가 jq 에 의존하고, 복원 상황(도구가 없을 수도 있는 상황)에서 읽을 수 없는 형식이 된다.

권고

ⓐ 한 줄 텍스트 · 무기한 append(로테이션 없음). 근거 — ① 문서 스스로 IS3 표식 파일과 모양을 맞추라고 권한다 ② 복원 상황에서 cat 하나로 읽혀야 한다 ③ 한 줄 ≈ 100 B 이면 1000 릴리스가 100 KB — 로테이션 규칙을 만드는 비용이 저장 비용보다 크다. 「이력은 지우지 않는다」가 이 레포의 일관된 태도다(〈166〉-㉮ — 「이력을 지우는 것이 아니라 개정을 표시한다」).

되돌리는 비용 — 낮다. 형식 변경은 새 파일로 시작하고 옛 파일을 남기면 된다. 단 「로테이션으로 지운 이력」은 되돌릴 수 없다.

⑤ 「이미지 롤백 시 스키마는 그대로 둔다」를 규칙으로 삼는가 막힘

원문 · I3.md:249 — 「이 판단은 정본에 명시가 없다 → [정본 무근거] 로 표시하되, 되돌리는 마이그레이션이 데이터를 지울 수 있다는 점에서 rollback.sh 의 기존 원칙(「롤백이 데이터를 지우면 그건 롤백이 아니라 재해다」)의 직접 연장이다. 세션에서 확정한다」

배경

두 postgres 체인(platform·ai)은 다른 데이터베이스이고 합치지 않는다(CLAUDE.md §3-3). 자동화가 새로 답해야 할 것은 순서·전제·되돌림 셋이고, 앞의 둘은 이미 값을 치르고 알아낸 것이 있다 — GRANT 를 테이블보다 먼저 주면 GRANT ON ALL TABLES 가 빈 집합에 걸려 조용히 아무것도 안 준다(I2 §2). 남은 것이 되돌림이다.

지금 상태

권고 = 마이그레이션은 forward-only 로 간주한다. 롤백은 이미지만 되돌리고 스키마는 되돌리지 않는다. 그 대가로 한 릴리스의 마이그레이션은 직전 이미지와도 호환되어야 한다 — 추가는 되고 파괴는 안 된다. 이걸 지키지 못하는 변경은 배포 자동화가 아니라 사람이 처리할 사건으로 분류하고 멈춘다.

선택지

  • ⓐ 규칙으로 삼는다 — forward-only. 롤백 = 이미지만. 파괴적 마이그레이션은 자동화 밖 사건.
  • ⓑ 스키마도 되돌린다 — downgrade 를 파이프라인에 넣는다. 「완전한 롤백」이지만 되돌리는 마이그레이션이 데이터를 지울 수 있다.

고르면 나중에 무슨 일이

ⓑ 를 고르면 — 롤백이 재해가 될 수 있는 경로가 자동으로 도는 상태가 된다. 그리고 이 레포에는 PITR·WAL 아카이빙이 없다(R1-RESTORE-DRAFT §2 #10 — 물리 백업 없음, 논리 덤프로 대체). 즉 downgrade 가 지운 데이터를 되찾는 경로가 사실상 마지막 pg_dump 하나다. ⓐ 를 고르면 — 개발 쪽에 제약이 하나 생긴다: 「직전 이미지와 호환되는 마이그레이션만 쓴다」. 파괴적 스키마 변경은 계약 동결 해제 ㉯(사람이 연다)와 같은 층으로 올라간다 — 「마이그레이션 ≥ 1 은 언제나 사람이 연다」(〈69〉)가 이미 그 규칙이다.

권고

ⓐ 규칙으로 삼는다. 근거 셋 — ① 문서 스스로 「rollback.sh 기존 원칙의 직접 연장」이라 적었다 ② PITR 이 없는 환경에서 자동 downgrade 는 fail-open 이다 — I3 가 고치려는 성질 그 자체다 ③ 이미 계약 층에서 같은 판정을 내려 뒀다(마이그레이션 ≥ 1 → ㉯ 사람 판정). 배포 층과 계약 층이 같은 규칙을 쓰면 예외의 자리가 줄어든다.

되돌리는 비용 — 낮다(규칙 자체), 다만 지연 비용이 있다. 규칙은 문서 한 줄이다. 그러나 이 규칙 아래 쌓인 마이그레이션은 그 제약을 전제로 쓰인 것이라, 나중에 ⓑ 로 바꿔도 과거 릴리스로는 여전히 못 돌아간다.

⑥ 배포 실패 시 직전 green 릴리스로 자동 롤백하는가 막힘

선택지

  • ⓐ 자동 롤백 없음 — red 면 중단 ＋ 표식 ＋ 사람 호출. 실패한 배포가 그 상태 그대로 멈춰 있다.
  • ⓑ 자동 롤백 켬. 실패가 스스로 치유되지만 판정 버그가 곧 롤백 루프가 된다.

고르면 나중에 무슨 일이

ⓑ 를 고르면 — 판정기가 틀렸을 때 멀쩡한 릴리스가 계속 걷어내진다. 그리고 이 환경에서는 롤백이 컨테이너 교체 한 번이라 루프가 빠르다 — 사람이 알아채기 전에 여러 번 돈다. ⓐ 를 고르면 — 실패한 배포가 깨진 채로 서 있다. 다만 이 환경은 사용자가 붙기 전 staging 이라 그 대가가 작고, ①에서 표식 파일 채널을 골랐다면 침묵도 아니다.

권고

ⓒ — 기본 off, 명시 옵션으로 배선만 해 둔다. 근거 — ① 문서 권고 그대로 ② 판정기를 먼저 쌓고, 판정기의 red/green 이력이 원장에 쌓인 뒤에 켠다 — 원장(④)이 그 판단의 근거가 된다 ③ 배선을 안 해 두면 나중에 켜는 것이 새 WU 가 된다(CLAUDE.md §5 「나중에로 남기기 금지」). 배선은 지금, 스위치는 off.

되돌리는 비용 — 매우 낮다. 플래그 하나다. ⓑ 로 먼저 켰다가 겪는 롤백 루프의 비용이 비대칭적으로 크다.

배경

정본이 「prod 는 승인 게이트」라고만 적었고, ㊵ 가 승인의 성질을 이미 정해 뒀다 — ① 구현·확인은 전부 staging ② Ted 가 staging 에서 직접 보고 승인한 뒤에 넘어간다 ③ 승인 단위는 WU 가 아니라 눈으로 확인 가능한 화면·흐름. 그리고 ㊻ 이 prod 착수 시점 자체를 닫아 뒀다.

지금 상태

권고 = 파이프라인에 타깃 개념을 도입하되 목록은 staging 하나. prod 타깃은 선언은 하되 실행 경로가 비어 있고, 호출하면 ㊻ 을 인용하며 즉시 거부한다(조용한 no-op 금지). 승인은 자동 판정이 아니라 사람의 기록 — 원장에 승인자 · 시각 · 무엇을 눈으로 봤는가. 그리고 승인 없이 prod 타깃이 도는 경로가 존재하지 않음을 red fixture 로 증명한다(음성 게이트 · ai-no-lineage-write 와 같은 계열).

선택지

  • ⓐ 배포 원장에 같이 적는다(④의 파일에 승인 필드 3개 추가).
  • ⓑ 별도 승인 원장 파일. 성격이 다르니 파일도 나눈다.
  • ⓒ PLAN-SoT §9 에 등재한다. 판정 이력의 정본이 이미 거기다.

고르면 나중에 무슨 일이

ⓒ 를 고르면 — 승인이 레포 커밋 이력에 남아 되돌릴 수 없다. 다만 파이프라인이 실행 시점에 읽을 수 없다(레포 파일이지 런타임 생성물이 아니다). ⓐ 를 고르면 — 파일 하나로 「무엇이 배포됐고 누가 승인했나」가 한 줄에 읽힌다. 그러나 그 파일은 .gitignore 로 커밋이 차단된 런타임 생성물이라 호스트가 죽으면 승인 이력도 죽는다. ⓑ 를 고르면 — 위 둘의 단점을 그대로 물려받는다.

권고

ⓐ ＋ ⓒ 둘 다 — 다만 층을 나눈다. 런타임 원장(ⓐ) = 파이프라인이 읽고 쓰는 값(승인자 · 시각 · 무엇을 봤는가). §9 등재(ⓒ) = 그 승인의 판정 근거. 이 레포가 이미 쓰는 형태 그대로다 — 「HANDOFF 에는 링크만, 값과 근거는 §9 에」(CLAUDE.md §6-3). 두 곳에 같은 값을 적는 것이 아니라 다른 층을 적는 것이므로 「두 곳에 적으면 갈라진다」에 걸리지 않는다. 승인자 표기는 실명 하나(현재 승인자가 한 사람이고, 〈56〉 이 「사람 이름은 source_label 에 넣지 않는다」로 도메인 데이터와 운영 기록을 이미 갈라 뒀다 — 운영 기록에는 실명이 든다).

되돌리는 비용 — 낮다. prod 타깃이 아직 닫혀 있어(㊻) 실 승인 기록이 0 건이다. 형식을 바꿔도 옮길 데이터가 없다. 이 항목은 지금이 가장 싸다.

배경

지금 상태

범위는 적혀 있다 — 사건(재가공 · 격자 변경 · 파일 추가) 감지 → 무효화 범위 계산 → 재생성. 무효화 대상 = 렌더 산출물. 소유 = D7/viz-render(트리거 발신은 D5). 진입조건 = P3 ＋ D5 stage 2 파트. 비어 있는 것은 「무엇이 green 인가」 하나다.

무엇을 정해야 완료를 잴 수 있나

  • ⓐ 오라클의 형태 — 「사건을 일으키면 낡은 렌더가 사라지고 새것이 난다」를 어떤 관측으로 판정하는가. 산출물 파일의 mtime 인가, d7 원장의 행인가, 화면인가.
  • ⓑ 무효화 범위 계산의 정확도 기준 — 과다 무효화(전부 다시 그린다)를 통과로 볼 것인가. 통과로 보면 「범위 계산」이라는 말이 빈다.
  • ⓒ 사건 3종 각각에 최소 1건을 요구할 것인가 — S3 가 「4종 각각 최소 1건」으로 같은 모양을 쓴다.

정하지 않으면

Y-1 을 「부분 완료로 닫지 않는다」가 적용될 수 없다. WORK-UNITS §1.5 유예 금지 규칙 — 「오라클이 green 이 아니면 🟧 부분(사유) 로 남긴다」. 오라클이 없으면 🟧 인지 ✅ 인지도 판정 불가다. 그리고 Y-1 은 stage 2 끝단에 있어, 여기가 흐리면 stage 2 완주 선언 자체가 흐려진다.

권고

권고

ⓐ 완료 정의를 착수 전에 쓴다 · ⓑ 기한 문언을 「stage 1 완료 판정과 동시」에서 관측 가능한 사건으로 바꾼다. 근거 — ① 〈167〉-㉯ 스스로 근거가 약하다고 적었다. 약한 근거를 그대로 두면 다음 기한도 같은 방식으로 흐려진다 ② 관측 가능한 사건의 후보 = 「03-HANDOFF 현재 단계가 stage 2 로 바뀌는 커밋」 — 이미 일어난 사건이고 한 점으로 찍힌다 ③ 기한 정본은 WORK-UNITS §7 의 PA-G 행 하나로 유지한다(§10.2-b 는 가리키기만) — 두 곳에 적으면 갈라진다.

⑥ 규율 장치 — 왜 이렇게까지 하나

배경 절이다. 결론에 필요한 것은 한 문장이고, 나머지는 접어 뒀다.

「예외적 1회」로 설계된 것이 7회 열렸다. 그러면 그것은 예외가 아니라 운영 경로다 — 그래서 횟수 상한을 버리고 3등급제(㉮ 자동허용 / ㉯ 승인 / ㉰ 금지)로 갔다(〈163〉-㉮). 「몇 번 여는가」가 아니라 「무엇을 여는가」로 판정한다.

회차가 는 이유는 의지가 아니라 점검 축의 누락이었다 — 진단과 증거

일곱 회차의 점검 축을 나열하면 축이 매번 새로 발견됐다(X2 §3).

  • 1~3 회차 = 「응답이 무엇을 담는가」
  • 4 회차 = 「그 응답을 부를 op 이 있는가」 — listPalettes 가 없어 createRender 가 도달 불가였다. 어떤 게이트도 말하지 않았다. 없는 것은 diff 에 안 나온다
  • 5·6 회차 = 「사용자 행위가 계약에 있는가」
  • 7 회차 = 「계약이 낼 수 없는 것을 선언하고 있는가」 — 202. lint·breaking 전부 green 이었다

결론(X2 §6). 「잘못된 것 = 「1회」라는 수. 〈80〉 은 「두 번째 해제가 일어나면 이 결정은 실패」라고 못 박았고 7회가 났다. 1회는 예측 가능한 세계에서만 성립하는 수인데, 회차마다 새 축이 발견됐다. 축을 다 아는 상태가 애초에 없었으므로 1회는 지킬 수 없는 약속이었다.」

잘못이 아닌 것 = 동결. 7회 전부 Ted 승인 · 마이그레이션 0 · 게이트 준수였다. 「동결의 산출물은 「안 여는 것」이 아니라 「열 때마다 근거와 증거가 남는 것」이었고, 그 산출물은 실제로 나왔다.」

상한을 버린 대가를 무엇이 받는가

㉰-6(묶음 쪼개기로 자동 허용 만들기 금지) 이 그 자리를 직접 받는다 — 한 목적의 변경을 나눠 각 조각을 ㉮ 로 통과시키는 것은 목적 단위 판정으로 막는다. 그리고 ㉱ 증거 7항이 「주장하지 말고 보여 준다」를 강제한다.

  • 남은 막힘(I3 7건)은 1단을 막지 않는다. I3→I4 는 3단에서 본체와 병렬이므로, 7건 판정을 1단 진행과 동시에 붙일 수 있다.
