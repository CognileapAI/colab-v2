# DEPLOY-CURRENT — 철거된 PoC 배포의 기록 + v2 staging 컷오버에 필요한 것

**상태** ⛔ **철거됨(TORN DOWN)** · **철거일** 2026-08-22 · **정찰일** 2026-08-22(철거 직전)

> 이 문서는 더 이상 "지금 돌고 있는 것"의 기록이 아니다. **PoC 배포가 무엇이었는지의 기록**이고,
> **v2 staging을 같은 Cloudflare 터널에 붙일 때 필요한 것**의 목록이다.
> 옛 서술은 지우지 않고 **과거형 기록으로 보존**한다 — 컷오버 때 되짚을 곳이 여기밖에 없다.
> 각 절 머리의 **[철거됨]** 은 "그 실물은 이제 없다"는 뜻이지, 내용이 틀렸다는 뜻이 아니다.

**대상** `colab-hydro.com` (CoLAB PoC) · **호스트** WSL2 머신 1대

지금 상태 한 줄: **`www.colab-hydro.com` 은 530**(터널 커넥터가 내려감). **의도한 결과다.**
**Cloudflare 쪽 터널·DNS 설정은 살아 있다.** 지운 것은 오리진뿐이다.

## 1. 경로 한 장 — [철거됨, 2026-08-22 이전의 실물]

```
브라우저
  → Cloudflare 엣지 (www.colab-hydro.com, TLS 종료)      ← 엣지  (살아 있음)
  → Cloudflare Tunnel (원격 관리형, 토큰) → cloudflared 컨테이너   ← 유입  (커넥터 제거됨)
  → nginx:80 (컨테이너)                                   ← 라우팅 (제거됨)
        /api/         → FastAPI backend:8000
        /health       → backend:8000/health
        /viz/         → viz:8100
        /colab-data/  → MinIO:9000 (presigned 다운로드 프록시)
        /             → Vite 빌드 정적 파일
  → postgres · redis · celery · processor worker · ElasticMQ   ← 뒷단 (제거됨)
```

엣지에서 터널 입구까지는 그대로 남아 있고, **터널 아래(오리진)만 통째로 사라진 상태**다.

## 2. 엣지 (DNS · TLS) — [유효, 손대지 않았다]

| 항목 | 실물 |
|---|---|
| 네임서버 | Cloudflare (`javon.ns.cloudflare.com` / `dns.cloudflare.com`) |
| `www.colab-hydro.com` | A/AAAA = Cloudflare anycast 프록시 IP. 철거 전 **HTTP/2 200**, 현재 **530**(오리진 없음) |
| `colab-hydro.com` (apex) | **A/AAAA/CNAME 없음(NODATA)** → **HTTP/2 530**. 철거 전에도 죽어 있었다 |
| TLS | **전량 Cloudflare 엣지 종료.** 오리진은 터널 내부 평문 HTTP였다 |
| 로컬 인증서 | **없음.** certbot·Let's Encrypt 디렉터리 자체가 없었다 |

인증서 만료 리스크는 없다. 대신 **Cloudflare 계정과 터널 토큰이 단일 실패점**이다.
실서비스 진입점은 `www` 하나뿐이므로, v2 staging을 붙일 때 apex/www 정책을 먼저 정해야 한다.

> **측정 조건** — 이 셸은 로컬 DNS 해석이 막혀 있어 DoH + `curl --resolve` 로 확인했다.
> 값 자체는 확실하지만, 재확인할 때 같은 방법이 필요할 수 있다.

## 3. 유입 (Cloudflare Tunnel) — [터널은 유효 · 커넥터만 철거됨]

- 터널은 **remotely-managed** — 설정이 Cloudflare 대시보드에 있다. 호스트에 `cloudflared` 설정 디렉터리도 로컬 ingress yml도 **없었다.**
- 컨테이너 실행 커맨드는 `--token ${CF_TUNNEL_TOKEN}`. 토큰이 프로세스 목록에 평문 노출됐다(운영 위생 이슈).
- ngrok·포트포워딩·호스트 nginx/caddy는 **없다.** 외부 노출 경로는 터널 하나뿐이었다.
- **철거로 사라진 것은 커넥터(컨테이너)뿐이다.** 터널 자체와 ingress 규칙은 대시보드에 그대로 있다 —
  v2 staging이 같은 토큰으로 커넥터를 다시 띄우면 같은 주소가 살아난다.

## 8. 백업 사건 — 2026-07-11 ~ 08-17 백업 전량 무효

**증상.** `backups/postgres/` 의 `*.sql.gz` 가 **전부 20바이트(gunzip 결과 0바이트)**. 로그에는 매일 "Dumping..."만 남았다. 즉 **해당 기간 복구 가능한 Postgres 백업이 하나도 없었다.**

**원인은 셋이 겹쳤다.**

| # | 원인 |
|---|---|
| ① | 크론이 **죽은 트리**의 스크립트를 돌려 compose가 다른 프로젝트를 못 찾았다 |
| ② | `gzip -c > $FILE` 리다이렉션이 pg_dump보다 **먼저 파일을 만들고**, `set -e` 가 가드에 닿기 전에 스크립트를 죽였다 |
| ③ | 가드가 **압축 파일 크기(`[[ -s ]]`)와 `gzip -t`만** 검사해 20바이트 빈 gzip을 통과시켰다 |

**조치.** 임시파일로 받고 → `PIPESTATUS[0]` 로 pg_dump 종료코드를 확인하고 → **복원된 `CREATE TABLE` 개수**를 검사한 뒤에야 `mv` 한다. 크론은 **실제 기동 트리**로 재지정했다.

## 10. v2 staging 컷오버에 필요한 것

터널이 살아 있으므로 컷오버는 **DNS가 아니라 커넥터·라우팅 문제**다. 필요한 재료는 셋이다.

| 재료 | 어디에 있나 |
|---|---|
| **터널 토큰** | 홈의 `.colab-poc-env.prod.bak` (`0600`). 이것이 있어야 새 커넥터가 같은 터널에 붙는다. **레포에 넣지 않는다** |
| **설정 스냅샷** | 레포의 `dev-package/reference/poc-deploy/` — `compose-resolved.yml`(전개본, 시크릿 마스킹) · `nginx.conf`(실효 conf). 컨테이너 구성·포트·프록시 라우팅의 사실 기록. **참조용이며 계승 대상이 아니다** |
| **터널 ingress 규칙** | **Cloudflare 대시보드에만 있다.** 레포에 재현본이 없다 — 컷오버가 수작업에 의존하는 지점(§11) |

스크래치패드에만 두고 레포에 넣지 않은 것: **PoC 스키마 덤프**(WU-G5가 `DATAMODEL-BASELINE.md` 로 이미 증류했고,
사본을 또 두면 `CLAUDE.md §5` 가 금지하는 코드·스키마 계승을 부른다) · **MinIO 버킷 목록** · **crontab**.
셋 다 세션 종료와 함께 소멸한다.

### 컷오버 — 이점과 남은 위험

**이점**

- **엣지가 터널이라 DNS를 건드리지 않는다.** 터널 라우팅만 바꾸면 공개 주소가 새 오리진을 향한다.
- **롤백이 되돌리기 한 번이다.** DNS 전파를 기다릴 필요가 없다.
- 오리진 인증서 개념이 없어 TLS 작업이 컷오버 경로에서 빠진다.
- 철거로 **오리진이 비어 있어** 새 staging이 기존 스택과 포트를 다툴 일이 없다.

**남은 위험**

| # | 위험 | 성격 |
|---|---|---|
| 1 | **라우팅 정본이 Cloudflare 대시보드에만 있다.** 레포에 재현본이 없어 컷오버가 수작업에 의존한다 | v2에서 **IaC로 끌어와야 한다** |
| 2 | **터널 토큰 사본이 홈의 파일 하나뿐이다.** 이걸 잃으면 터널 재연결에 대시보드 재발급이 필요하다 | 단일 실패점 |
| 3 | **백업이 지금 0이다.** 크론은 껐고 데이터는 없다. staging에 데이터가 들어오는 순간 §8이 재발할 수 있다 | 착수 전 해소 |
| 4 | 서비스가 WSL2 머신 1대에 얹혀 있어 **호스트 재부팅·Windows 업데이트가 곧 서비스 중단**이다 | staging 재사용 시에도 유효 |

## 12. 후속 WU 후보

각 항목은 **무엇을 막는지**와 함께 적는다. 철거로 사라진 항목(MinIO 스냅샷 복원 리허설·PoC 데이터 이관 규격)은 뺐다.

| 후보 | 작업 | 이것이 없으면 막히는 것 |
|---|---|---|
| **v2 staging을 기존 터널에 연결** | 보관한 토큰으로 커넥터를 다시 띄우고, 터널 ingress를 v2 staging 오리진으로 돌려 `www` 530을 해소 | staging 배포 전부. `CLAUDE.md §4`의 "I2 이후 staging green" 조건이 성립하지 않는다 |
| **staging 백업 체계 수립** | 비활성화한 PoC 크론을 되살리는 대신, v2 staging 기준으로 백업·복원을 새로 설계. §8의 fail-closed 검증(복원된 테이블 수 확인)을 **처음부터** 요구조건에 넣는다 | staging에 실데이터를 넣는 모든 작업. 지금 백업은 0이다 |
| **터널 라우팅 IaC화** | Cloudflare 대시보드의 터널 ingress 규칙을 레포의 `infra/` 에 선언형으로 재현하고, 대시보드와의 diff를 게이트로 검사 | 컷오버의 재현성. 정본이 레포 밖이면 I2·I5가 수작업이 된다 |
| **apex/www 정책 결정** | apex 530 해소 여부와 최종 공개 주소 형태를 확정 | I5 prod 전환 |
| **노출 포트 정합화** | PoC에서 5432·8100이 의도와 달리 호스트에 열려 있던 문제를 staging 구성에서 반복하지 않도록 규격화 | staging 재사용의 전제 |
| **터널 토큰 취급 개선** | 프로세스 목록 평문 노출을 제거(파일·시크릿 주입 방식으로 전환)하고, 홈의 사본 하나에 의존하는 상태를 해소 | staging 재사용. 토큰 유출 = 오리진 장악, 토큰 분실 = 터널 재발급 |
| **기동 트리 정리** | 보존한 두 PoC 트리의 처분(보관·아카이브·삭제)을 결정 | 디스크·혼선 정리. 급하지 않으나 열어 두면 다시 "어느 트리가 진짜인가"가 된다 |
