# Intent: dev 검증 데이터 전면 삭제와 실물 참조 데이터 재적재 — 화면 조작 시나리오로 고정
메타 — 발의자: Ted · 작성 2026-09-13 · 승인 Ted 판정 2026-09-13(항목별 아래 표기)
상태 — 확정 — Ted 판정 2026-09-13 ＋ 에이전트 확정(근거 기재) · 구현·검증 완료를 뜻하지 않음

## 문제
- dev 에 든 데이터는 검증 목적으로 쌓인 것이다. 마지막으로 적힌 값은 운영자 전 연구실 읽기 화면 기준 데이터셋 26건(2026-09-12)이고 업로더 이름이 시험 계정이다. `[미확인 현재값]` — 현시점 계수는 재측정하지 않았다.
- dev 를 사람이 쓰는 상태로 세우는 절차가 반복 실행 가능한 형태로 없다. 지금까지의 적재는 적재 스크립트 1개와 계정·연구실 SQL 여러 개로 나뉘어 있고, 화면을 실제로 눌러 만든 기록이 아니다.
- 포맷 5종(grib · nc · bin · tif · hdf)의 미리보기가 dev 실물에서 확인된 기록이 없다. 포맷 완주 검사는 로컬 원천 마운트를 상대로 돌고 브라우저·dev 주소를 상대로 돌지 않는다(`gates/tools/e2e-format-coverage.sh:33-40`).

- 시나리오의 시작 상태 = 「초기화 도구 1회 실행 직후」로 고정한다.

- 계보 간선 18건이 선다 — precipitation 4 ＋ vegetation 7 ＋ drought 0 ＋ 포멧테스트 7. 내역 — precipitation 4간선(Lv.0 HSR→Lv.1 HSR · Lv.0 rn15→Lv.1 rn15 · Lv.1 HSR→Lv.2 · Lv.1 rn15→Lv.2) · vegetation 7간선(Lv.0→Lv.1 GK2A · DEM→경사향 · Lv.1 GK2A·DEM·경사향·토지피복·HLS→Lv.2) · drought 0간선(Ted 확정 · 설명 문서에 파생 관계 기재 없음) · 포멧테스트 7간선(포맷 폴더 `00.Data` 원본 → `02.Results` 결과 · 타일별).
- 소유 = 고려대학교 수문학 연구실(전창현 교수). 데이터를 만든 계정이 그 연구실 소속이다.
- 화면 조작 시나리오 파일이 레포에 있고, 같은 문서로 dev 를 상대로 다시 실행할 수 있다(단계·입력값·기대 화면이 한 곳에 적혀 있다).

### 실행 순서 초안 (미승인 · 각 단계의 비가역 표시)
1. 현재 계수 실측 1회 — 데이터셋·파일·객체 계수를 파일로 고정. 읽기 전용 · 기록용이며 삭제 목록 고정 목적이 아니다.
2. ⛔ **dev 전용 초기화 도구 신설 — 별도 선행 작업 단위.** 완료 정의 = dev 식별자 검증(버킷 이름 ＋ DB 식별자) ＋ 명시 플래그 없으면 거부(fail-closed 실패 픽스처 포함) ＋ 두 DB 스키마 재생성 ＋ 접두사 2개(`uploads/`·`previews/`) 비우기 ＋ `_ops/` 무접촉 ＋ 실행 후 자체 점검 15/15.
3. ⛔ **비가역 · Ted 명시 GO 필요** — 2단계 도구 1회 실행. 원장 행 1건이 같이 필요하다. 버저닝 탓에 삭제 후에도 이전 판이 30일 남는다(즉시 소멸 아님).
4. 연구실·계정 준비 — 대상 연구실 1개와 소유 계정. 연구실을 만드는 화면이 없다(아래 ㈓).
5. 화면 투입 — 로그인 → 프로젝트 생성 4건 → 프로젝트별 업로드 모달로 데이터셋 1건씩 → 기준 격자 파일 부착 → 계보 설정. 되돌리는 수단이 2단계 도구뿐이므로 투입 중 오입력은 그대로 남는다.
6. 확인 — 각 데이터셋 상세에서 미리보기 확인 · 자체 점검 15/15 한 번의 실행.
7. 시나리오 고정 — 5·6단계를 단계·입력값·기대 화면으로 문서화해 레포에 둔다.

## 제약
- 현재 규칙은 목록 고정 삭제만 허용하고 접두사 삭제·DB 재생성 경로가 없다(`.claude/rules/deploy.md:42-49` · 프리픽스 일괄 삭제 도구 부재 = 정찰 산출 G-2) — dev 한정 예외를 결정 행으로 등재해야 한다(규칙 개정 필요 · 미승인).
- 경계를 걸지 않으면 삭제가 0행에 조용히 성공한다. 계수 판정도 같은 경계가 실린 경로로만 한다(`.claude/rules/deploy.md:42-46`).
- `_ops/backups/` 는 지우지 않는다 — 지우면 자체 점검 ⑭ 가 red 가 된다.
- 활동 이력·다운로드 이력 표는 트리거가 DELETE 를 막는다(`services/core-api/ops/purge_datasets.py:23-25`) — 행 삭제로는 비워지지 않으므로 스키마 재생성이 필요하다.
- 적재 원천 4.4 GB(v2 재목록 실측 · 종전 3.7 GB)는 외부 드라이브에 있다. 드라이브가 붙어 있어야 투입이 가능하다.
- 업로드 크기 상한 상수는 없다 — 16 MiB 이상은 멀티파트로 갈라 올린다(`services/core-api/src/colab_core/app/routes/upload_transfers.py:44,214`). 149.5 MB 파일 1건도 이 경로로 처리된다. 1회 업로드 파일 수 상한 500 · 파일명 255자(`services/core-api/src/colab_core/app/routes/ingestion.py:49,53`).
- 기준 격자 파일은 데이터셋당 2건이 상한이다(`services/core-api/src/colab_core/app/routes/upload_transfers.py:40`).
- 화면 업로드 총량 — 데이터 3,641,736,593 B ＋ 격자 부착 2,489,512,224 B(데이터셋마다 위경도 쌍을 다시 붙이는 계수) ≈ 6.1 GB(재목록 v2 §5-5). 업로드는 화면에서 1건씩이므로 소요는 파일 수·바이트에 비례한다.
- AI 없이도 완결(`CLAUDE.md §3`) — 이 범위에 AI 지점 없음.
