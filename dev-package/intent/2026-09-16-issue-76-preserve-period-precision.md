# Intent: 데이터셋 수정에서 기간의 시각을 표시하고 보존
메타 — 발의자: samtae0610 · 작성 2026-09-16 · 승인 2026-09-16

## 문제
- 분 단위 데이터도 수정 화면에서 날짜까지만 보여 기존 시각을 확인하거나 수정할 수 없다.
- 기간을 변경하면 날짜를 자정 UTC로 다시 조립하는 경로 때문에 기존 시각을 잃을 수 있다. 다른 항목만 수정해 기간 요청이 생략되는 경우와 구분한다.

## 원한 결과 (proposed outcome)
- 수정 화면에서 기간 최소 단위에 따라 년·월·일·시·분·초까지 필요한 자리를 표시하고 편집할 수 있다. 분 단위이면 `2026-09-18 23:30`까지 확인할 수 있다.
- 기간을 바꾸지 않고 저장하거나 다른 항목만 수정하면 기간을 변경 요청에 포함하지 않아 원래 시각과 최소 단위를 보존한다.
- 저장 응답을 기다리는 동안 화면을 먼저 갱신하는 처리에서도, 변경하지 않은 기간의 원래 시각을 유지한다.
- 기간을 변경해 저장한 결과가 상세 조회와 다시 연 수정 화면에서 동일한 시각·단위로 확인된다.
- 단위를 더 거칠게 바꾸면 등록 화면의 기존 규칙대로 하위 자리를 정리하며, 숨겨진 시각이 저장되지 않는다.
- 종료 시점 없음, 기간 전체 없음, 최소 단위가 없는 기존 데이터의 의미를 보존한다. 수정하지 않은 기존 데이터에 단위 재선택을 강제하지 않는다.

## 영향 범위
- 사용자 / 화면: 데이터셋 상세의 수정 폼 중 기간 입력.
- 서비스 · 스키마 · 계약: 기존 `DataPeriod` 및 데이터셋 수정 API 재사용. 서버·스키마 변경 없음.
- 계약 파괴 여부: 아니오.

## 제약
- 등록 화면에 있는 기간 입력과 년~초 단위 규칙을 재사용하며 새 날짜 입력 라이브러리를 추가하지 않는다.
- 브라우저 현지시간 변환으로 시각이 이동하지 않도록 기존 UTC 문자열 처리 규칙을 유지한다.
- 무변경 저장, 다른 필드만 변경, 분·초 편집, 단위 축소, 끝 없음, 기간 삭제를 검증한다.
- 최소 단위 미지정 데이터도 무변경/다른 필드만 저장하는 두 경우를 검증하고, 저장 응답 전 화면에서도 기존 시각이 유지되는지 확인한다.
- 프런트 관련 검사와 실제 브라우저 편집·저장·재조회 검증을 수행한다. 현재는 정적 조사만 완료했으며 시험·브라우저 재현은 미실행이다.

## 설계트리 (grill-me 결과)
- Q1 어떤 정밀도로 보여야 하는가 → A 이슈가 요청한 대로 기간 최소 단위까지 표시한다. 단위 목록은 기존 계약의 년~초 여섯 값을 유지한다.
- Q2 새 입력기를 만드는가 → A 기존 등록 화면의 기간 입력과 자리 분해·조립 처리를 재사용하는 최소 변경을 권고한다. 사용자에게 구현 방식의 선택을 요구하지 않는다.
- Q3 단위를 낮출 때 숨은 시각은 어떻게 하는가 → A 등록 화면과 같은 하위 자리 정리 규칙을 따른다.
- Q4 기간을 건드리지 않은 저장은 어떻게 하는가 → A 원본 기간을 그대로 유지하고 기간 변경 요청을 생략한다. 기존 단위 미지정 데이터도 보존한다.
