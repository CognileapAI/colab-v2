# 로그인 신뢰성과 복구 — 확정 intent

상태: 두 라운드의 총 8개 정책 승인 완료. 이 문서는 사용자 의도 확정본이며 구현·검증 완료를 뜻하지 않는다.
출처: 이번 대화의 로그인 전수검사 및 “intent부터 엄격히 정리” 요청.
근거: [검사 기록](../reports/stage3-password-change/lane-worker/full-audit/tests/login-audit.md).

## 해결하려는 문제

기존 정상 흐름·회귀시험 통과만으로는 비밀 정보의 보호, 여러 탭과 늦은 응답 사이의 로그인 일관성, 통신 실패 이후 복구를 보장하지 못했다. 오류 상황에서도 사용자가 누구로 로그인돼 있는지, 무엇이 끝났는지, 다음에 무엇을 하면 되는지 알 수 있어야 한다.

## 유지되는 사용자 결정

- 서비스 운영자가 기존 연구실과 교수/연구원 역할을 지정해 계정을 생성한다. 기존 이메일은 덮어쓰지 않는다.
- 운영자가 초기 비밀번호를 전달하고 첫 로그인에서 변경한다.
- 변경 화면에는 새 비밀번호·확인 두 칸을 둔다. 초기 비밀번호를 다시 입력시키지 않는다.
- 비밀번호 조건은 입력 전에 안내한다.
- WSL stage에서 검증한다. 실제 사용자 비밀번호를 시험 목적으로 변경하지 않는다.

## 해결 대상의 근거

검사에서 오류응답의 입력 원문 반사, 통신 실패 후 대기 상태 고정, 늦은401의 새 세션 제거, 탭 간 로그아웃 미동기화, 이메일 길이 불일치, 로그인 방식 부분 혼합, 문자 길이 단위 불일치의 7종을 확인했다.

## 이번 대화에서 확정한 8개 정책

승인 근거: 첫 라운드 6개 질문·권고안에 사용자 “모두 그렇게 하자”, 후속 2개 질문·권고안에 사용자 “모두 권고대로”. 앞선 단독 “좋아”를 정책 승인으로 소급하지 않는다.

1. 같은 브라우저의 모든 탭은 같은 계정으로 맞춘다. 새 계정을 확인하기 전에는 이전 계정 화면을 가린다.
2. 로그아웃은 현재 브라우저의 모든 탭과 해당 서버 세션을 종료한다. 다른 기기의 로그인은 유지한다.
3. 로그인한 시점부터 12시간 유지하고 자동 연장하지 않는다. 이후 재로그인한다.
4. 작성·업로드 중인 탭이 있으면 계정 전환을 막고, 작업을 마치거나 명시적으로 취소하도록 안내한다.
5. 오프라인 로그아웃은 현재 화면의 로그인 정보를 먼저 지우고, 서버 종료를 확인하지 못했다는 안내를 표시한다. 서버 종료 완료로 표시하지 않는다.
6. 비밀번호 변경 요청의 응답이 유실되면 변경 여부를 단정하지 않는다. 자동 재전송하지 않고 새 비밀번호로 재로그인하도록 안내한다.

7. 12시간이 만료되면 새 제출을 막고 재로그인을 요청한다. 작성 내용은 현재 탭에 임시 보관하며 같은 계정으로 재로그인한 뒤 복구한다. 이미 서버가 접수한 업로드는 실제 처리 상태를 확인한다. 만료 시간을 연장하거나 성공을 추정하지 않는다.
8. 오프라인 로그아웃 후 연결이 돌아오면 해당 이전 세션의 서버 종료만 자동 재시도한다. 새 로그인 세션은 종료하지 않는다. 앱을 닫아 재시도하지 못하면 서버 종료를 보장하지 않으며 해당 세션의 원래 12시간 만료가 상한이다.

실패 제한의 기존 승인(자격/클라이언트 각각5회/15분·성공 시 초기화·프로세스 메모리)은 유지하며 수치를 재질문하지 않는다.
문자 길이 계산·입력 형태 allowlist·비밀 제거의 세부 구현은 기존 정책을 바꾸지 않는 방향으로 spec에서 정합성을 증명한다.

## spec에서 입증할 약속

- 비밀번호·접속 코드 원문이 오류응답이나 로그로 되돌아오지 않는다.
- 오래된 요청이 새 로그인 상태를 지우거나 이전 계정 화면을 새 계정 권한과 섞지 않는다.
- 네트워크 실패 후 사용자가 재시도할 수 있고, 저장 여부가 불명확하면 성공/실패를 단정하지 않는다.
- 계정 생성에서 허용한 로그인 정보는 로그인에서도 허용한다.
- 최초 변경은 인증된 제한 세션으로만 가능하며 동시 요청에서도 한 번만 완료된다.
- 로그아웃·만료·탭 전파는 위에서 승인된 범위 안에서 실제 서버/화면 시험으로 증명한다.

정책 질문은 위 8개로 확정했다. 이 약속을 spec에서 관찰 가능한 결과와 실패 시험으로 구체화한다. 새로운 정책 선택이 필요해지면 기존 승인을 확대 해석하지 않고 별도로 제시한다.

## 실행 경계

기존 spec/실행 계획은 미승인 초안으로 표시했다. 기존 제품을 되돌리거나 배포를 취소하지 않는다.
이번 요청은 intent 정립이며 코드 수정·새 배포는 수행하지 않는다. 확정 후 spec→계획을 다시 대조하고 구현 단계로 넘긴다.
커밋·push·AWS dev/prod 변경·외부 메시지 전송을 이 문서가 승인하지 않는다.

## 사실조회 반영

`dev-package/sessions/20260910-stage12-decisions.md`의 실패 제한 승인은 유지한다. 과거 무상태 서명 토큰·localStorage 방식은 채택됐지만 서버 조기 회수와 탭/기기 범위는 당시 미정이었다. 이번 6개 정책 승인으로 현재 브라우저의 서버 세션 종료와 고정12시간을 새로 확정했다. 따라서 기존 무상태 구현만으로 새 정책을 충족한다고 보지 않으며 세션 식별·서버 무효화 설계가 필요하다. 첫 변경 강제·새 비밀번호+확인은 이번 대화의 사용자 승인에 근거한다.

## 기존 spec·계획 재작성 필수 사항

- 현재 브라우저 세션만 서버에서 무효화하면서 다른 기기는 유지할 수 있는 세션 식별·회수 모델을 설계한다. 기존 계정 단위 version 증가만으로 대체하지 않는다.
- 오프라인 종료 재시도에 필요한 최소 정보의 보관·제거·만료, 이전 세션과 새 세션의 분리를 명시한다. 화면 로그아웃이 서버 종료 완료로 오인되지 않게 한다.
- 여러 탭의 작성/업로드 상태 공유와 계정 전환 차단을 설계한다. 이전 사용자 데이터를 새 계정에 복원하지 않는다.
- 만료 중 초안 보관은 현재 탭 범위이며 브라우저 종료 후 영구 복구를 약속하지 않는다. 비밀번호 입력값은 보관 초안에 포함하지 않는다.
- 고정 만료 시점은 서버에서도 검증하고, 첫 비밀번호 변경·토큰 교체가 같은 로그인 수명을 암묵적으로 연장하지 않도록 명시한다.
- 서버에 이미 접수된 작업의 상태를 조회해 안내한다. 오프라인 재시도가 계정 생성·비밀번호 변경·업로드를 자동 중복 실행하지 않도록 구분한다.
- 기존 7종 결함 수정뿐 아니라 이 8개 정책의 정상·실패·경합 시나리오를 모두 완료 조건으로 연결한다.

기존 spec의 “서버 회수는 별도 후속”, “DB migration 없이 적용”과 같은 가정은 새 정책과 충돌할 수 있으므로 실행 근거로 사용하지 않는다. 상세 설계와 계획 재작성 전 신규 구현은 시작하지 않는다.
