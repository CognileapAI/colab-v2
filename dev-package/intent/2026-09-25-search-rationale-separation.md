# Intent: 검색 결과 카드에서 「왜 이 결과?」 근거를 자료 설명과 구분되게 표기한다
메타 — 발의자: Ted · 작성 2026-09-25 · 승인 미승인

## 문제
- 검색 결과 카드에서는 자료 설명(요약) 바로 아래에 검색 근거 문장이 이어진다. 두 문단은 같은 글자 크기와 줄 간격을 쓰고, 라벨·구분선·배경이 없다. 그래서 사용자는 어느 문장이 자료 등록자가 쓴 설명이고 어느 문장이 검색이 붙인 이유인지 구분하지 못한다(Ted 발의 원문: "llm검색이 된 이유를 같이 알려주는거같은데 이건 구분되게 표기해서 데이터의 디스크립션과 구분해줄수있을까? 이건 인텐트로 넣어줘").
- 코드 근거(develop `67a03a05`)
  - 요약: `frontend/src/components/search/SearchHitCard.tsx:73-75` `<p className="hit-summary">`
  - 근거: `:77-79` `<p className="hit-why" data-testid="search-rationale">`. 라벨 없이 문장만 넣는다.
  - 스타일: `search.css:95-98` `.hit-summary`는 13px·행간 1.6·`--color-text`, `:99` `.hit-why`는 13px·행간 1.6이고 색 지정이 없다. 두 문단의 모양이 사실상 같다.
- 정본은 이미 이 구분을 요구한다. `Policy_데이터_찾기.md:148` 「AI 근거 블록」: 「좌측 코랄 선과 코랄 라벨의 "왜 이 결과?" 한 줄 … AI가 만든 설명임이 색으로 읽힌다」. 목업 `데이터_찾기_260817.html:218-221` `.rc-why`는 좌측 `--color-ai` 2px 선, 가라앉은 면, `.wl` 라벨 「왜 이 결과?」로 이루어져 있다.
- 코드 주석 `search.css:93-94`는 「근거는 코랄 라벨을 단 AI 문장이고 … 색으로 갈린다」고 적는다. 그러나 해당 규칙 `:99`에는 색도 라벨도 없다. 주석이 실제 구현과 다르고, 정본 §8 AI 근거 블록은 구현되지 않았다.

## 원한 결과 (proposed outcome)
- 결과 카드마다 근거 문장이 라벨이 보이는 별도 영역 안에 있다. 라벨 문구는 Q1a에서 정한다. 이 영역은 요약 문단(`hit-summary`)과 다른 DOM 요소다.
- 근거 영역은 요약 문단과 시각적으로 다르다. 최소한 좌측 AI 액센트 선과 라벨 색이 다르며, 라이트와 다크 두 테마 모두 그렇다.
- 근거 문장은 계속 한 줄로 고정한다(`AiRationale` 줄바꿈 금지 · `common.json:186-191`). 펼침·더보기는 두지 않는다(`Policy §8:148`).
- 잠긴 카드와 Verified 카드에도 같은 영역이 선다. 0건 화면과 검색 불가 화면은 변하지 않는다.
- 검증
  - 시험 1건 이상(vitest)을 둔다. 카드 안에서 ⑴ 라벨 텍스트가 있고 ⑵ `search-rationale` 텍스트가 응답 `rationale`과 같고 ⑶ 근거 영역이 `hit-summary`와 다른 요소·다른 클래스인지 단언한다.
  - 기존 `frontend/test/search.test.tsx:159-166`(근거 한 줄 · 더보기 없음)은 green을 유지한다.
  - 게이트 `frontend-design-lint`가 green이다.
  - agent-browser로 dev 검색 결과 카드를 라이트와 다크에서 캡처하고 두 영역이 구분되는지 대조한다(`AGENTS.md` · UI 변경은 실제 브라우저로 검증).

## 가치 가설
- 검색 사용자는 자료 설명과 검색 근거를 한눈에 구분하게 된다. 그 결과 자료 내용을 검색의 판단으로, 검색의 판단을 자료의 사실로 오인하지 않는다. 결과를 고를 때 근거 문장이 밝힌 한계(「기간·지역·품질은 확인하지 못했으니…」)를 자료 설명과 따로 읽는다.
- 확인 방법: Ted가 dev 결과 화면(교수 계정 1개 · 운영자 계정 1개)을 보고, 추가 설명 없이 두 영역이 구분되는지 판정한다. 캡처 전후 비교와 시험 green을 PR 요약의 「원한 결과 ↔ 실제 ↔ 근거」 표에 싣는다. Ted가 여전히 헷갈린다고 하면 가설이 틀린 것으로 본다.

## 설계트리 (grill-me 결과)
- Q1 표기 방식: ⓐ 접두 라벨 + 좌측 선·배경(정본 §8 `.rc-why` 모양) / ⓑ 별도 접이식 블록 / ⓒ 아이콘+색만 → A <대기>
  - 권장: ⓐ. 정본 `Policy §8:148`과 목업 `.rc-why`(`:218-221`)가 이미 이 모양이고, 코드 주석 `search.css:93-94`가 약속한 것도 이것이다.
  - 반대 사유: 카드마다 면과 선이 하나씩 늘어 목록 밀도가 떨어진다. ⓑ는 `§8:148` 「펼침·더보기를 두지 않는다」에 정면으로 걸린다. ⓒ는 색만으로 뜻을 전해 WCAG 1.4.1을 어기고, Ted가 말한 「구분되게 표기」를 글자로 충족하지 못한다.
  - Q1a 라벨 문구: 「왜 이 결과?」(정본·목업 축자) / 「검색이 고른 이유」(Ted 표현) → A <대기>
    - 권장: 「왜 이 결과?」. 정본 용어표 `Policy §4:96`·`§8:148`과 같은 문구여서 화면과 정본이 갈리지 않는다.
    - 반대 사유: 「검색이 고른 이유」는 주체(검색)를 드러내므로 자료 설명과의 구분이 더 직접적이다. Ted가 그 문구를 원하면 정본 개정이 필요하다(기획 원본 무수정이라 별도 절차).
- Q2 자료 설명(요약)의 노출 범위: 첫 2줄 + 더보기 / 전문(현행) → A <대기>
  - 권장: 전문(현행 유지). 이 intent의 목적은 근거와 설명의 구분이다. 요약 줄 처리는 상세 헤더 여러 줄 펼침 판정(`DetailHeader.tsx:11-24`, 「Ted 최종 확인 대기」)과 묶여 있으므로, 여기서 정하면 두 화면이 갈린다.
  - 반대 사유: 시드 요약에는 전각 슬래시로 이은 긴 문단이 있다(`DetailHeader.tsx:14-15`). 전문을 보이면 근거 영역이 카드 아래로 밀려 목록을 훑기 어렵다. 2줄 말줄임(CSS `line-clamp`)은 정보를 지우지 않고 카드 높이만 맞춘다.
- Q3 AI(llm) 해석과 규칙(낱말 일치·조건) 근거에 같은 라벨을 쓸지, 「AI가 읽은 조건」·「일치한 낱말」로 나눌지 → A <대기>
  - 사실 관계: 근거 문장은 전부 core-api의 템플릿 조립이다.
    - AI 해석 경로 문장은 `dataset_search.py:66-93`이 조립한다: 「{연구실} 안 N건에서 ‘낱말’가 {자리}에 맞았어요 — 기간·지역·품질은 …」.
    - `catalog.py:598-611`이 여기에 조건·온톨로지·계보 문장을 덧붙인다.
    - 조건 검색 경로는 고정 문장 1개를 쓴다(`catalog.py:717`).
    - LLM(ai-service interpret)이 주는 것은 검색어·주제·`source`뿐이다(`d10_ai_services.py:152`).
    - 해석이 LLM에서 오지 않으면 문장 앞에 「질의 해석 없이 질문의 낱말 그대로 찾았고,」가 붙는다(`dataset_search.py:91-92`, `catalog.py:584`).
  - 권장: 같은 라벨 하나. 문장은 한 줄로 고정되어 있고(`common.json:186-191`), 둘로 나누려면 계약과 서버 조립을 함께 바꿔야 한다. 또 모든 문장이 규칙으로 조립되므로 「AI 문장」과 「규칙 문장」을 가를 근거가 약하다.
  - 반대 사유: Ted는 이 문장을 「llm검색이 된 이유」로 읽었다. 어느 부분이 모델 해석이고 어느 부분이 낱말 일치인지 보이지 않으면 이 오인이 계속된다. 둘로 나누면 해석이 틀렸을 때 사용자가 그 부분만 의심할 수 있다. 이를 위해서는 계약 비파괴 선택 필드 설계가 필요하다.
- Q4 접근성: 영역에 `aria-label`(또는 `role="note"`)만 둘지, 보이는 라벨 텍스트를 둘지 → A <대기>
  - 권장: 보이는 라벨 텍스트(Q1a)를 근거 문장 앞 형제 요소로 둔다. 그러면 `aria-label`이 없어도 라벨이 먼저 읽힌다. 색과 선은 보조 수단으로만 쓴다(WCAG 1.4.1).
  - 반대 사유: 카드마다 라벨이 반복되어 스크린리더가 N번 읽는다. `aria-label`만 쓰는 편이 조용하다. 다만 그 방식으로는 시각 사용자의 구분 문제가 해결되지 않는다.
- Q5 적용 범위: 검색 결과 카드만 / 자료 상세 검색 근거 편집 화면(`SearchEvidenceEditor.tsx:209`)·조건 검색 판단 패널(`SearchAssessment.tsx:29-44`)까지 → A <대기>
  - 권장: 결과 카드만. 상세의 「검색 근거」는 사람이 검토하고 기록하는 파일 근거 편집 폼이지 AI 설명이 아니다. 조건 검색 패널은 이미 `<h2>`「조건과 근거로 찾았어요」와 `aria-label`「검색 조건과 근거」로 구분되어 있다(`SearchAssessment.tsx:30-31`).
  - 반대 사유: 「근거」라는 말이 세 화면에서 서로 다른 뜻(검색 이유 / 사람이 기록한 파일 근거 / 조건 판단)으로 쓰인다. 카드에만 라벨을 달면 용어 혼선은 남는다.
