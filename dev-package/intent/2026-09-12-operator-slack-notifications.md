# Intent: 운영자에게 시스템 상태와 사용자 활동을 Slack으로 알린다
메타 — 발의자: Ted · 작성 2026-09-12 · 승인 2026-09-12

## 문제
- 운영자는 배포 결과와 서비스·백업 이상, 복구 여부를 제때 알아야 한다. 기존 배포 완료 Slack만으로는 실패와 장애 대응 요구를 충족하지 못한다.
- 개발자·운영자가 매일 누가 언제 무엇을 했는지 확인할 일일 보고가 필요하다. 현재 활동·다운로드·권한 변경 감사 기록은 나뉘어 있고, 일일 Slack 보고로 통합되어 있지 않다.

## 원한 결과 (proposed outcome)
- 개발자·운영자는 개발 상태 전용 Slack 채널에서 환경을 구분한 배포 성공·실패, 배포 후 검증 실패, 서비스·백업 이상과 복구를 확인한다. AWS가 제공하는 관련 상태와 CoLAB 자체 점검 결과를 함께 다룬다.
- 배포 결과는 건별로 알리고, 이상·복구는 감지 시 알린다. 같은 이상이 지속되는 동안 반복 통지는 줄여 새로운 사건과 복구를 구분할 수 있게 한다.
- 별도 사용자 활동 보고용 Slack 채널 하나에서 매일 한국 시간 오전 8시에 전날 00:00 이상 당일 00:00 미만의 활동·감사 기록을 받는다. 개발 상태 채널과 분리하며, 일일 요약과 상세 감사 내역을 다시 별도 채널로 나누지 않는다.
- 보고 대상은 실제 사용 환경의 모든 연구실이다. 시험 활동은 제외한다. 대상 활동은 업로드·변경·삭제, 프로젝트 생성·삭제, 다운로드, 접근 요청·승인·거절, 권한 변경이다.
- 일반 활동은 사용자별로 요약하고, 삭제·권한 변경·접근 승인·거절은 행위자·시각·대상·행위 및 변경 내용을 건별로 표시한다. 연구실과 사용자·대상을 구분할 수 있어야 하며, 권한 변경은 어떤 권한이 어떻게 바뀌었는지 확인할 수 있어야 한다.
- 활동이 없는 날에도 ‘활동 없음’을 보낸다. 집계 일부를 읽지 못하면 ‘집계 불완전’으로 표시하며, 누락을 활동 없음으로 보고하지 않는다.
- Slack 전송·일일 집계 실패를 기록하고 재시도하여 늦게라도 전달한다. 중요한 장애 알림의 전송 여부가 불명확하면 누락 방지를 우선하고, 중복 가능성을 표시하여 재전송한다.

## 영향 범위
- 사용자 / 화면: 알림 수신자는 기존 Slack을 사용하는 개발자·운영자다. 개발 상태 채널과 사용자 활동 보고 채널을 분리한다. 일반 CoLAB 사용자에게 직접 알리는 화면·채널은 이번 대상이 아니다.
- 서비스 · 스키마 · 계약: 배포 결과 알림, 운영 상태 감지, 관련 AWS 상태 수집, 활동·다운로드·권한 변경 감사 기록 및 필요한 누락 사건의 기록, 일일 집계, Slack 전달·실패 기록이 영향 대상이다. 구체적인 구성과 변경 파일은 승인 후 spec에서 정한다.
- 계약 파괴 여부: 아니오 — 기존 제품 API·이벤트 계약의 파괴적 변경을 요구하지 않는다. spec에서 필요성이 발견되면 별도 결정 없이 변경하지 않는다.

## 제약
- 기존 미커밋 변경을 보존한다. 이번 intent 작성은 재배포·외부 알림 전송·자동배포 HOLD 해제·커밋·main push를 승인하지 않는다.
- 개발 알림은 현재 사용하는 개발·스테이징 환경을 구분한다. 일일 활동 보고에는 시험 활동을 포함하지 않는다.
- 기존 연구실 경계와 도메인 경계를 유지한다. 모든 연구실을 대상으로 하는 운영 보고에는 명시적인 운영자 수집 경로가 필요하며, 일반 사용자 조회 권한을 넓히는 방식으로 구현하지 않는다.
- Slack 보고는 행위·대상·결과와 운영 상태에 필요한 정보를 담는다. 자격증명·웹훅 주소·원시 요청 본문·파일 내용은 보고에 넣지 않는다.
- 기존 `scripts/deploy_release.py`는 배포·검증 성공 후 통지하며, 전송 결과 불명확 시 자동 재전송하지 않는다. 기존 구현 자체를 전체 알림 정책으로 취급하지 않는다. 이번에 합의한 ‘중요한 장애 알림은 중복 가능성을 표시해 재전송’과 적용 사건을 구분하여 spec에서 정합시킨다.
- 실제 채널 식별자·인증정보는 연결 단계의 환경 입력이다. 비밀값을 intent에 기록하지 않는다. 감지 임계값, 재시도 간격·상한, 사건 식별·중복 억제 방법, AWS 연결 방식, 시험 활동 식별 방법, Slack 메시지 분할 등 구현 세부는 승인 후 spec에서 검증 가능한 형태로 구체화한다. 제품 범위나 전달 원칙을 바꾸는 선택은 다시 사용자에게 묻는다.

## 설계트리 (grill-me 결과)
- Q1 누구를 위한 알림인가 → A 운영자만. 사용자용 알림 논의는 이번 범위에서 제외한다.
  - Q1a 어떤 목적을 나누는가 → A 개발 관점의 배포·서비스·백업 이상·복구 상태 알림과 운영 관점의 사용자 활동·감사 로그 일일 보고.
- Q2 전달 수단과 수신 대상은 무엇인가 → A Slack, 다른 개발자·운영자도 함께 수신한다.
  - Q2a 채널을 어떻게 나누는가 → A 개발 상태 채널과 사용자 활동 채널을 분리한다. 일일 보고·활동 요약·감사 상세는 사용자 활동 채널 하나에 함께 보낸다.
- Q3 개발 상태 알림의 시점은 언제인가 → A 배포 결과는 건별, 이상·복구는 감지 시 통지하고 같은 이상이 지속될 때 반복 통지를 줄인다(권고안 수용).
  - Q3a 감시 환경은 어디인가 → A 현재 사용하는 개발·스테이징을 구분해 알린다(권고안 수용).
- Q4 일일 보고 기준은 무엇인가 → A 매일 한국 시간 오전 8시, 전날 하루. 활동 없는 날도 보고한다(권고안의 오전 9시를 사용자가 오전 8시로 수정).
  - Q4a 대상과 사건은 무엇인가 → A 실제 사용 환경의 모든 연구실, 시험 활동 제외. 업로드·변경·삭제, 프로젝트 생성·삭제, 다운로드, 접근 요청·승인·거절, 권한 변경(권고안 수용).
  - Q4b 얼마나 자세히 보여주는가 → A 일반 활동은 사용자별 요약, 삭제·권한 변경·접근 승인·거절은 행위자·시각·대상·행위 및 변경 내용의 건별 상세(권고안 수용).
- Q5 실패와 불명확한 결과는 어떻게 다루는가 → A 집계·전송 실패를 기록하고 재시도한다. 집계 일부 누락은 ‘집계 불완전’으로 알린다. 중요한 장애 알림은 누락 방지를 우선하여 전송 여부가 불명확하면 중복 가능성을 표시해 재전송한다(권고안 수용).
