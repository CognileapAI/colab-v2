# Intent: 백오피스 관리자(운영자) 지정·해제와 관리자 전 연구실 열람
메타 — 발의자: Ted · 작성 2026-09-12 · 승인 2026-09-12(대화 확인 · 이 커밋)

## 문제
- 백오피스에서 서비스 계정만 추가할 수 있고 관리자(운영자) 계정은 SQL 로만 지정된다. 관리자 교체·퇴사 시 운영자가 DB 를 직접 만져야 한다.
- 관리자가 운영 문의를 처리하려면 소속 연구실 밖의 데이터도 봐야 하는데, 현재 모든 조회가 소속 연구실 경계로 잘린다.

## 원한 결과 (proposed outcome)
- 계정 목록의 각 행에 「관리자 지정 / 해제」 토글이 있고, 계정 추가 폼에 「관리자로 등록」 체크박스가 있다.
- 기존 관리자 누구나 지정·해제할 수 있다. 자기 자신 해제와 마지막 관리자 해제는 거절된다(항상 1명 이상).
- 관리자는 모든 연구실의 데이터를 **읽기 전용**으로 열람한다(카탈로그·데이터셋 상세·프로젝트·연구실 정보·계보·미리보기). 쓰기(수정·삭제·업로드·권한 변경)는 소속 연구실 범위 그대로다.
- 비관리자의 cross-tenant 음성 시험은 그대로 통과한다. 관리자 지정·해제 즉시 그 계정의 기존 로그인은 전부 종료된다(권한 변경 = 자격 버전 +1).

## 영향 범위
- 사용자 / 화면: 백오피스(토글·체크박스) · 관리자 로그인 시 연구실 선택/전체 보기 표시(기존 화면 재사용, 새 화면 없음).
- 서비스 · 스키마 · 계약: `service_operator` 지정·해제 엔드포인트(추가) · 스코프 커널에 관리자 전 연구실 **읽기** 스코프 추가 · RLS 정책에 관리자 읽기 경로 추가(플랫폼 마이그레이션 1건) · 세션 서명에 관리자 여부 반영.
- 계약 파괴 여부: 아니오(추가만).

## 제약
- 「모든 조회에 연구실 경계가 자동 주입된다」(`CLAUDE.md §3-5`)는 유지 — 관리자 스코프는 경계 해제가 아니라 **명시적 읽기 스코프**이며 쓰기에는 적용되지 않는다. cross-tenant 음성 시험은 비관리자·관리자 쓰기 둘 다에 유지된다.
- 관리자 여부는 `account_admin.service_operator` 행이 원본이며 세션 발급 시점에 서명에 실리고, 지정·해제 시 자격 버전 +1 로 기존 세션이 즉시 무효화된다.
- 비밀번호 원문 무노출 등 앞선 intent 약속 유지.

## 설계트리 (grill-me 결과)
- Q19 지정 방식 → A 목록 행 토글 ＋ 추가 폼 체크박스 (권장안 수용)
- Q20 누가·자기 보호 → A 관리자 누구나. 자기 자신 해제 금지 ＋ 마지막 관리자 해제 금지 (권장안 수용)
- Q21 효과 범위 → A 모든 연구실 데이터 열람 가능 (반대: 권고는 백오피스 접근만 — Ted 결정 「지금은 관리자는 모든 연구실 데이터도 열람가능해야함」). 구현 가정 = 읽기 전용 · 쓰기는 소속 범위.
