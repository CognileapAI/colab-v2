## 설계트리 (grill-me 결과)

- Q1 계보 확정 화면에 지금도 AI 가 자동으로 앞 데이터를 찾는가 → A 아니다. 실측 결과 화면에 누르는 버튼(`data-testid="lin-ask"`)이 이미 있고, 마운트 시 자동으로 부르는 방식은 이전 회차에서 이미 버튼 방식으로 바뀌어 있다. 이번 결정은 「자동 호출을 버튼으로 바꾼다」가 아니라 「버튼 자체를 없앤다」는 새 물음이다.
- Q2 등록 필수 항목을 넓히면 기존에 이미 등록된 데이터셋이 문제가 되는가 → A 아니다. 필수 검사는 새로 등록을 요청하는 시점에만 걸린다. 기존 행의 해당 값은 비어 있어도(데이터베이스 열은 nullable) 그대로 조회·수정된다. 수정 화면(`DatasetEditForm`)은 이번에도 그 값들을 강제하지 않는다(이름 한 글자 고치는 데 새 필수값을 강제하지 않기 위해서다) — 승인되면 등록과 수정의 필수 판정이 갈린 채로 남는다.
  - Q2a 그러면 화면이 이미 입력을 유도하고 있는데 왜 서버까지 맞추는가 → A 화면만 막으면 다른 경로(직접 호출 등)로 값 없이 등록이 가능해 화면 규칙이 유일한 방어선이 된다. 서버가 최종 방어선이어야 한다는 것이 이 프로젝트의 반복된 원칙이다. 실측 확인 — 커밋 `5049ca42` 이후에도 서버(`ingestion.py`)는 관측 간격·Lv0 출처 값 없이 오는 등록 요청을 여전히 성공시킨다.
- Q3 출처 칸 조건은 이미 반영이 진행 중인데 왜 다시 묻는가 → A 새로 반영하는 조건이 예전 판정과 다른 값이라, 판정을 다시 여는 것이 아니라 「새 근거(이번 기획서·구두 피드백)로 값이 갈렸다」는 사실을 기록하고 확인받기 위함이다.
- Q4(신규) 관측 간격·Lv0 출처 필수화도 예전 판정을 뒤집는 결정인데, 화면부터 먼저 짠 이유는 무엇인가 → A 사용자 결정(2026-09-14)이 「기획자 구두 피드백을 새 근거로 지금 구현한다」였고 Ted 서명은 구현 조건이 아니라 병합 조건으로 못박혔다(구현 커밋 본문 축자). 그 결과 화면·화면 시험은 이미 존재하고, 이 문서가 요청하는 것은 그 상태를 계약·서버까지 밀 것인지, 아니면 화면을 되돌릴 것인지의 판정이다.
- Q5(신규) 화면만 필수, 서버는 선택인 지금 상태를 그대로 두면 무엇이 나빠지는가 → A 두 경로가 갈린다 — 화면으로 등록하면 값이 강제되고 API 를 직접 호출하면 강제되지 않는다. 같은 데이터셋 종류인데 등록 경로에 따라 데이터 품질이 달라진다. 이 비대칭이 요구인지 결함인지가 이 문서의 ㉱·㉲ 판정 대상이다.
