# Intent: develop·product 브랜치 전환과 사람의 PR 병합에 따른 운영 배포 및 최초 reseed
메타 — 발의자: Ted · 작성 2026-09-15 · 승인 2026-09-15
## 문제
- 현재 main을 함께 사용하는 개발·운영 배포 원천을 분리하고, 사람이 GitHub에서 배포 PR을 병합하는 행위로 운영 배포를 결정하려 한다.
- 운영 환경을 최초 1회 dev reseed와 동일한 계정·데이터 구성으로 전면 교체해야 한다.
## 원한 결과 (proposed outcome)
- main을 기본 브랜치 develop으로 변경하고, 운영 배포 원천인 product 브랜치를 신설한다. 사용자 표현의 dev 브랜치는 develop을 뜻한다.
- product에는 같은 저장소의 develop에서 보내는 PR로만 변경을 반영한다. 직접 push 또는 다른 출발 브랜치의 반영을 차단한다.
- 사람이 develop → product PR을 직접 병합하면 해당 병합 결과의 운영 배포가 시작된다. 별도 배포 승인 단계는 두지 않는다.
- 첫 배포 PR에 기존 운영 데이터의 삭제·재적재 범위를 명시한다. 그 PR을 사람이 병합하면 배포와 최초 reseed·검증까지 실행한다.
- 최초 reseed는 기존 운영 데이터를 삭제하고 정본으로 전면 교체한다. dev reseed의 계정·역할·소속·데이터 구성과 로그인 비밀번호까지 동일하게 재현한다.
- 이후 일반 배포에서는 reseed를 실행하지 않는다. 실행 기록을 남겨 배포 재시도가 전체 초기화를 자동 반복하지 않도록 한다.
- 최초 reseed 도중 실패하면 운영을 점검 상태로 유지한다. 사람이 실행 기록과 정합성을 확인하고 재개를 결정한다.
- 운영 주소·환경 설정은 Ted가 별도로 제공할 파일을 기준으로 연결한다.
## 영향 범위
- 사용자 / 화면: 운영 최초 초기화 중 점검 상태와 재개 후 로그인·자료 조회. 기존 제품 기능의 변경은 요청하지 않는다.
- 서비스 · 스키마 · 계약: 브랜치 정본, GitHub 보호 규칙·CI·배포 연결, 배포 원천 검사, 최초 reseed와 계정·DB·저장 파일 초기화 및 검증. 스키마 설계 변경은 요구하지 않는다.
- 계약 파괴 여부: 아니오 — API·이벤트 계약 변경은 요청 범위에 없다. 기존 운영 데이터 삭제는 별도 명시된 요청 범위다.
## 제약
- CLAUDE.md §10과 docs/BRANCHING.md의 기존 main 단일 배포 원천 규칙은 이 intent 승인 후 새 정책에 맞게 함께 개정한다. 브랜치 이름만 바꾸고 CI·배포 검사의 origin/main 참조를 남기지 않는다.
- 기존 dev 전용 초기화 도구의 운영 환경 거부 조건을 단순 우회하지 않는다. 승인된 운영 대상·삭제 범위·첫 실행 여부를 확인하는 운영용 실행 경계를 마련한다.
- 현재 저장소에는 PR 병합으로 운영 배포를 시작하는 workflow가 없다. 기존 운영 배포 절차를 새 자동 배포 흐름에 연결해야 한다.
- 기존 reseed의 잔여 결함을 수정하고 dev에서 10단계 단일 실행의 전체 성공을 검증한 뒤 최초 운영 reseed를 진행한다. 준비 실패나 미실행을 성공으로 보고하지 않는다.
- 동일 구성 재현에 사용할 정본 입력과 계정 구성을 식별할 수 있게 고정한다. 비밀번호 값은 intent·로그·커밋에 기록하지 않고 외부 비밀 전달 경로를 사용한다.
- 실패 후 점검 상태 유지는 자동 데이터 복구를 의미하지 않는다. 사람이 재개를 결정하기 전 자동 전체 초기화나 자동 서비스 공개를 하지 않는다.
- 운영 설정 파일 수령과 실제 대상 식별은 운영 실행의 선행조건이다. 현재 초안 작성은 운영 데이터 삭제·배포 실행이 아니다.
## 설계트리 (grill-me 결과)
- Q1 사람이 배포를 결정하는 시점은? → A develop → product PR을 사람이 직접 병합하면 배포 시작. 별도 배포 승인 없음. (권장안 수용)
- Q2 최초 reseed에서 기존 운영 데이터는 어떻게 처리하는가? → A 기존 데이터 삭제를 포함하여 정본 자료로 전면 교체. (사용자 선택)
  - Q3 최초 reseed를 첫 배포 PR에 포함하는가? → A 삭제·재적재 범위를 PR에 명시하고 병합 후 초기화·검증까지 실행. 이후 배포에서는 제외. (권장안 수용)
  - Q4 운영에 어떤 구성을 재현하는가? → A dev reseed의 계정·데이터 구성까지 동일하게 재현. (권장안과 다른 선택, 별도 사유는 제시하지 않음)
    - Q5 비밀번호도 동일하게 유지하는가? → A 로그인 비밀번호까지 dev와 동일하게 유지. (권장안과 다른 선택, 별도 사유는 제시하지 않음)
  - Q6 최초 reseed 도중 실패하면? → A 점검 상태를 유지하고 사람이 재개를 결정. 일반 배포 재시도로 전체 초기화를 자동 반복하지 않음. (권장안 수용)
## 미해결 질문
- 없음 — 사용자 의도에 대한 질문은 닫혔다. 운영 설정 파일 수령과 실행 환경 확인은 후속 설계·실행의 선행조건으로 남는다.
## 범위 밖 (명시 제외)
- 정기적 운영 reseed 또는 배포 때마다 초기화.
- 사람의 PR 병합 뒤 추가 배포 승인 단계.
- product에 다른 브랜치의 PR 반영 또는 직접 push.
- 운영 비밀번호를 dev와 다르게 새로 발급하는 정책.
- reseed 실패 시 기존 데이터로 자동 복구하거나 자동으로 서비스를 다시 공개하는 동작.
- 이번 초안 작성 중 브랜치·원격 설정 변경, 배포, 데이터 삭제 실행.
