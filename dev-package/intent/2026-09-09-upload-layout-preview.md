# Intent: 기획 HTML 기준 업로드·상세 화면 재구성과 포맷별 미리보기 완성
메타 — 발의자: Ted · 작성 2026-09-09 · 승인 2026-09-09(사용자 "엉 그렇게해"로 범위 확인, 초안 제시 후 "자 다음"으로 후속 진행 지시)

## 문제
- 현재 업로드·데이터셋 상세 화면의 구성과 정보 배치가 기획 HTML과 크게 다르다. 기능 존재나 과거 작업대장의 완료 표시만으로 기획을 충족했다고 볼 수 없다.
- 실제 데이터 파일의 포맷별 미리보기가 동작하지 않는다는 사용자 보고가 있다. 업로드에서 저장·상세·계보·다운로드까지 실제 데이터로 연결되는지 다시 점검해야 한다.
- 전송·분석·미리보기 생성 중 사용자가 현재 상태를 놓치지 않아야 한다. 통신 오류 이후 진행 상태가 멈추거나 오류와 진행 표시가 함께 남을 위험을 코드에서 발견했으며 재현 검증은 아직 하지 않았다.

## 원한 결과 (proposed outcome)
1. 기획 HTML의 화면 구성과 사용 흐름을 실제 제품의 기준으로 삼는다. 단순히 같은 입력 항목을 두는 것이 아니라 모달 형태, 열 배치와 비율, 여백, 카드 묶음, 단계, 파일 배지, 하단 행동 줄, 상세 정보의 순서까지 비교한다.
2. 파일 선택 전 → 전송·분석 → 등록 입력의 장면을 구분한다. 입력 장면은 왼쪽 미리보기, 오른쪽 분류·메타데이터 입력·연결의 구조를 유지한다. 저장에 필요한 동작은 이 구성 안에서 완성한다.
3. 저장 후 상세 화면에는 실제 저장된 이름·파일 정보·분류·유형·가공 단계·기간·좌표계·관측 간격·원천·설명·변수 표가 채워진다. 계보·미리보기·활용과 접근 영역이 기획의 구조로 이어진다.
4. 실제 파일로 업로드 → 정보 저장 → 계보와 프로젝트 연결 → 상세 조회 → 편집·재조회 → 원본 다운로드를 검증한다. 계보 노드 이동, 연결 수정, 파일 묶음 다운로드도 해당 흐름에 포함한다. 예제 문구·그림·완료 토스트만으로 성공 판정하지 않는다.
5. 포맷별 실제 파일의 읽기·그림 생성·화면 표시를 각각 검증한다. 기획의 nc·tif·hdf·bin을 기본 검수 대상으로 삼고, 실제 등록 지원 포맷과 별칭·내부 구조를 대조해 빠진 미리보기 지원을 개선 대상으로 올린다. GRIB의 현재 미리보기 제외도 누락으로 드러내고 필요한 지원 작업을 검토한다. 기존 제외 안내를 정상 미리보기 성공으로 계산하지 않는다.
6. 업로드 미리보기·확장보기·상세 미리보기에서 그림, 좌표계와 경계, 확대·이동·초기화가 실제 데이터에 맞는다. 빈 영역·결측값·다중 변수·다중 파일도 확인하고, 일부 파일만 표시하면 그 대상을 사용자에게 알린다. 포맷의 하위 구조까지 무제한 지원한다고 약속하지 않고 실제 검수 파일과 결과를 남긴다.
7. 전송 → 분석 → 미리보기 생성 → 이미지 로딩과 표시까지 진행 안내가 끊기지 않는다. 바이트를 셀 수 있는 전송은 실제 비율, 진행률을 알 수 없는 단계는 단계명과 진행 표시를 사용한다. 목업의 타이머 기반 퍼센트를 제품에 복사하지 않는다.
8. 전송 100%, 분석 완료, 렌더 작업 완료, 실제 이미지 표시를 구분한다. 다음·확장보기·저장 버튼의 활성 조건을 각 실제 상태와 연결하고 미리보기 실패만으로 등록·계보·다운로드를 막지 않는다.
9. 느린 처리, 일시 통신 오류, 서버 실패, 이미지 로딩 실패, 일부 파일 실패, 취소·재시도, 단계 이동 중에도 상태가 누락되지 않는다. 오류를 알리고 복구 경로를 제공하며 오래된 응답이 새 파일의 상태를 덮지 않는다.
10. 같은 창 크기·같은 장면·같은 데이터 상태에서 기획과 구현을 시각적으로 대조한다. 번호별 정책 → rev2 변경 → 구현 → 실제 검증 근거를 연결하고 불일치·미검증 항목을 숨기지 않는다.

## 영향 범위
- 사용자 / 화면: 파일 선택 모달, 분석 진행, 등록 3단계, 업로드 미리보기와 확장보기, 데이터셋 상세·편집, 계보 연결·수정, 연관 프로젝트, 다운로드 및 오류·빈 상태.
- 서비스 · 스키마 · 계약: frontend의 업로드·미리보기·상세 흐름, core-api의 저장·조회·진행 상태, pipeline-worker의 파일 판별·분석, viz-render의 포맷 읽기·그림 생성·결과 전달을 점검한다. 구체적인 변경 파일과 계약 확장 필요성은 후속 명세에서 근거와 함께 도출한다.
- 계약 파괴 여부: 아니오(이번 intent는 기존 계약 파괴를 승인하지 않는다. 필요성이 발견되면 영향과 대안을 제시하고 별도 결정한다).

## 제약
- 다른 세션과 충돌하지 않는다. 이번 초안은 별도 작업 사본에만 기록한다. 기존 루트의 미커밋 변경·기획 원본·작업대장·서버·DB·배포 상태를 변경하지 않는다. 구현 시 별도 브랜치와 독립 실행 자원을 사용하고 병합 전 타 세션 변경과 대조한다.
- 화면 구성은 사용자 지시에 따라 HTML을 우선한다. 기존 코드나 과거 완료 기록을 이유로 달라진 화면 구성을 그대로 정당화하지 않는다.
- 저장·권한·공개 범위 및 기존 데이터에 영향을 주는 충돌은 화면 배치와 구분해 근거를 제시하고 별도 결정한다. 목업에 없는 기존 기능의 삭제나 임의 재배치까지 승인받은 것으로 보지 않는다.
- 연구실 경계, 도메인 분리, AI의 계보 직접 기록 금지 등 기존 불변 규칙을 유지한다. 생성 타입을 직접 수정하지 않는다.
- rev1의 번호별 정책 65개와 rev2의 화면·동작 변경을 구분한다. rev1 정책을 rev2의 확정 내용으로 오인하지 않고, 첨부 이미지의 번호와 실제 원문을 대조한다. 번호와 정책 패널은 기획 검수용이며 제품 UI로 복사하지 않는다.
- 이번 작업의 완료점은 구현과 실제 파일 검증을 마친 배포 가능한 상태다. 배포 시점은 다른 세션과 조율하며 이번 intent 자체가 배포 권한을 부여하지 않는다.
- 과거 GeoTIFF E2E와 CI 통과는 당시 기록이다. 이번 포맷별 검증이나 화면 일치의 증거로 재사용하지 않는다. 준비 실패·미실행·코드상 위험 후보를 실제 재현 또는 통과로 표현하지 않는다.

## 설계트리 (grill-me 결과)
- Q1 원본을 참고해 재기획할지 기존 제품을 기획에 맞출지 → A 기획 HTML 기준으로 현재 CoLAB의 차이와 누락을 보완한다(사용자: "엉").
- Q2 기능 범위 → A 실제 업로드부터 저장·계보·상세·다운로드까지 전체 흐름(사용자: "전체흐름").
- Q3 기존 데이터·권한·공개 범위와 충돌 → A 영향 있는 변경은 따로 설명하고 결정한다(사용자: "엉").
- Q4 완료점 → A 구현과 실제 파일 검증을 마쳐 배포 가능한 상태, 배포 시점 조율(사용자: "좋아").
- Q5 무엇이 핵심 문제인가 → A 화면 구성이 HTML과 다르고 포맷별 미리보기가 안 된다. 화면 일치를 부차적인 검수로 취급하지 않는다.
- Q6 기획을 그대로 복사하는가 → A 화면과 정책을 기준으로 저장 등 부족한 기능을 연결해 제품으로 완성한다. 업로드 후 실제 데이터로 상세 화면이 구성돼야 한다.
- Q7 진행 표시 → A 미리보기가 나타날 때까지 전송·분석·그림 생성·표시 상태를 빠짐없이 제공하고 실패·복구도 검증한다(최종 확인: "엉 그렇게해").
- Q8 정책 출처 → A rev1 HTML에서 번호 1~65의 내장 정책을 조회했고 rev2의 상태·이벤트 코드와 대조한다. 별도 정책 전송을 사용자에게 다시 요구하지 않는다.
