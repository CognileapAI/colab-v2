# infra/staging/backup — staging 백업 체계

> **지금 백업 대상이 붙어 있지 않다.** staging 에는 데이터 저장소가 없다(`../README.md`).
> 그래서 이 디렉터리는 **기구(機構)와 그 실증**이다. postgres 가 I2 로 올라오면
> 설정 한 줄(`COLAB_BACKUP_TARGET=postgres`)로 붙는다 — 다시 쓰는 일이 아니다.

## 왜 이렇게 생겼나

2026-07-11 ~ 08-17, PoC 백업은 **8주 내내 20바이트 빈 gzip 을 성공으로 기록**했다
(`dev-package/DEPLOY-CURRENT.md §8`). 원인 셋을 그대로 반대로 세운 것이 이 구조다.

| 사건의 원인 | 여기서의 대응 |
|---|---|
| ① 크론이 죽은 트리를 가리켰다 | 대상을 설정으로 **명시**한다. 대상이 없으면 `exit 78` — 조용한 성공이 없다 |
| ② 리다이렉션이 pg_dump 보다 먼저 파일을 만들었다 | 임시파일에 받고 `PIPESTATUS[0]` 확인. 실패 시 최종 경로에 **아무것도 남기지 않는다** |
| ③ 가드가 크기·`gzip -t` 만 봤다 | `verify-artifact.sh` 가 **CREATE TABLE 수 · 데이터 행 수 · 신선도**까지 본다 |

성공 신호가 "명령이 0 으로 끝났다" 인 백업은 백업이 아니다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `backup.sh` | 1회 백업. 검사 통과분만 최종본이 된다. 보존 정리 포함(최신 1개는 절대 안 지운다) |
| `verify-artifact.sh` | 산출물 검사 C1~C6. **fail-closed 의 본체** |
| `verify-restore.sh` | 복원 **결과** 검사 — 테이블 수 · 테이블별 행 수 · 총 행 수 |
| `roundtrip.sh` | 백업→파괴→복원 왕복 실증(리허설 인스턴스) |
| `selftest.sh` | fixture 10건이 전부 RED 임을 강제. 하나라도 GREEN 이면 셀프테스트가 실패한다 |
| `latest-check.sh` | 최신 산출물 재검사. 산출물이 **없는 것도 실패**다 |
| `schedule.crontab` · `install-schedule.sh` | 스케줄 선언과 설치. 경로는 실행 시점에 결정한다(①의 재발 방지) |
| `config.example.env` | 설정 예시. 비밀 없음 |
| `seed.sql` · `count-query.sql` · `content-digest.sql` · `expected-counts.tsv` | 리허설용. **staging 실데이터가 아니다** |

## 설정과 보관처 — 레포에 넣지 않는 것

- 설정 실값: 홈의 `.colab-v2-staging-backup.env` (권한 `0600`). `CF_TUNNEL_TOKEN` 과 같은 관행이다.
- 산출물: 기본 보관처는 **홈 아래 `colab-v2-backups/staging/`** — **레포 밖**이다.
  백업을 레포에 쓰면 git 이 데이터 저장소가 된다. 하지 않는다.

## 검사 항목 (verify-artifact.sh)

| | 검사 | 무엇을 잡나 |
|---|---|---|
| C0 | **합격선 자체가 숫자로 선언돼 있다** | **선언 없는 합격선이 전역 기본값 `1` 로 조용히 메워지는 것**(`〈171〉-㉯`) |
| C1 | 존재 · 1KiB 이상 | 0바이트 · 20바이트 빈 gzip |
| C2 | `gzip -t` | 절단·손상 |
| C3 | 해제 후 바이트 > 0 | **사건의 실물** — 압축은 멀쩡한데 알맹이가 0 |
| C4 | `CREATE TABLE` >= 20 | 스키마 없음 · 덤프 중간 절단 |
| C5 | 데이터 행 >= 합격선 | 구조만 있고 내용이 없는 덤프 |
| C6 | 신선도 <= 1500분 | **옛 성공본이 오늘의 백업으로 오독되는 것** |

## 실행

```bash
./selftest.sh          # fail-closed 증명 (docker 필요 — F8 이 실제 postgres 를 쓴다)
./roundtrip.sh         # 왕복 실증 (일회용 d1_* 컨테이너를 만들고 지운다)
./backup.sh            # 1회 백업 — 대상이 붙기 전에는 exit 78
./verify-artifact.sh <파일.sql.gz>
./install-schedule.sh show | install | remove
```

리허설 컨테이너는 `d1_` 접두사이고 **호스트 포트를 열지 않으며** PGDATA 를 tmpfs 에 둔다.
끝나면 지운다. 살아 있는 staging 컨테이너(`colab_v2_staging_*`)는 건드리지 않는다.

## I2 뒤에 붙이는 절차

1. 홈의 설정 파일에서 `COLAB_BACKUP_TARGET=postgres` 로 바꾸고
   `COLAB_BACKUP_PG_CONTAINER` · `_DB` · `_USER` 를 채운다.
2. `./backup.sh` 1회 → GREEN 확인.
3. `./install-schedule.sh install` — **여기서 처음 스케줄을 건다.**
   대상이 없는 동안 걸어 두면 매일 실패 메일이 쌓이고, 그 알람 피로가 8주 침묵의 메커니즘이었다
   (`DEPLOY-CURRENT.md §9`).
4. `./roundtrip.sh` 를 실데이터 규모에서 한 번 더 — 복원 시간이 실측된다.

## 프로파일 — 두 체인은 두 백업이다 (2026-08-23)

`COLAB_BACKUP_PROFILES="platform ai"`. 산출물 이름은 `<프로파일>-<타임스탬프>.sql.gz` 이고,
프로파일마다 합격선(`_MIN_TABLES_<p>` · `_MIN_ROWS_<p>`)이 따로다.
**한쪽만 백업된 상태는 성공이 아니다** — `selftest.sh` 의 F9 가 그것을 fixture 로 못 박는다.

**합격선은 코드가 쥔다 · 미선언은 RED** (2026-08-27 · `〈171〉-㉯`).
`platform` 190/20 · `ai` 45/4 의 기본값이 `lib.sh` 안에 있다 — 홈 env 파일에 키가 없어도 그 값으로 돈다.
선언이 **아예 없는 프로파일**(예: 새로 추가한 것)은 전역 `COLAB_BACKUP_MIN_ROWS=1` 로 떨어지지 않고
**C0 에서 RED** 가 난다. 종전 배선은 「행 1건이면 통과」를 새 프로파일마다 조용히 붙이고 있었다 —
볼륨 쪽 `volume_min_files` 의 조용한 `1`(`〈170〉-㉳`)과 **같은 모양**이다. `F10`·`F11` 이 fixture 다.

## 스케줄이 실패했을 때 어디에 보이는가

크론은 `run-scheduled.sh` 를 거쳐 실행된다. 실패하면 세 자리에 남는다.

| 자리 | 무엇 |
|---|---|
| `staging-backup.log` | `!!! <스크립트> 실패 (exit N)` 한 줄 |
| `BACKUP-FAILED.txt` | 실패 표식. **다음 성공에서만 사라진다** |
| `LAST-SUCCESS.txt` | 마지막 성공 시각. 크론이 아예 안 돈 경우를 이것으로 잡는다 |

여기에 더해 매주 월 04:10 `latest-check.sh` 가 최신 산출물의 **신선도(C6, 25시간)** 를 다시 묻는다.
백업이 조용히 멈추면 늦어도 그 주에 RED 가 된다.

**정직하게 적어 둔다 — 이 셋은 전부 "가서 봐야 보이는" 자리다.** push 알림 채널(메일·메신저)은
아직 없다(`§5-5`). 그것이 붙기 전까지 "실패했는데 아무도 모르는" 창은 최대 1주다.

## 볼륨 백업 (2026-08-27 · `R-1`)

**여기까지는 원장 두 개뿐이었다.** DB 만 되돌리면 **파일 행이 가리키는 바이트가 현재에 남는다** —
`WORK-UNITS §10.2` 의 `R-1` 행이 「볼륨 없이 닫으면 DB 만 과거로 가고 파일은 현재에 남는다」고 적은 자리다.

### 대상 — named volume 은 **정확히 둘**이다

`compose.i2.yml` 의 `volumes:` 는 `uploads` · `previews` 뿐이다.
**postgres 는 named volume 이 아니라 바인드 마운트**라 여기 없다 — 그쪽은 논리 덤프가 덮는다(물리 백업·PITR 은 없다).

| 볼륨 | 무엇 | 오라클 |
|---|---|---|
| `uploads` | 접수한 원본 바이트. `d3_file.storage_key` 가 곧 이 볼륨 안 상대 경로다(`contracts/storage/layout.json`) | **있다** — `d3_file` |
| `previews` | 미리보기 3층 산출물 | **없다** — 원장에 대응 행이 없다 |

> ⚠ **`previews` 의 「재생성 가능」은 지금 실제로는 거짓이다.**
> 재생성은 `viz-render` 렌더 재실행에 걸려 있고 그 기구는 **stage 2 범위**다. 그래서 백업한다(싸다).
> stage 2 에서 재생성 수단이 서면 이 판단을 다시 잰다.

### 순서 — **원장 덤프 먼저, 볼륨 tar 나중**

`backup-full.sh` 가 순서를 쥔다. 취향이 아니라 **오라클의 조건**이다.

- t0 에 원장, t1 에 볼륨. 저장키는 ULID 라 덮어쓰이지 않고 접수는 추가만 하므로
  **t0 에 원장이 가리키던 파일은 t1 에도 전부 있다** → 아카이브가 원장을 덮는다.
- [t0,t1] 접수분은 아카이브에만 있는 **고아 바이트**가 되는데, 그것은 초안 `§4.4-㈏` 가 이미 **정상으로 선언**한 상태다.
- **정지(quiesce)를 걸지 않는다** — 위 논증이 정지 없이 성립한다. 공개 staging 을 세울 이유가 없다.
- ⚠ **남는 가장자리 = [t0,t1] 사이의 삭제.** 그때는 오라클이 RED 를 낸다. **staging 에서 이것을 위해 설계하지 않는다** —
  발생하면 그 회차를 다시 돌린다. 조용히 통과시키는 완화(예외 목록·유예)를 넣지 않는다. 그 완화가 곧 「빠진 파일을 못 보는 가드」다.

### 검사 V1~V7 — `gzip -t` 를 신뢰하지 않는다

**`F2` 가 이미 값으로 보였다: 빈 gzip 20바이트는 `gzip -t` 를 통과한다.**
크기·무결성만 보는 가드가 8주를 통과시킨 것이 이 디렉터리의 출발점이다. 그래서 볼륨 쪽은 이렇게 본다.

| | 검사 | 무엇을 잡나 |
|---|---|---|
| V1 | 존재 · ≥ 1KiB | 0바이트 · 20바이트 |
| V2 | `gzip -t` | 절단·손상. **이것만으로는 보증이 없다고 출력에 적는다** |
| V3 | tar 로 열리고 **파일 항목 > 0** | 디렉터리만 든 아카이브 · 빈 tar |
| V4 | **매니페스트 ↔ 아카이브 경로·크기 전건 일치** | 매니페스트 위조 · 절단된 개별 파일 |
| V5 | ⭑ **짝 원장 덤프의 `d3_file` 대조** — 행 수 = 고유 저장키 수 ＋ 참조 경로 **전건 포함** | **원장이 가리키는데 백업에 없는 파일** |
| V6 | 볼륨별 최소 건수 — **오라클과 같은 세 상태**(`〈171〉-㉮`) | 거의 빈 아카이브 · **선언을 잊은 볼륨** |
| V7 | 신선도 | 옛 잔존 파일이 오늘의 백업으로 오독되는 것 |

매니페스트(`.manifest.tsv` — 경로·크기·sha256)는 **tar 와 같은 목록에서** 만들어진다.
그래서 둘은 구성상 같은 집합이고, V4 가 산출물만 보고 그 사실을 재확인한다.
`sha256` 은 여기서 쓰이지 않고 **복원 뒤 대조**에 쓰인다(`../restore/restore-volume.sh`).

**증명** — `selftest-volume.sh` 가 fixture **24건**을 전부 RED 로 강제한다. **docker 없이 돈다.**
그중 `VF5`(원장에 있는 파일이 아카이브에 없다)가 이 기구의 핵심 fixture다.

**V5·V6 두 선언은 같은 세 상태다** (`〈171〉-㉮`). 한쪽만 3상태로 두면 둘이 갈라진다 —
`ORACLE_<볼륨>=none` 이라는 **정당한 면제** 하나로 V5 는 승인된 SKIP 이 되는데
V6 는 조용히 합격선 1 이 되어 **파일 1건짜리 아카이브가 GREEN** 이 됐다. `VF19`·`VF20` 이 fixture 다.

| 값 | V5 오라클 | V6 최소 건수 |
|---|---|---|
| `<테이블명>` / `<숫자>` | 대조가 돈다 | 그 값으로 건수를 본다 |
| `none` | **명시 면제** — 승인된 SKIP, 요약줄에 건수가 실린다 | 같다 |
| 빈 값 · 미설정 | **RED** | **RED** |

### 보존 정책과 그 근거

| 대상 | 보존 | 근거 |
|---|---|---|
| 원장 덤프 (`*.sql.gz`) | **14일** | 종전 그대로. 수백 KB 수준이라 길게 둬도 싸다 |
| 볼륨 아카이브 (`vol-*.tar.gz`) | **3일** | 아래 |

**볼륨 3일의 근거 셋.**

1. **오프호스트 사본이 없다**(초안 `§2` #13) — 백업이 원본과 **같은 WSL2 디스크 1대** 위에 있다.
   보존을 늘리는 것은 안전을 늘리는 게 아니라 **한 디스크에 사본을 더 쌓는 것**이다.
2. **크기 비대칭.** 원본 풀은 **3.5 GB · 2,122 파일**(`SEED-DATA.md` 실측)이고 staging 원장은 그중 129 파일을 가리킨다.
   그리고 GeoTIFF·NetCDF 는 **이미 압축돼 있어 tar.gz 가 거의 안 줄인다** — 낙관하지 않는다.
   14일치를 두면 원장 덤프의 수천 배 부피가 같은 디스크에 쌓인다.
3. **되돌리기의 실효 창이 짧다.** 복원 재료로 실제 쓰이는 것은 **가장 최신본과 「복원 직전 백업」**이다(초안 `§4.7`).
   3일이면 주말을 낀 사고까지 걸친다.

⚠ **`[미확인]` — 볼륨의 실제 바이트 크기를 재지 않았다.** (재는 법: `backup-volume.sh` 의
디스크 사전점검이 매 회차 `볼륨 실사용 …KiB` 를 로그에 찍는다. 첫 GREEN 회차의 그 값이 실측이다.)
그래서 보존 일수를 크기로 정하지 않고 **런타임 가드**를 함께 세웠다 —
`COLAB_VOLBACKUP_FREE_MULTIPLIER`(기본 3): 볼륨 실사용 x 3 만큼 보관처에 안 남아 있으면 **시작하지 않는다.**
**디스크를 채워 staging 자체를 죽이는 백업**이 실재하는 위험이고, 그것은 일수가 아니라 여유로 막는 것이 맞다.

**어느 쪽이든 가장 최신 1개는 지우지 않는다** — 원장 쪽과 같은 규칙이다.

### 스케줄

`install-schedule.sh install` 이 거는 대상이 `backup.sh` → **`backup-full.sh`** 로 바뀌었다.
주간 `latest-check.sh` 도 **볼륨 아카이브를 같이 묻는다** — 원장만 살아 있고 볼륨이 조용히 멈춘 상태는
「DB 만 과거로 가고 파일은 현재에 남는」 복원을 예약해 둔 것과 같다.

**스케줄에 없는 백업은 한 번 돌고 삭는다.**

### 볼륨 백업이 정지했을 때 — **무엇이 서고, 무엇이 보이고, 어떻게 푸는가** (2026-08-27 · `〈171〉-㉰㉱`)

`backup-volume.sh` ①-b 는 볼륨 안에 **비밀 모양 파일**이 있으면 **그 볼륨의 아카이브를 만들지 않고 선다.**
조용히 빼지 않는 이유는 `〈170〉-㉰` 에 있다 — 빼면 아카이브와 원장이 어긋나 **V5 오라클이 거짓 RED** 를 내고,
사람이 그 RED 를 「원래 그렇다」로 읽게 된다. Ted 판정 「지우고, 생기지 않게 막는다」가 이 자세다.

**무엇이 서나** — 그 볼륨만이 아니다. `backup-full.sh` 는 볼륨이 하나라도 실패하면 **전범위 백업을 실패로 기록**한다.
원장 덤프는 이미 떠 있고, 그 회차의 볼륨 아카이브가 **통째로 없다.**

**판정기는 두 자리에서 다르다** (`lib.sh` 주석 참조).

| 자리 | 판정기 | 낱말(`token`·`secret`·`password`) | 왜 |
|---|---|---|---|
| 보관처 | `secret_shaped` | **잡는다** | 이름을 **기계가** 짓는다. 규약이 닫혀 있어 오탐 비용이 0 이고, 진짜 비밀 사본이 떨어질 자리다 |
| 볼륨 트리 | `secret_shaped_volume` | **안 잡는다** | 이름을 **연구자가** 짓는다. `station_token_map.csv` 는 수문 자료에 정상적으로 온다 |

확장자(`.env`·`.pem`·`.key`·`.envrc`) · 고정 이름(`id_rsa`·`credentials*`·`subjects*`) · 접속 문자열 키(`*_DB_URL*`)는
**두 자리 모두** 잡는다. 기준은 **낱말인가 모양인가**다 — 비밀이 볼륨에 흘러드는 경로는 어휘가 아니라 꼴을 갖는다.
⚠ **남는 위험을 적어 둔다**: 볼륨에 `api-token.txt` 라는 진짜 비밀이 놓이면 볼륨 판정기는 못 잡는다.
그 위험보다 **오탐 하나가 야간 백업을 세우고 아무도 모르는 위험**이 컸다는 것이 판단이다.

**어떻게 사람에게 닿나** — 세 자리다. 셋 다 「가서 봐야 보이는」 자리인 것은 그대로다(push 채널은 아직 없다).

| 언제 | 어디 | 무엇이 보이나 |
|---|---|---|
| 그날 밤 | `staging-backup.log` | `⛔ <파일 상대경로>` ＋ 「볼륨에서 치운 뒤 다시 돌린다」 |
| 그날 밤 | `BACKUP-FAILED.txt` | 실패 표식. **다음 성공에서만** 사라진다 |
| 다음 월요일 04:10 | `latest-check.sh` | ⭑ **표식을 읽어 RED 로 만든다** ＋ 볼륨 아카이브 **신선도(V7)** RED |

⭑ **월요일 검사가 표식을 읽는 것은 이번에 배선한 것이다** (`〈171〉-㉱`). 종전에는 표식을 **한 번도 읽지 않았다** —
「가서 보는」 유일한 기구가 그 표식을 안 봤다. 정지 시 사람에게 닿는 유일한 신호는 V7 의
「옛 잔존 파일이다」뿐이었고, **왜 멈췄는지가 거기 없었다.** `VF23` 이 fixture 다.

**어떻게 푸나.**

1. `staging-backup.log` 에서 `⛔` 줄의 **파일 이름**을 찾는다. (값은 어디에도 안 찍힌다 — 이름과 건수뿐이다)
2. 그 파일을 볼륨에서 **치운다.** 진짜 비밀이면 `〈163〉-㉲` 대로 **지우고, 어떻게 들어갔는지 막는다.**
3. `./backup-full.sh` 를 다시 돌린다. 성공하면 `BACKUP-FAILED.txt` 가 스스로 사라진다.
4. 사라지지 않으면 아직 안 풀린 것이다 — `./latest-check.sh` 로 되묻는다.

⚠ **오탐이라고 판단해도 예외 목록을 넣지 않는다.** 파일 이름을 바꾸거나 볼륨 밖으로 옮기는 것이 조치다.
예외 목록은 곧 「빠진 파일을 못 보는 가드」가 된다(`〈169〉` 이래 같은 자세).

### 실행

```bash
./selftest-volume.sh                       # fail-closed 증명 (docker 불필요)
./backup-full.sh                           # 원장 → 볼륨 (스케줄이 부르는 것과 같은 것)

./verify-volume-artifact.sh <vol-*.tar.gz> [--pair <덤프>] [--skip-age]
```
