## 2. 레인 · 워크트리

### 2-1. 병합 후 워크트리 3종 정리 — `worktree-cleanup-after-merge.md`

- 규칙 = 병합·푸시 직후 지시 없이 셋 다 삭제 — ⑴ `git worktree remove <경로>` + `git worktree prune` ⑵ `git branch -d <브랜치>`(`-D` 선사용 배제, 병합 확인 겸) ⑶ `git push origin --delete <브랜치>`.
- 근거 = 사용자 지적(2026-08-23) 「워크트리는 작업끝나면 항상 정리해야지 이것이 상식」. 잔존 시 `git worktree list`·브랜치 목록이 죽은 항목으로 증가하고 다음 세션이 생존 여부를 매번 재확인.
- 적용 = 삭제 후 `git worktree list`·`git branch -a` 로 실측 확인. `ExitWorktree` 는 세션이 워크트리 안일 때만 동작하므로 이미 나온 뒤에는 git 명령 사용. 병합 전이거나 미커밋 변경 잔존 시 삭제 보류.

### 2-2. 조사 산출물은 회수 즉시 커밋 — `commit-survey-artifacts-immediately.md`

- 규칙 = 서브에이전트 산출물(`dev-package/sessions/*.md` 등)은 회수 즉시 `git add` + 커밋 + push. 후속 에이전트 스폰은 그 다음.
- 근거 = 서브에이전트는 자기 워크트리에서 동작. 산출물이 본 체크아웃에 미추적으로만 있으면 워크트리에 부재하고, 지시문이 그 파일을 근거로 지목하면 에이전트가 읽지 못함(2026-08-29 한 세션에서 4회 발생). 부작용 = 미추적 사본 잔존 시 같은 경로가 원격에서 추적되기 시작하면 `git merge --ff-only` 거부.
- 적용 = 지시문에서 파일을 근거로 지목하기 전에 `git ls-files <경로> | wc -l` 로 `main` 존재 확인. 부재 시 지목 대신 내용을 지시문에 직접 적재.

### 2-3. 레인은 `isolation: "worktree"` 로 스폰 — `subagent-worktree-isolation-pin.md`

- **P-A 에이전트 정의로 강제 예정**(`lane-worker` frontmatter `isolation: worktree`) — 규칙문은 판독법 참고.
- 규칙 = 워크트리에 고정된 세션에서 스폰한 서브에이전트는 부모 핀을 승계하므로 **형제 워크트리 지시는 전부 실패**. 레인은 `Agent(isolation: "worktree")` 로 스폰하고 하네스가 만든 `.claude/worktrees/agent-<id>` · 브랜치 `worktree-agent-<id>` 를 사용.
- 근거 = 2026-09-03 레인 5개 동시 정지. `EnterWorktree(path=형제)` 는 성공을 반환하지만 Bash 가드가 따라오지 않아 `pwd` 한 줄도 거부, `git -C` 도 거부, `ExitWorktree` 는 서브에이전트에서 호출 불가. 원인 = 가드의 경로 포함 검사가 형제 경로를 공유 체크아웃으로 취급.
- 적용 = 기준이 `origin/<default>` 이므로 지시문 첫 줄에 `git merge --ff-only <통합 브랜치>` 와 기대 HEAD 기재. 손으로 만든 `git worktree add` 형제 워크트리는 사용하지 않음. 레인 최종 메시지에 `WORKTREE=… BRANCH=…` 기재, 병합은 오케스트레이터가 그 브랜치 이름으로 수행.

### 2-4. 새 워크트리 게이트 환경 구성 — `worktree-gate-env-setup.md`

- **훅/스크립트로 강제됨 — 규칙문은 참고** (P-E H2 `SubagentStart:lane-worker` + `worktree-setup.sh`).

- 적용 = 좁은 게이트만 도는 레인은 자기 단위분만 구성. 전수 판정은 호스트가 한가할 때 수행 — 부하는 일회용 postgres 준비 창을 넓힘.

## 3. 게이트

### 3-1. 반복 검증은 단독 게이트로 좁히고 작업은 직렬 — `narrow-gates-one-at-a-time.md`

- 규칙 = 반복 검증은 변경 대상 서비스의 단독 게이트(예 `service-tests-viz-render`)로 축소. 전수는 병합 직전 1회. 실행 레인은 한 시점에 하나.
- 근거 = 2026-09-05 Ted 질의 「시간이 뭐때문에 길어지는거지?」, 실측 원인 = 한도·529 끊김 복구 + 반복 전수 + 원장 정정 왕복. Ted 결정 「단독으로 좁히자, 하나씩 하자」.
- 적용 = 레인 지시문에 「반복 검증은 `<서비스>` 단독 게이트 N회 연속 green, 전체 게이트는 마지막 1회」 명시. 병렬은 진짜 독립 fan-out 에만. `PLAN-SoT §9` 원장 행 기입은 레인 지시문에 처음부터 포함해 정정 왕복 제거.

### 3-2. 같은 트리 전수 재실행 배제 — `no-redundant-gate-rerun-after-merge.md`

- 규칙 = 병합 커밋의 트리가 이미 전수 판정된 통합 브랜치 끝 트리와 동일하면 `main` 에서 전수를 다시 돌리지 않음. 동일성 확인 = `git log -1 --format=%T`.
- 근거 = 2026-09-05 Ted 가 중단시킴(「이미 충분히 했잖아」). 전수 1회가 10분 이상이고 같은 트리를 다시 재는 것은 근거를 더하지 않음. 「돌렸다」는 안도감을 위한 실행은 비용만 발생.
- 적용 = 병합 전에 통합 트리에서 전수 종료 → 병합 후 트리 해시 동일성 확인 → 원장에 「갈음」으로 기재. 재실행 조건은 트리 변경뿐. 문서만 바꾼 커밋은 원장 게이트 3종만 수행.

### 3-3. 「main 과 동일」은 수용 근거가 아님 — `same-as-main-is-not-ok.md`

- 규칙 = 레인 보고의 「이 오류는 main 에도 있다 · 기존 값 · 레인 기여분 0」을 수용 근거로 읽지 않음. main 과 같다는 것은 레인이 새로 만든 결함이 아니라는 뜻이고, main 의 건강 증명과 별개.
- 근거 = 2026-09-02 — 시험 파일의 `node:fs` 사용으로 `tsc --noEmit` 오류 4건 발생, 레인 5개가 전부 「main 동일」로 보고, 오케스트레이터가 기존 상태로 수용. 프런트 타입 검사가 Dockerfile 안에만 있고 게이트에 없어(green-by-skip 형제) main 은 12:01 부터 배포 불가였고 22:32 배포 창이 처음 밟음. 게이트 37 green 이 그 결함을 놓침.
- 적용 = ⑴ 「main 과 동일」이 붙은 red 는 즉시 **main 이 배포 가능한가**를 재질의 ⑵ 레인 지시문에 「기존 오류를 발견하면 '기존'이라 적지 말고 그 오류가 어느 검사(게이트·Dockerfile·배포)에 걸리는지 적어라」 포함 ⑶ advisor 게이트 ②에 「보고서가 기존 값이라고 넘긴 것」을 명시적 공격 대상으로 부여 ⑷ 검사가 Dockerfile·배포 스크립트 안에만 있고 게이트에 없으면 그 자체가 결함이므로 게이트로 승격.

### 3-4. 전수 실행 전 시험 환경 source — `gates-need-test-env-sourced.md`
