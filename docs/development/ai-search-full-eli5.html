자료와 개념의 연결

“이 자료에는 강수라는 근거가 있다”를 출처와 함께 기록합니다.

이번에 자동 갱신하도록 만든 대상입니다.

구조를 보여주는 예시입니다. 실제 자료·동의어의 등록 상태를 나타내는 그림은 아닙니다.

온톨로지와 KG를 왜 분리하나요?
공통 개념은 여러 자료가 함께 사용합니다. 자료 하나가 수정되었다고 공통 개념 자체를 다시 정의할 필요는 없습니다. 자료별 KG에는 원본 버전, 실제 인용, 참고한 개념의 버전을 저장합니다. 자료를 삭제하면 관련 연결은 검색에서 무효가 되지만, 별도 저장된 공통 온톨로지까지 함께 없어지는 구조는 아닙니다. 다만 온톨로지 DB 자체의 삭제·손상에는 별도 보호와 백업이 필요합니다.
02 / 검색 전에 준비하는 흐름

에이전트가 제안하고, 서버가 확인합니다.

자료 한 건이 바뀌었을 때의 순서입니다. 모델에게 전체 데이터베이스를 읽으라고 시키지 않습니다.

변경 기록 남기기

자료 수정과 함께 “이 자료를 다시 확인해야 한다”는 표시를 저장합니다.

현재 자료 읽기

지정 계정이 볼 수 있는 자료에서, 현재 버전의 사실을 가져옵니다.

관련 개념 좁히기

공통 온톨로지에서 관련 후보를 최대 6개 찾습니다.

Sonnet이 선택하기

후보 중 자료와 맞는 개념과, 자료에 실제 있는 문구를 제안합니다.

서버가 다시 확인하기

인용·개념·버전·권한이 맞는지 확인합니다. 중간에 자료가 바뀌어도 거부합니다.

한 번에 완료하기

사실·참고 기록·선택한 연결·처리 완료를 함께 저장합니다.

“모델이 그렇게 말했으니까”만으로 연결하지 않습니다.출처에 있는 개념 또는 확인된 동의어와 실제 인용이 있어야 합니다.
조금 더 자세히: 중간 결과가 잘못 저장되지 않게 하는 방법
  • 버전 고정: 조회한 사전 내용의 해시를 비교합니다. 중간에 사전이나 원본이 바뀌면 다시 확인해야 합니다.
  • 읽은 후보와 고른 후보를 구분: 선택하지 않은 후보도 판단에 영향을 주었으므로, 읽은 개념의 변경을 추적합니다.
  • 원자적 저장: 결과와 완료 표시를 하나의 DB 트랜잭션으로 묶습니다. 일부만 저장된 상태를 정상 완료로 취급하지 않습니다.
  • 후보가 없으면: 모델을 호출하지 않고 연결 0개로 처리할 수 있습니다. 정상 0개와 아직 처리하지 않은 상태는 따로 기록합니다.
  • 네트워크 대기: 모델 응답을 기다리는 동안 DB 트랜잭션을 계속 잡고 있지 않습니다.
03 / 사용자가 검색하는 흐름

검색은 미리 만든 연결을 활용합니다.

“강우 관련 자료를 찾고 싶어요.”

아래는 ‘강우’와 ‘강수’의 관계가 사전에 등록되어 있고, 자료 연결이 검증되었다고 가정한 설명용 예시입니다.

기존 질의 해석·사전 확장 경로에, 자료별 KG에서 찾은 후보를 더합니다.

자료와 맞는 이유를 보여줍니다. 모델이 결과 ID나 순위를 마음대로 정하지 않습니다.

검색할 때도 Sonnet이 모든 자료를 다시 읽나요?
이번에 추가한 Sonnet 어댑터의 역할은 자료가 갱신될 때 개념 연결을 제안하는 것입니다. 검색 요청 때 전체 자료를 Sonnet에 보내 연결을 처음부터 만드는 구조가 아닙니다. 기존 질문 해석 경로는 유지되며, 그 경로 전체를 이번 작업에서 Sonnet으로 바꾼 것도 아닙니다. DB는 기존 검색 점수·정렬 규칙을 유지하고 현재 유효한 연결로 후보를 보강합니다. 결과 설명에 붙이는 개념은 표시된 데이터셋마다 최대 3개입니다.
권한이 없는 자료는 언제나 검색에서 완전히 사라지나요?
비공개 본문에서 만들어진 연결을 통해 접근 권한을 우회할 수 없도록 검사합니다. 다만 기존 제품 정책상 목록에 보여도 본문은 잠겨 있을 수 있습니다. 따라서 “본문 기반 연결을 제외한다”와 “자료의 모든 목록 표시를 숨긴다”는 같은 뜻이 아닙니다. 기존 공개 메타데이터 검색·잠김 표시 정책은 유지됩니다.
04 / 매일 전체 자료를 다시 읽지 않는 방법

처음에는 목록을 나누어 읽고,
이후에는 바뀐 부분을 처리합니다.

처음 시작할 때

초기 목록을 조금씩 등록

어디까지 등록했는지 저장하므로, 중간에 멈춰도 이어서 진행할 수 있습니다.

그다음 갱신할 때

수정·삭제·무효화된 자료

초록색 부분처럼 변경 기록이 있거나 참고한 개념이 달라진 자료를 다시 확인합니다.

하루 한 번 갱신 ≠ 검색 결과를 하루 동안 무조건 믿기검색할 때도 현재 버전과 권한을 검사합니다. 오래된 연결은 다음 갱신 전이라도 제외될 수 있습니다.
‘하루 한 번’의 정확한 동작과 비용 한도
  • 정상 완료 후 다음 실행은 24시간 뒤입니다. 매일 특정 시각에 고정 실행하는 방식은 아닙니다.
  • 실행 루프는 30초마다 기한을 확인합니다. 초기 등록·미처리 작업은 60초 뒤 다시 확인합니다.
  • 계정별 공통 사전 버전 확인도 24시간 간격입니다. 바뀐 개념을 참고한 연결을 찾아 다시 처리합니다. 후보 발견 규칙이 바뀌면 영향 범위가 넓어질 수 있습니다.
  • 기본 회차는 최대 100건, 작업을 시작하는 시간 예산은 180초입니다. 이 값이 개별 요청의 엄격한 총시간 보장을 뜻하지는 않습니다.
  • 실패한 자료는 대기 시간을 늘려 재시도합니다. 미래 재시도도 미처리 상태로 남습니다.
  • 사전 내용은 한 버전의 메모리 스냅샷으로 재사용합니다. 이것이 제품 원본 전체를 매일 모델에 읽히는 것과 다릅니다.
05 / 에이전트의 권한

모델의 판단 범위는 작게,
저장 조건은 코드로 고정했습니다.

LLM · Sonnet

제안 담당

제공된 자료의 사실과 최대 6개 개념 후보에서 연결을 고릅니다.

새 개념 확정, SQL 실행, 파일 삭제 권한 없음
WORKER · 실행 담당

순서·재시도 담당

작업을 가져오고, 모델을 부르고, 실패와 재개 위치를 기록합니다.

자유롭게 도구를 고르는 무제한 에이전트가 아닌 고정 흐름
SERVER + DB

권한·저장 담당

인용·버전·접근 권한을 확인하고 허용된 결과만 저장합니다.

모델의 주장보다 실제 원본·DB 검사가 우선
기술 이름을 쉽게 풀면
  • Lease: 한 작업을 누가 처리 중인지 잠시 표시합니다. 작업자가 죽어도 기한이 지나면 다시 가져갈 수 있습니다.
  • Generation: 실행 회차 번호입니다. 옛 작업자가 늦게 돌아와 새 결과에 완료 표시를 붙이지 못하게 합니다.
  • Checkpoint: 어디까지 처리했는지 기록한 재개 위치입니다.
  • RLS: DB가 조회·저장마다 적용하는 행 접근 규칙입니다. 에이전트에게 “조심하라”고 말하는 것과 별개입니다.
  • Manifest와 hash: 사전의 내용이 같은지 비교하는 버전 목록과 내용 지문입니다.
  • Golden set: 질문·기대 결과·근거를 묶어, 검색이 개선됐는지 반복 확인하는 시험 자료입니다.
계정은 신뢰된 운영 설정에서 지정합니다. 사용자 질문이나 모델 출력으로 처리 계정을 바꿀 수 없습니다. 처리 범위는 그 계정이 실제로 접근할 수 있는 자료까지입니다.
06 / 직접 눌러 보는 상황 설명

이런 일이 생기면 어떻게 되나요?

아래 버튼은 설명 화면만 바꿉니다. 실제 검색·모델 호출·자료 변경은 실행하지 않습니다.

07 / 지금 어디까지 되었나

개발 완료와 운영 확인은 구분합니다.

현재 검사 통과만으로 과거 간헐 사례의 원인이 해결됐다고 말하지 않습니다.
최신 전체 회귀와 20회 연속 변경에서 재현되지 않았지만, 원인 확인은 남아 있습니다. 실패 0건이어도 대기 작업이 남아 있을 수 있어 처리량과 남은 작업을 함께 봐야 합니다.
검색 속도는 얼마나 달라졌나요?
격리된 시험 DB에서 유효 연결 1,002건의 실제 검색 API가 약 0.65초, 모두 오래된 연결이면 약 0.33초였습니다. 중간 구현에서는 100초 이상 걸리는 사례가 나왔고, 반복되는 연결 검사·DB 컴파일 비용·원본 접근 검사의 불필요한 반복을 줄였습니다. 이 수치는 실제 Sonnet 응답 시간을 포함하지 않는 특정 시험 결과이며, 운영의 모든 자료·동시 사용자에 대한 속도 보장이 아닙니다.
모델이 가짜였다는 것은 무슨 뜻인가요?
모델을 제외한 DB·HTTP·검증·저장 경로는 실제 코드로 검사했고, 모델 응답만 통제 가능한 시험 응답으로 바꿨습니다. 이를 통해 잘못된 인용이나 잘못된 후보를 거부하는지 확인할 수 있습니다. 그러나 실제 Sonnet이 좋은 후보를 고르는지, 자연어 질문을 잘 이해하는지는 따로 평가해야 합니다. 이번 회차의 실제 모델 호출은 0건입니다. 기본 제안 모델 설정은 claude-sonnet-4-5이며 변경 가능한 설정값입니다.
08 / 다음에 할 일

먼저 간헐 누락을 분류하고,
그다음 실제 환경에서 확인합니다.

1

어디에서 멈췄는지 확인

변경 기록 → 작업 가져오기 → 자료 읽기 → 모델 제안 → 저장 → 검색 중 어느 단계인지 추적합니다. 단순 대기와 실제 누락을 구분합니다.

확인할 값: 처리 건수, 남은 작업, 재시도 시각, lease, 원본 버전, 선택 결과
2

ST에서 배포·권한·복구 시험

격리된 계정과 시험 자료로 원본 수정, 권한 회수, 중단 후 재시작을 확인합니다. 온톨로지 보존과 복구 절차도 대조합니다.

완료 기준: 정한 시나리오대로 재개되고, 오래되거나 권한 없는 근거가 사용되지 않음
3

실제 Sonnet으로 골든셋 평가

보류가 해제되면 실제 레퍼런스 질문과 기대 결과를 비교합니다. 정답뿐 아니라 근거, 누락, 속도와 비용을 확인합니다.

완료 기준: 실패 사례마다 수정·한계·범위 밖 판정과 사유가 남음
