# product 운영 시작 전 최초 초기화

사용자가 product(pr)은 운영 전이며 기존 데이터를 모두 청소하겠다고 명시한 경우에 읽는다.
목표는 기존 사용자 데이터를 보존하는 전환이 아니라 승인된 대상의 삭제와 정본 재적재다.
이 문서는 실행 권한을 새로 부여하지 않는다.

## 실행 경로

1. 이미 승인된 환경·배포 SHA·삭제 범위·재적재 자료·계정 구성을 현재 계획에서 확인한다. 배포 완료 여부와 초기화 완료 여부를 구분한다.
2. `dev-package/tools/product-reseed/reseed.py`와 `services/core-api/ops/reset_product_environment.py`를 사용한다. dev 실행기의 환경 거부 조건을 바꾸거나 prod를 dev로 위장하지 않는다. 공통 seed 함수 재사용 시 도구 버전과 입력을 고정한다.
3. 실행 전에 입력과 모든 단계 연결을 확인한다. 계정 파일, 비밀번호 파일, 브라우저 세션, 정본 파일이 누락되면 삭제 전에 중단한다. 현재 실행기가 요구하는 백업·manifest·상태 조건을 문서만으로 면제하지 않는다. 서비스 중 데이터 보존을 가정한 추가 절차는 운영 전 목적에 맞게 계획에서 조정한다.
4. 삭제 대상을 실제 목록으로 고정하고 다른 환경에 닿지 않는지 확인한다. 공통 작업 스킬의 삭제 직전 검토를 적용한다. 독립 검토가 미실행이면 통과로 보고하지 않는다.
5. product 전용 실행 기록과 잠금 아래 최초 1회 수행한다. 성공 기록이 있으면 다시 초기화하지 않는다. 실패하면 비공개/점검 상태를 유지하고 자동 재초기화하지 않는다. dev 실행기의 실패 후 자동 기동 동작을 가져오지 않는다.
6. 계정별 로그인·권한·연구실 소속과 자료·프로젝트·연결·미리보기를 검증한 뒤 공개한다. 초기화만 끝난 상태를 재적재 완료로 보고하지 않는다.

## 계정 입력과 검증

- 이메일·이름·연구실·역할·관리자 여부는 이번 실행 설정에 둔다. 개인 이메일이나 비밀번호를 공용 스킬에 고정하지 않는다.
- 사용자의 “슈퍼관리자”를 실제 제품 권한과 대조한다. `account_admin.service_operator`는 계정 관리 권한이며, 연구실의 교수 역할이나 모든 연구실 자료 접근 권한과 같다고 추정하지 않는다.
- 연구실 미소속 관리자와 연구실 소속 교수를 구분한다. 사용자가 지정하지 않은 관리자 소속·교수 역할을 임의로 부여하지 않는다.
- 정본 bootstrap의 임시 교수 이메일을 실제 이메일로 바꿀 때는 동일 계정 ID의 신원·로그인 자격을 함께 반영한다. 임시 계정과 실제 교수가 중복되지 않았는지 확인한다.
- 계정별로 승인된 초기 비밀번호를 적용할 수 있는지, 첫 로그인 강제 변경 설정이 요청과 일치하는지 삭제 전에 확인한다. 공통 비밀번호만 지원하는 등 도구가 요청을 구현하지 못하면 준비 실패로 중단한다. 초기 비밀번호 지정과 영구 비밀번호 고정을 구분한다.
- 비밀번호는 보호된 파일로만 입력하며 값은 argv·로그·보고서에 쓰지 않는다. 로그인 검증이나 자료 적재 중 강제 변경을 수행했다면 사용자에게 전달할 초기 자격이 바뀌지 않도록 승인된 초기 상태로 정리하고 확인한다.
- 계정 하나라도 생성·권한·로그인 검증에 실패하면 성공으로 집계하지 않는다. 실제 최종 계정 목록과 요청 목록을 대조한다.
